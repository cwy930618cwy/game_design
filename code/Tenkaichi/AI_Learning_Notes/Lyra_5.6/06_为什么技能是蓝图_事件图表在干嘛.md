# 为什么技能还是一堆蓝图？事件图表在干嘛？

> **定位**：[05 速查手册](./05_各资产配置项速查手册.md) 里每个技能（`GA_Weapon_Fire` 等）都是 `.uasset` 蓝图，打开后除了配置格子，还有一张**事件图表（Event Graph）**。本文回答一个根本问题：**既然 `ULyraGameplayAbility` 已经是 C++ 基类了，为什么还要蓝图？那堆事件图表到底在写什么？**
>
> **一句话**：**C++ 写"规则与框架"，蓝图写"这个技能具体干什么"**。C++ 是"剧本模板"，蓝图是"这一场戏的具体演法"。

---

## 一、先破最大的误区

```
❌ 误区：  有 C++ 基类了，技能就该全写在 C++ 里，蓝图是多余的
✅ 真相：  C++ 只写"通用框架"，每个技能"具体做什么"留给蓝图填
```

**打个比方**（延续我们的剧院世界观）：

| 层 | 类比 | 谁来做 |
|----|------|--------|
| C++ 基类 `ULyraGameplayAbility` | **剧本模板**：规定"每个技能都要有：何时触发、耗什么、失败怎么办、和谁互斥" | 程序员（写一次，所有技能共用） |
| 蓝图 `GA_Weapon_Fire` | **这一场戏的具体演法**：开火这场戏——播开火动画、生成子弹、扣弹药、造成伤害 | 策划/设计师（每个技能各做一份） |
| 事件图表（Event Graph） | **导演给演员的走位指令**：先做啥、再做啥、什么条件下做 | 策划/设计师 |

> **核心认知**：如果全写 C++，每加一个技能（开火、换弹、跳跃、治疗……）都要程序员重新编译代码。现在**程序员写好"技能该有哪些环节"，策划在蓝图里"填空"即可**——这就是**数据驱动 + 蓝图扩展**。

---

## 二、C++ 到底做了什么？（看 `.cpp` 才知道）

我读了 `LyraGameplayAbility.cpp`，C++ 基类把**所有技能共用的"骨架逻辑"**都写死了：

### 2.1 构造函数：定死通用规则

```cpp
ReplicationPolicy  = ReplicateNo;           // 复制策略
InstancingPolicy   = InstancedPerActor;     // 每个角色一个实例
NetExecutionPolicy = LocalPredicted;        // 本地预测（手感好）
ActivationPolicy   = OnInputTriggered;      // 默认：按一下放一次
ActivationGroup    = Independent;           // 默认：独立，不挡别人
```

> 这些"每个技能都一样"的设置，写死在 C++ 里，蓝图**继承即可，不用重复配**。

### 2.2 重写了 GAS 的关键环节（框架级）

C++ 重写了这些引擎回调，插入 Lyra 的通用逻辑：

| C++ 重写的方法 | Lyra 往里加了什么通用逻辑 |
|----------------|--------------------------|
| `CanActivateAbility` | 检查"激活组是否被挡"（互斥规则） |
| `DoesAbilitySatisfyTagRequirements` | 处理死亡排除 + 标签扩展（互斥/必要条件） |
| `CheckCost` / `ApplyCost` | 除了蓝量，还要付 `AdditionalCosts`（如弹药），且支持"命中才扣" |
| `MakeEffectContext` | 把"武器/技能来源"塞进伤害上下文（用于距离衰减、材质倍率） |
| `OnGiveAbility` / `OnRemoveAbility` | 给/删技能时的通用处理 + 调用蓝图钩子 |
| `EndAbility` | 结束时自动清镜头模式 |

### 2.3 关键：C++ 留了"蓝图钩子"

注意 C++ 里这几行——它们**调用蓝图**：

```cpp
void ULyraGameplayAbility::OnGiveAbility(...) {
    Super::OnGiveAbility(...);
    K2_OnAbilityAdded();        // ← 调用蓝图！蓝图里可重写
    TryActivateAbilityOnSpawn(...);
}
```

这些 `K2_xxx` / `ScriptOnXxx` 就是 **`BlueprintImplementableEvent`**——**C++ 喊一嗓子，具体做什么由蓝图决定**。

## 三、那蓝图（事件图表）在写什么？

C++ 把"框架"搭好了，但**"这个技能具体放出来干什么"它不知道**——因为开火和跳跃做的事完全不同。这部分就在**蓝图的事件图表**里写。

### 3.1 蓝图重写 `ActivateAbility`（最核心）

C++ 的 `ActivateAbility` 只调了 `Super`，啥具体事都没干。**真正"开火"的逻辑在蓝图里**：

```
蓝图 GA_Weapon_Fire 的事件图表（示意）：

[Event ActivateAbility]  ← 技能被激活时触发
        │
        ▼
[播放开火动画 Montage]
        │
        ▼
[从枪口生成子弹 / 做射线检测]  ← 用武器实例 WID_Rifle 的散布/射程
        │
        ▼
[命中？]──是──▶[对目标施加 GE_Damage_RifleAuto]  ← 造成伤害
        │
        └─否──▶[播放打空特效]
        │
        ▼
[消耗弹药]  ← AdditionalCosts
        │
        ▼
[End Ability]  ← 结束技能
```

> 这张图就是"开火这场戏怎么演"。**每个技能一张，各不相同**——这就是为什么必须用蓝图。

### 3.2 蓝图实现各种"钩子事件"

| 蓝图里的事件 | 触发时机 | 蓝图里通常干什么 |
|-------------|---------|-----------------|
| `Event ActivateAbility` | 技能激活 | **主体逻辑**：放动画、发子弹、算伤害（最重要）。 |
| `Event OnAbilityAdded` | 技能被授予 | 加 UI 图标、初始化。 |
| `Event OnAbilityRemoved` | 技能被移除 | 移除 UI、清理。 |
| `Event OnPawnAvatarSet` | 角色附身完成 | 绑定角色相关数据。 |
| `ScriptOnAbilityFailedToActivate` | 激活失败 | 播失败音效/提示（C++ 已发通用消息，蓝图做表现）。 |

### 3.3 事件图表里常见的节点

打开 `GA_Weapon_Fire` 的事件图表，你会看到这类节点：

| 节点 | 作用 |
|------|------|
| `Ability Task - Play Montage` | 播动画（GAS 专用任务节点） |
| `Ability Task - Wait Target Data` | 等待玩家瞄准/开火数据 |
| `Apply Game Play Effect to Target` | 对目标施加伤害/效果 |
| `Get Ability System Component` | 拿到 ASC 查属性/标签 |
| `Branch` / `Sequence` | 条件判断 / 顺序执行 |
| `End Ability` | 手动结束技能 |

> `Ability Task` 是 GAS 蓝图的精华——它把"播动画、等事件、等输入"这类**异步操作**做成了可视化节点，事件图表就是靠它们串起"先做什么、再做什么"。

## 四、不只是技能——GAS 里"一堆蓝图"的完整清单

你看到"一堆蓝图"，其实不止技能本身。GAS 体系里**很多资产天生就是蓝图**：

| 资产 | 是蓝图吗 | 为什么用蓝图 |
|------|---------|-------------|
| `GA_Weapon_Fire`（技能） | ✅ 蓝图（继承 `ULyraGameplayAbility`） | 每个技能的具体表现不同，用蓝图填。 |
| `GE_Damage_Rifle`（伤害效果） | ✅ 通常是蓝图（数据型） | 只是"配置数据"：改哪个属性、改多少、持续多久，无需写代码。 |
| `GC_Hit_Fire`（GameplayCue） | ✅ 蓝图 | **纯表现**：命中特效、音效、镜头震动——美术/特效师在蓝图里搭。 |
| `ULyraAbilityCost`（消耗） | ✅ 蓝图（可实例化） | "消耗弹药""消耗蓝量"各有不同算法，用蓝图配。 |
| `AttributeSet`（属性集） | ❌ 一般 C++ | 血量/蓝量属性是通用逻辑，写 C++。 |
| `AbilitySystemComponent` | ❌ C++ | 通用组件，写 C++。 |

> **规律**：**通用、稳定、逻辑复杂** → C++（如 ASC、AttributeSet、技能基类）；**具体、多变、偏表现/数据** → 蓝图（如每个技能、每个伤害效果、每个特效）。

---

## 五、为什么不全部用 C++？（蓝图的价值）

| 全写 C++ 的问题 | 用蓝图的好处 |
|----------------|-------------|
| 加个技能要改代码、重新编译、重启编辑器 | 复制个蓝图、连几个节点，**几分钟出新技能** |
| 策划调数值/表现要等程序员 | 策划/美术**自己就能改**，不碰代码 |
| 表现层（动画/特效/音效）写 C++ 很痛苦 | 蓝图有现成的 `Ability Task`、动画/特效节点 |
| 一改动就要重新打包 | 蓝图可**热重载**，改了立刻见效 |

> **本质**：这是**"程序写引擎，策划做内容"**的分工。C++ 提供"能力（capability）"，蓝图提供"内容（content）"。Lyra 作为官方示例，正是要展示这套**可扩展的数据驱动架构**。

---

## 六、一句话总结

```
C++ 基类 ULyraGameplayAbility = "技能该有哪些环节"的框架（触发/消耗/互斥/失败/镜头）
        │ 留出蓝图钩子（K2_xxx）+ 让蓝图重写 ActivateAbility
        ▼
蓝图 GA_Weapon_Fire = "开火这场戏具体怎么演"（放动画→射子弹→算伤害→扣弹药）
        │ 事件图表 = 把上面这些用 Ability Task 节点串成流程图
        ▼
再配合：GE（伤害数据蓝图）+ GC（特效蓝图）+ AbilityCost（消耗蓝图）
```

> **记住**：**C++ 是骨架，蓝图是血肉**。你看到的一堆蓝图，正是 Lyra "让策划能自己造技能"的设计精髓——不是冗余，而是**分工**。

# 30 — 教学铁律：规划教学顺序必须先查真实依赖（.h+.cpp），排版必须清晰不乱

> **定位**：本文件沉淀 2026-10-08 阶段三（L3 系统基础）推进中暴露的两类问题——**依赖规划混乱**和**教程排版混乱**。核心教训一句话：
>
> **① 判断"某类现在能不能教"，必须先查该类 `.h` + `.cpp` 的完整真实依赖（不是只看 `.h`、不是只记一层、不是把软引用当无依赖），依赖要追到底；② 每份规划/讲义 md 的排版（层次、表格、编号、前后逻辑）要清晰，不能让用户看着乱。**

---

## 一、教训一：依赖混乱（根因 + 怎么避免）

### 直接现象

阶段三按总 md 分"线 A（独立优先）/ 线 B（带依赖）"两条线教。但推进到线 A 第 3 项 `TenkaichiGameData` 时卡住——它的 `.cpp` 里 `Get()` 硬调用了线 B 的 `TenkaichiAssetManager`：

```cpp
const ULyraGameData& ULyraGameData::Get()
{
	return ULyraAssetManager::Get().GetGameData();   // ← 依赖 AssetManager（被归到线 B）
}
```

**线 A 项依赖线 B 项**，"独立优先"的划分当场失效。继续往下追，发现 `AssetManager → PawnData → AbilitySet → AbilitySystemComponent → GameplayAbility → Character/PlayerController/HeroComponent……` 一路无底，基本等于把阶段五整个提前。

### 三个根因（对应三条硬规则）

| 根因 | 错误 | 正确做法 |
|------|------|---------|
| **只看 `.h`，没看 `.cpp`** | 总 md 判据只基于 `GameData.h` 的 `TSoftClassPtr` 字段，说"不影响编译" | **判断一个类能不能独立编译，必须同时看 `.h` 和 `.cpp` 的完整 `#include` + 运行时硬调用** |
| **把"软引用"当"无依赖"** | `TSoftClassPtr<UGameplayEffect>` 不阻塞编译，就以为整个类独立 | **软引用字段 ≠ 无依赖**。`.h` 软引用不阻塞编译，但 `.cpp` 里**硬调用**的外部类必须存在且能链接 |
| **依赖只记一层，不追到底** | 记了 `AssetManager → PawnData`，没继续查 PawnData 又依赖什么 | **依赖要追到底**：A 依赖 B，就继续查 B 依赖什么，直到全是"引擎类 / 插件 / 已教内容 / 已还原代码" |

### 连锁影响（不解决会怎样）

1. 线 A/B 划分失效，整条"独立优先"线跑不通。
2. 范围失控：还原一个 `GameData`，被迫连带还原 `AssetManager` → 整个 GAS 核心 + 角色体系，**基本等于把阶段五整体提前**。
3. 阶段节奏打乱：原"阶段三系统 → 阶段五 GAS"顺序被破坏。

### 通用避免方法（不只阶段三）

1. **教任何类前，先读它的 `.h` + `.cpp` 完整内容**，把所有 `#include` 和运行时硬调用的外部类都列出来。
2. **依赖要追到底**：A 依赖 B，就继续查 B 依赖什么，直到全是"引擎类 / 插件 / 已教内容"。
3. **区分软引用和硬依赖**：`.h` 里 `TSoftClassPtr` 不阻塞编译；`.cpp` 里硬 `#include` + 硬调用才决定能不能编译。
4. **别急着定"线 A/B 划分"**：先靠查证把每个类的真实依赖树画出来，再按依赖分层，而不是按"我以为它独立"分组。
5. **发现一个依赖断点，就回溯检查总 md 里同批所有类**——很可能不止一个判据是错的。

## 二、教训二：排版混乱（根因 + 怎么避免）

> 阶段三推进中，用户反馈**教程排版混乱**——规划、讲义 md 的结构让人看着乱。这暴露了 AI 在"把依赖树/教学顺序讲清楚"上的排版问题。

### 为什么会排版乱

1. **分层依据不清**：把"依赖别人的类"和"被依赖的类"混在一起罗列，没先画出清晰的依赖树，读者分不清谁在上谁在下。
2. **表格/清单堆砌，缺乏引导**：一次性丢大量表格、类名、依赖箭头，没有"先给一句话结论 → 再给细节"的引导结构，用户看不进去。
3. **顺序与依赖不一致**：列表顺序没按"自下而上"或"由浅到深"排，读者跟着走会撞到"这个类依赖的东西还没教"。
4. **缺少"断点/边界"的显式标注**：哪些类是能自包含的叶子、哪些是一碰就无底的节点，没在一开始就标清楚，用户中途才发现"原来这没法独立教"。

### 排版怎么做才清晰（硬动作）

1. **先给"一句话结论"**：每个规划 md 开头，用一两句话说清"这条线/这批类能不能独立教、真正的断点在哪"，再展开细节。
2. **先画依赖树，再排教学顺序**：依赖树用统一的"被依赖在下、依赖别人在上"的方向（和总纲 L1~L7 一致），先让读者看清结构，再给教学顺序。
3. **顺序严格按依赖由浅到深**：教学列表 = 自下而上的依赖树，读者跟着列表走不会撞到"没教的依赖"。
4. **显式标注"叶子 / 节点 / 断点"**：把"能自包含的叶子""一碰就无底的节点""真正的断点（缺插件/缺前置类）"用分组标题或表格列清楚，不要混在一个列表里。
5. **一张表讲透一类**：依赖关系用"类 | 依赖 | 能否独立编译"这种统一表头，别一会儿表格一会儿清单，格式前后一致。
6. **每个类标注"真实查证过的依赖"**：写明"`.h` + `.cpp` 都看过了"，给读者（和未来的自己）信心，也让"没查证就分组"没法再犯。

## 三、对照表（做什么 / 不做什么）

| 场景 | ✅ 我做 | ❌ 我不做 |
|------|--------|----------|
| 判断某类现在能不能教 | 读该类 `.h` + `.cpp` 完整依赖，追到底 | 只看 `.h` / 只记一层 / 把软引用当无依赖 |
| 画依赖关系 | 统一"被依赖在下"方向，标注叶子/节点/断点 | 把依赖别人的类与被依赖类混在一起罗列 |
| 排教学顺序 | 按依赖由浅到深（自下而上），跟依赖树一致 | 顺序跟依赖不一致，读者中途撞到未教依赖 |
| 写规划/讲义 md | 先一句话结论 → 再依赖树 → 再顺序 → 统一表格 | 堆表格/清单无引导，格式前后不一致 |

---

## 四、一句话结论

**规划教学顺序前，必须先查每个类的 `.h` + `.cpp` 完整真实依赖并追到底（区分软引用与硬依赖，绝不只看 `.h`、绝不把软引用当无依赖）；排版上先给一句话结论 → 画统一方向的依赖树 → 顺序严格自下而上 → 显式标注叶子/节点/断点 → 统一表格，做到清晰不乱。依赖没查透、排版讲不清，就不算规划好了。**

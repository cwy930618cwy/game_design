# 31 — 教学铁律：严格根据真实依赖来新建教程，禁"先省略/不影响编译/以后教"

> **定位**：本文件是 [30_规划必须先查真实依赖_排版必须清晰不乱](./30_规划必须先查真实依赖_排版必须清晰不乱.md) 的**进一步收紧**，也是 [23](./23_一比一完整还原_不做任何简化.md) / [25](./25_代码一比一完整写上_逻辑可后讲代码绝不能后补.md) / [26](./26_uproject模块声明字段也要一比一_别拿阶段当借口漏字段.md) 的**依赖版统一收口**。
>
> **一句话（用户原话要求）**：**严格根据依赖来新建教程。一比一还原，不存在"先省略、不影响编译、以后教"。** 教学顺序由**真实依赖链**决定——A 依赖 B，就**必须**先教 B；凡是拿"暂时用不到 / 不影响编译 / 后面阶段再补"当借口的，都是违规。

## 一、这条铁律怎么来的（真实教训，2026-10-08 阶段三）

阶段三（L3 系统基础）原规划按"线 A（独立优先）/ 线 B（带依赖）"分组，声称线 A 的 `TenkaichiGameData` 可以现在做。但推进时发现它 `.cpp` 的 `Get()` 硬调用了线 B 的 `TenkaichiAssetManager`，再往下追 `AssetManager → PawnData → AbilitySet → AbilitySystemComponent → GameplayAbility → Character/PlayerController/HeroComponent……` 一路无底。

**AI 之前的错误判据**（正是用户这次明令禁止的）：
> "`GameData.h` 里只是 `TSoftClassPtr<UGameplayEffect>` 软引用，**不影响编译**，可以现在教；依赖的 `AssetManager` 属于线 B，**以后教**。"

用户当场纠正，核心诉求就是这次铁律的主题：
> **"严格根据依赖来新建教程，我的要求就是一比一还原，不存在先省略、不影响编译、以后教。"**

**根因复盘**：
1. **把"教学顺序"当成了可以自由安排的事**，而不是被真实依赖**强制约束**的事。依赖是客观的，教学顺序必须服从它——A 依赖 B，就只能先 B 后 A，没有"反正不影响编译，我先教 A"的余地。
2. **"不影响编译"被误当成"可以省略"**。软引用确实不阻塞编译，但**软引用 ≠ 无依赖**——`.cpp` 里硬调用的类必须真实存在。即便真有个别符号不阻塞编译，"能编译"也不等于"该省略"，一比一还原要求**全都教、按依赖教**。
3. **"以后教"成了省略的挡箭牌**。凡是想跳过的，都用"这个到阶段 X 再教"糊弄过去，结果就是范围失控、顺序错乱。

## 二、核心规则（三条硬动作）

### 规则 1：教学顺序 = 真实依赖链的自下而上展开，A 依赖 B 就必须先教 B

- 教任何一类前，先查它 `.h` + `.cpp` 的**完整依赖**（所有 `#include` + 运行时硬调用），把依赖树画出来。
- **被依赖的先教，依赖别人的后教**。绝不允许"依赖的类还没教，就教依赖它的类"。
- 依赖树方向统一"被依赖在下、依赖别人在上"（和总纲 L1~L7 一致）。

### 规则 2：不存在"先省略""不影响编译""以后教"这三种说法

| ❌ 禁止的说法 | 为什么禁止 | ✅ 正确做法 |
|--------------|-----------|-----------|
| "这部分先省略，以后补" | 省略 = 违反一比一还原（23/25） | 该教就教，一个符号不落 |
| "这只是软引用，不影响编译，现在能教" | 软引用 ≠ 无依赖，`.cpp` 硬调用才是关键（30 号） | 查清 `.cpp` 硬依赖，按依赖排顺序 |
| "这个依赖到阶段 X 再教" | "以后教"成了省略挡箭牌，会范围失控 | 依赖没就位，依赖它的类就先不教；要么先补依赖 |

> **核心**：`TSoftClassPtr` 这种软引用字段**不等于**无依赖；真正决定能不能编译/能不能教的，是 `.cpp` 里的**硬 `#include` + 硬调用**。即便个别符号真不阻塞编译，"能编译"也不是"该省略"的理由——一比一还原要求**按真实依赖全部教、按顺序教**。

### 规则 3：依赖没就位时，要么先补依赖，要么就停，绝不跳过往下教

- 一个类的依赖链里有"未教 / 未装插件 / 未还原"的东西，这个类**现在就不能教**。
- 两个选择：**先补依赖**（自下而上把前置类教了），或者**明确停下来告诉用户**"这个类依赖 X，需要先教 X / 装 X 插件，不能跳过"，**让用户决定**。
- 绝不"先教这个，反正依赖以后补"。

## 四、对照表（做什么 / 不做什么）

| 场景 | ✅ 我做 | ❌ 我不做 |
|------|--------|----------|
| 某个类依赖另一个未教的类 | 先教被依赖的类（自下而上） | 先教这个类、说依赖"以后补" |
| 类里有软引用字段（TSoftClassPtr） | 仍查 `.cpp` 硬依赖，按依赖排 | 说"不影响编译"就跳过/提前教 |
| 依赖链里有未装插件（如 CommonGame） | 明确标注为断点，停下来让用户决定 | 假装能教、用"以后装"糊弄过去 |
| 判定一个类现在能不能教 | 看它完整依赖是否全就位 | 看它"会不会编译失败"来决定省略 |
| 规划教学顺序 | 严格按真实依赖自下而上展开 | 按"我以为独立"分组，自由排序 |

## 五、执行要求（每次规划/新建教程时自检）

1. **这个类依赖的东西，都教过了吗**？没教过的，就先去教那些被依赖的类。
2. **我有没有说过"先省略""不影响编译""以后教"**？说过 = 违规（除非用户明确说这块先跳过）。
3. **我有没有拿"软引用"当"无依赖"**？`.cpp` 硬调用查过了吗？
4. **顺序是依赖决定的，还是我拍脑袋定的**？A 依赖 B，我是不是先教了 A？
5. **依赖有断点（未装插件/未还原前置）时，我停下来让用户决定了吗**？还是自己糊弄过去了？

## 六、一句话结论

**新建教程必须严格根据真实依赖来排——A 依赖 B 就先教 B，自下而上、一比一还原；不存在"先省略""不影响编译""以后教"这三种说法。软引用不等于无依赖，`.cpp` 硬调用才是关键；依赖没就位就停下来补依赖或让用户决定，绝不跳过往下教。教学顺序不是自由安排的事，是被真实依赖强制约束的事。**

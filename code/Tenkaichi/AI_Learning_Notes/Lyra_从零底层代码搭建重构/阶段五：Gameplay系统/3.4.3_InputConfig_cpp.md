## 一、本文件要解决什么

`.h` 里声明了构造函数 + 2 个查询函数，这里写实现。

两个查询函数的逻辑几乎一样：**遍历对应的数组，找到 `InputTag` 相等的那条映射，返回它的 `InputAction`；找不到就按参数决定要不要打印错误日志。**

#include "TenkaichiInputConfig.h"

// 根据标签，在「原生输入」里找出对应的输入动作；找不到时按 bLogNotFound 决定是否打印错误日志
const UInputAction* UTenkaichiInputConfig::FindNativeInputActionForTag(const FGameplayTag& InputTag, bool bLogNotFound) const
{
	for (const FTenkaichiInputAction& Action : NativeInputActions)
	{
		if (Action.InputAction && (Action.InputTag == InputTag))
		{
			return Action.InputAction;
		}
	}

	if (bLogNotFound)
	{
		UE_LOG(LogTenkaichi, Error, TEXT("Can't find NativeInputAction for InputTag [%s] on InputConfig [%s]."), *InputTag.ToString(), *GetNameSafe(this));
	}

	return nullptr;
}

// 根据标签，在「技能输入」里找出对应的输入动作；找不到时按 bLogNotFound 决定是否打印错误日志
const UInputAction* UTenkaichiInputConfig::FindAbilityInputActionForTag(const FGameplayTag& InputTag, bool bLogNotFound) const
{
	for (const FTenkaichiInputAction& Action : AbilityInputActions)
	{
		if (Action.InputAction && (Action.InputTag == InputTag))
		{
			return Action.InputAction;
		}
	}

	{
		UE_LOG(LogTenkaichi, Error, TEXT("Can't find AbilityInputAction for InputTag [%s] on InputConfig [%s]."), *InputTag.ToString(), *GetNameSafe(this));
	}

## 四、逐段讲解

### 1. 头文件

```cpp
#include "TenkaichiInputConfig.h"
#include "TenkaichiLogChannels.h"
#include UE_INLINE_GENERATED_CPP_BY_NAME(TenkaichiInputConfig)
```

- 第一行：自己的 `.h`。
- 第二行：**`TenkaichiLogChannels.h`** —— 提供日志通道 `LogTenkaichi`（L1 阶段已教）。错误日志要打印到哪个通道，就在这定义。
- 第三行：`UE_INLINE_GENERATED_CPP_BY_NAME(TenkaichiInputConfig)`——UHT 内联生成宏，名字须与类名一致。

### 2. 构造函数

```cpp
UTenkaichiInputConfig::UTenkaichiInputConfig(const FObjectInitializer& ObjectInitializer)
{
}
```

- 空实现。UE 反射类必须匹配 `.h` 里声明的带 `FObjectInitializer` 的构造函数，这里无需初始化任何东西，所以是空的。

### 3. `FindNativeInputActionForTag`

```cpp
const UInputAction* UTenkaichiInputConfig::FindNativeInputActionForTag(const FGameplayTag& InputTag, bool bLogNotFound) const
{
	for (const FTenkaichiInputAction& Action : NativeInputActions)
	{
		if (Action.InputAction && (Action.InputTag == InputTag))
		{
			return Action.InputAction;
		}
	}

	if (bLogNotFound)
	{
		UE_LOG(LogTenkaichi, Error, TEXT("Can't find NativeInputAction for InputTag [%s] on InputConfig [%s]."), *InputTag.ToString(), *GetNameSafe(this));
	}

	return nullptr;
}
```

逻辑拆解：

1. **范围 for 循环** `for (const FTenkaichiInputAction& Action : NativeInputActions)`——遍历 `NativeInputActions` 数组，`const` 引用（只读不拷贝）。
2. **匹配条件** `if (Action.InputAction && (Action.InputTag == InputTag))`：
   - `Action.InputAction` 非空（这条映射真的存了输入动作，防止空指针解引用）；
   - 且这条映射的 `InputTag` **等于**传入的 `InputTag`。
   - 都满足 → 返回 `Action.InputAction`。
3. **找不到时**：如果 `bLogNotFound` 为 `true`，打印一条 `Error` 级日志，把没找到的标签和这个 `InputConfig` 资产名打出来，方便排查。
   - `*InputTag.ToString()`：`FGameplayTag` → 字符串（`*` 取字符串底层指针，`UE_LOG` 需要）。
   - `*GetNameSafe(this)`：`GetNameSafe` 安全地取对象名（即使对象无效也返回 `"None"` 而非崩溃）。
4. **兜底返回 `nullptr`**：整段没匹配到就返回空指针，调用方自己处理。

### 4. `FindAbilityInputActionForTag`

和上面**结构完全一样**，只是：
- 遍历的数组换成 `AbilityInputActions`；
- 日志文案换成 `"AbilityInputAction"`。

## 五、两个函数的对比

| 函数 | 遍历数组 | 日志文案 |
|------|---------|---------|
| `FindNativeInputActionForTag` | `NativeInputActions` | `NativeInputAction` |
| `FindAbilityInputActionForTag` | `AbilityInputActions` | `AbilityInputAction` |

## 六、几个要记住的点

1. **范围 for + `const &`**：遍历不修改时用 `const FTenkaichiInputAction&`，避免拷贝。
2. **先判空再比较**：`Action.InputAction && (...)`，防止空指针。
3. **`bLogNotFound` 默认参数**：调用方可省略（默认 true）或传 false 静默查找。
4. **`UE_LOG` 日志**：`*InputTag.ToString()`、`*GetNameSafe(this)`——都取 `*` 转为日志需要的格式；`GetNameSafe` 防崩溃。
5. **`LogTenkaichi`**：日志通道来自 `TenkaichiLogChannels.h`（L1 已教）。

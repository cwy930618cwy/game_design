## 一、为什么需要它（解决什么问题）

先搞清楚一个概念：**GameplayCue（能力表现）** 是什么。

GAS（Gameplay Ability System，能力系统）里，一个"技能"通常分两半：

- **Ability（能力）**：逻辑——造成多少伤害、加什么 Buff、消耗什么。
- **GameplayCue（表现）**：效果——技能打出来时放的**粒子特效、音效、屏幕震动**这类"看得见摸得着"的东西。

> 类比：Ability 是"这一拳的伤害数值"，GameplayCue 是"这一拳打出去的火花和音效"。

引擎里已经有个 `UGameplayCueManager` 负责管理这些表现（哪些 cue 加载了、怎么触发）。**但引擎原版有个性能痛点**：

> 引擎默认会把**所有** GameplayCue 在启动时一次性加载进内存。一个游戏几百上千个特效、音效，全塞内存里很浪费——尤其很多 cue 其实根本没被用到的能力引用。

`UTenkaichiGameplayCueManager` 就是 Lyra 对这个痛点的**优化方案**：**"延迟加载（Delay Load）"**——不一次性全加载，而是**某个 cue 真的被用到（它的 tag 被加载）时，才去异步加载它**。这样省内存、启动快。

> 一句话：**它把 GameplayCue 从"启动全加载"改成"用到才加载"**，是 GAS 表现层的地基优化。

## 三、它长什么样（全景）

### 3.1 类声明（`.h`）

```
UTenkaichiGameplayCueManager : public UGameplayCueManager
```

它重写了引擎父类的 **4 个"要不要加载"钩子**：

| 方法 | 干嘛的 |
|------|--------|
| `ShouldAsyncLoadRuntimeObjectLibraries()` | 运行时对象库是否异步加载 |
| `ShouldSyncLoadMissingGameplayCues()` | 缺的 cue 是否同步加载（返回 false） |
| `ShouldAsyncLoadMissingGameplayCues()` | 缺的 cue 是否异步加载（返回 true） |
| `OnCreated()` | 创建时挂监听 |

再加自己的核心能力：

| 方法 | 干嘛的 |
|------|--------|
| `Get()` | 从 `UAbilitySystemGlobals` 拿到全局单例 |
| `LoadAlwaysLoadedCues()` | 加载"无论如何都要常驻"的 cue |
| `RefreshGameplayCuePrimaryAsset()` | 刷新 cue 的主资产（打包进 bundle） |
| `DumpGameplayCues()` | 调试命令：打印当前加载的所有 cue |

内部还维护两组缓存：

| 成员 | 干嘛的 |
|------|--------|
| `PreloadedCues` | 客户端因"内容引用了它"而预加载的 cue 集合 |
| `AlwaysLoadedCues` | "代码引用/显式常驻"、永远加载的 cue 集合 |
| `PreloadedCueReferencers` | 记录"谁引用了这个 cue"（用于清理时判断） |

### 3.2 实现核心（`.cpp`）

三个关键机制：

1. **加载模式枚举 `ELyraEditorLoadMode`**（`.cpp` 内部）：
   - `LoadUpfront`：启动全加载（编辑器默认，省得 PIE 时"特效咋没出来"）。
   - `PreloadAsCuesAreReferenced_GameOnly`：运行时"被引用才预加载"。
   - `PreloadAsCuesAreReferenced`：一直"被引用才预加载"。

2. **"tag 加载 → 预加载 cue"的流水线**：监听 `UGameplayTagsManager` 的 `OnGameplayTagLoaded` 委托 → 一个 tag 被加载 → 在游戏线程异步去加载对应的 cue（`ProcessTagToPreload` → `RequestAsyncLoad`）。

3. **线程安全 + GC 配合**：因为 cue 加载可能跨线程/赶上垃圾回收，它用 `FCriticalSection` 加锁、用 `TGraphTask` 把处理切回游戏线程、GC 后再补处理（`HandlePostGarbageCollect`）。

> 这些机制到 `.cpp` 那一步再逐个展开讲，现在先有个全景即可。

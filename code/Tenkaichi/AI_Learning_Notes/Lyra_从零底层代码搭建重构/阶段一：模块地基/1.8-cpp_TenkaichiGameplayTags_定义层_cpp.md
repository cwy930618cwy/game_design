## 一、先讲为什么（这文件解决什么）

`.h` 里 `UE_DECLARE_GAMEPLAY_TAG_EXTERN(Ability_ActivateFail_IsDead)` 只是声明「有这么个变量」。但变量名 `Ability_ActivateFail_IsDead`（下划线）和真实 tag 字符串 `"Ability.ActivateFail.IsDead"`（点）是**两个不同的东西**，谁也没说它俩是一回事。

`.cpp` 的职责就是**把这两者绑定起来**：用 `UE_DEFINE_GAMEPLAY_TAG_COMMENT` 宏，告诉 UE「变量名 `Ability_ActivateFail_IsDead` 对应的 tag 字符串是 `"Ability.ActivateFail.IsDead"`，注释是『因为拥有者死亡导致技能激活失败』」。绑定后，代码里用变量名 `Ability_ActivateFail_IsDead` 就等于拿到那个 `FGameplayTag`。

> 一句话类比：`.h` 是「报名表」（声明有 35 个人名），`.cpp` 是「分配表」（给每个人发工牌：名字 ↔ 工号 ↔ 岗位说明）。

## 二、几个没教过 / 要讲清的点（铁律 18）

### 1. `UE_DEFINE_GAMEPLAY_TAG_COMMENT(TagName, Tag, Comment)` 三个参数

引擎真实定义（`NativeGameplayTags.h` 已核实）：

```cpp
#define UE_DEFINE_GAMEPLAY_TAG_COMMENT(TagName, Tag, Comment) \
    FNativeGameplayTag TagName(UE_PLUGIN_NAME, UE_MODULE_NAME, Tag, TEXT(Comment), ENativeGameplayTagToken::PRIVATE_USE_MACRO_INSTEAD); \
    static_assert(...)
```

三个参数分别是：
1. **`TagName`**：变量名（下划线版），和 `.h` 里 `UE_DECLARE_GAMEPLAY_TAG_EXTERN(TagName)` 的 `TagName` **必须一模一样**，才能「声明 ↔ 定义」对上。
2. **`Tag`**：真实 tag 字符串（点分层版），如 `"Ability.ActivateFail.IsDead"`。
3. **`Comment`**：给人看的说明文字，会显示在编辑器 Tag 管理器里。

> 展开后它其实是一个 `FNativeGameplayTag` 类型的**全局变量定义**，构造时就把 tag 注册进 `UGameplayTagsManager`。所以这 35 行代码「定义变量」的同时，就「把 35 个 tag 注册好了」。

### 2. 为什么是「构造时注册」而不是「显式调用注册」

`FNativeGameplayTag` 的构造函数会调用 `UGameplayTagsManager` 去注册这个 tag。因为它是**全局变量**，在模块加载时（静态初始化阶段）就被构造，于是 35 个 tag 自动全部注册完毕。这也是为什么 `.h` 里要用 `extern`——真正的「定义」（也即「注册」）发生在 `.cpp` 的这些全局变量上。

### 3. `const TMap<uint8, FGameplayTag> MovementModeTagMap = { ... }`

这是 C++ 的**聚合初始化**：`{ MOVE_Walking, Movement_Mode_Walking }` 表示「key = `MOVE_Walking`，value = `Movement_Mode_Walking`（那个 Tag）」。

- `MOVE_Walking` 等是引擎 `EMovementMode` 枚举里的值（`Engine/EngineTypes.h`），类型是 `uint8`（所以 TMap 的 key 是 `uint8`）。
- 作用：把「引擎的移动模式枚举」映射到「对应的 GameplayTag」，后面 L5 移动逻辑用「枚举」查「Tag」。

### 4. `CustomMovementModeTagMap` 为什么是空的

Lyra 预置了标准移动模式（走/导航走/下落/游泳/飞/自定义）的映射，但**自定义移动模式**要等你扩展游戏时才填，所以默认 `{ }`（空表）。注释也说明了：扩展时填这里。

### 5. `FindTagByString` 里的几个 API（源码已核实存在）

| API | 签名（`GameplayTagsManager.h` 已核实） | 作用 |
|-----|------|------|
| `UGameplayTagsManager::Get()` | `static UGameplayTagsManager& Get()` | 拿单例管理器 |
| `RequestGameplayTag(FName, bool)` | `FGameplayTag RequestGameplayTag(FName TagName, bool ErrorIfNotFound=true)` | 按名字精确查 Tag，第二个参数 `false` 表示「找不到不报错」 |
| `RequestAllGameplayTags(container, bool)` | `void RequestAllGameplayTags(FGameplayTagContainer&, bool OnlyIncludeDictionaryTags)` | 拿全部 Tag，第二个参数 `true` = 只拿字典里的 |
| `Tag.IsValid()` | `FGameplayTag` 成员 | 判断 Tag 是否有效（非 `None`） |
| `FGameplayTagContainer` 可迭代 | —— | `for (const FGameplayTag& TestTag : AllTags)` |

> 逻辑（先讲大概，详细后面 L5 用到再展开）：先精确查一次；查不到且允许部分匹配，就遍历所有 Tag 找「名字里包含输入串」的第一个，用 `UE_LOG` 打条提示日志。

	FGameplayTag FindTagByString(const FString& TagString, bool bMatchPartialString)
	{
		const UGameplayTagsManager& Manager = UGameplayTagsManager::Get();
		FGameplayTag Tag = Manager.RequestGameplayTag(FName(*TagString), false);

		if (!Tag.IsValid() && bMatchPartialString)
		{
			FGameplayTagContainer AllTags;
			Manager.RequestAllGameplayTags(AllTags, true);

			for (const FGameplayTag& TestTag : AllTags)
			{
				if (TestTag.ToString().Contains(TagString))
				{
					UE_LOG(LogTenkaichi, Display, TEXT("没找到 [%s] 的精确匹配标签，但找到了部分匹配标签 [%s]。"), *TagString, *TestTag.ToString());
					Tag = TestTag;
					break;
				}
			}
		}

		return Tag;
	}

## 五、两个成对核对（铁律 11）

1. **`.h` 声明 ↔ `.cpp` 定义 一一对应**：`.h` 里 35 个 `UE_DECLARE_GAMEPLAY_TAG_EXTERN(名字)`，`.cpp` 里 35 个 `UE_DEFINE_GAMEPLAY_TAG_COMMENT(名字, ...)`，变量名**逐个对应**、顺序一致。
2. **`FindTagByString`**：`.h` 声明（带默认参数 `bMatchPartialString = false`），`.cpp` 实现（函数体），签名一致。

> ⚠️ 一个易错点：`.h` 里 `FindTagByString` 声明带默认参数 `= false`，`.cpp` 实现里**不要再写** `= false`（默认参数只能出现一次，通常在声明处）。

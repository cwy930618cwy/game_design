# 1.8 — GameplayTags（游戏标签）：认识它为什么放模块地基

> **对应 Lyra**：`Source/LyraGame/LyraGameplayTags.h`（60 行）+ `LyraGameplayTags.cpp`（99 行）
>
> **一句话**：GameplayTag 是 UE 的一种「带层级名字的标签」，用来给游戏里的**状态、事件、输入、技能**打标记。Lyra 把所有要用的 Tag **提前一次性声明好**，放在模块地基，后面各层代码直接引用同一个 Tag 变量，不会出现「你写 `"Ability.ActivateFail.IsDead"`、我写 `"Ability.ActivateFail.Dead"`」这种拼写不一致的 bug。这一步先搞清楚「GameplayTag 是什么、为什么放地基、Lyra 声明了哪些」，还不写代码。

---

## 一、这一小步要解决什么问题

日志通道（1.7）解决的是「日志分类」。这一步解决另一个更基础的问题：**怎么给游戏里的各种东西打「统一标签」**。

想象一个场景：角色死亡了，技能系统要判断「这个技能能不能放」。技能系统会查「这个角色身上有没有『死亡』这个状态」。这个「死亡状态」怎么表示？

- 最笨的办法：定义一个 `bool bIsDead`。但「死亡」不止一个系统关心——动画要看（播死亡动画）、UI 要看（变灰）、队伍系统要看（减员）、技能系统要看（禁止放技能）……到处都是「死亡」判断，`bool` 分散在各处，一旦要加「濒死」「假死」就全乱套。
- 好办法：用**一个全局统一的字符串标签** `Status.Death`，谁需要就查「身上有没有 `Status.Death` 这个 Tag」。所有系统都认这同一个字符串，不会各写各的。

**GameplayTag 就是这个「全局统一标签」**：它本质是一个 `FName`（带层级、用点分隔的名字），由 UE 的 GameplayTags 系统统一注册、统一管理、可复制到网络。Lyra 在模块地基这一步，就把它项目里要用的所有 Tag **一次性声明成 C++ 变量**，后面直接用变量名（有编译器帮你查拼写），而不是到处手写字符串。

**验收**：读完本文，能说清「GameplayTag 是什么、为什么用变量而不是裸字符串、Lyra 声明了哪几类 Tag」。本步不写代码。

## 二、GameplayTag 是什么（先查引擎真实定义）

GameplayTag 是 `FGameplayTag` 结构体，本质包装了一个带层级的 `FName`。它的名字用 `.` 分层，像目录路径一样，例如：

```
Ability.ActivateFail.IsDead
│        │          └─ 具体原因：因为死亡
│        └─ 动作：激活失败
└─ 大类：技能
```

层级的好处：
1. **可读**：一眼看出这个 tag 属于哪个系统、干什么的。
2. **可批量匹配**：可以用「父级」匹配「子级」，比如查 `Ability.ActivateFail` 就能匹配到所有 `Ability.ActivateFail.*` 的失败原因。

---

## 三、为什么用「C++ 变量」而不是「裸字符串」（关键）

这是本步最核心的认知。

如果直接在代码里写字符串 `"Ability.ActivateFail.IsDead"`，会有一个大坑：**拼写错误编译器查不出来**。你写 `IsDead`、别人写 `IsDead`（少个字母）或 `IsDed`，运行时才发现匹配不上，极难排查。

Lyra 的做法：**把每个 Tag 提前声明成一个 C++ 变量**，例如：

```cpp
UE_DECLARE_GAMEPLAY_TAG_EXTERN(Ability_ActivateFail_IsDead);
```

这个变量名 `Ability_ActivateFail_IsDead`（下划线连起来）对应 tag 字符串 `"Ability.ActivateFail.IsDead"`（点分层）。以后代码里都用这个变量，**拼错了编译器直接报错**，从根上杜绝字符串不一致。

> 这就是 GameplayTag 放在「模块地基」的原因：它和日志通道一样，被 L2~L7 所有层依赖，所以必须最先建好，后面各层才能「用变量」而不是「手写字符串」。

## 五、两个关键宏（先讲清「声明 vs 定义」成对）

和日志通道的 `DECLARE`/`DEFINE` 一模一样，GameplayTag 也是「`.h` 声明、`.cpp` 定义」两件套（引擎源码 `NativeGameplayTags.h` 已核实）：

| 宏 | 放哪 | 作用 | 引擎真实定义（简化） |
|----|------|------|---------------------|
| `UE_DECLARE_GAMEPLAY_TAG_EXTERN(TagName)` | `.h` | **声明**一个 Tag 变量，别的文件 include 就能用 | `extern FNativeGameplayTag TagName;` |
| `UE_DEFINE_GAMEPLAY_TAG_COMMENT(TagName, Tag, Comment)` | `.cpp` | **定义** Tag，绑定「变量名 ↔ 真实字符串 ↔ 注释」 | `FNativeGameplayTag TagName(..., Tag, Comment, ...);` |

注意 `UE_DEFINE_GAMEPLAY_TAG_COMMENT` 有三个参数：
1. `TagName` = 变量名（下划线版，如 `Ability_ActivateFail_IsDead`）
2. `Tag` = 真实 tag 字符串（点分层版，如 `"Ability.ActivateFail.IsDead"`）
3. `Comment` = 这个 tag 的说明文字（给人看，会显示在编辑器 Tag 管理器里）

> 关键理解：**变量名（下划线）和 tag 字符串（点）是两个东西，靠这个宏绑定在一起**。`.h` 里只写变量名，`.cpp` 里把「变量名 → 字符串 → 注释」三者绑定。

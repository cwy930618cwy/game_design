# P05.5-3 `ALyraTaggedActor` —— 总 md

## 一、这个类要解决什么

P05.5-1 教了"效果上下文"（GE 执行时带的信息），P05.5-2 教了"目标数据"（命中信息怎么填进上下文）。这两个都是 **GAS 内部的数据结构**。

`ALyraTaggedActor` 完全不同——它是**场景里能摆的 Actor**，而且它是整个 P05.5 里**最简单的一个类**（Lyra 只有 36 行 `.h` + 30 行 `.cpp`）。

**它解决一个很具体的问题**：

引擎的 `AActor` 自带一个 `Tags` 属性（`TArray<FName>`），可以给 Actor 打标签。但这个 `Tags` 是 **FName 数组**——纯字符串，没有层级、没有校验、拼写错了编译器也不管。

GAS 生态里用的是 **`FGameplayTag`**（GameplayTag 容器）：有层级（`Weapon.Rifle.Heavy`）、有编辑器校验、能在 GameplayEffect 里做匹配查询。**但普通 `AActor` 不支持 GameplayTag。**

所以 Lyra 做了一个**带 GameplayTag 的 Actor 基类**：

> 继承 `AActor` + 实现 `IGameplayTagAssetInterface` → 这个 Actor 就能被 GAS 的标签查询系统识别了。

**典型用途**：场景里摆一个"掩体"/"补给箱"/"传送门"，给它打上 `World.Cover` 或 `Interactable.Supply` 标签，技能/查询系统就能通过标签找到它、判断能不能交互。

**核心一句话**：它把 GAS 的 GameplayTag 能力"嫁接"到普通 Actor 上，让场景里的物件也能参与标签系统。

## 二、全景：这个类长什么样

| 项 | 内容 |
|----|------|
| **Lyra 文件** | `AbilitySystem/LyraTaggedActor.h/.cpp`（36 / 30 行） |
| **类型** | `UCLASS()`（**真正继承自 AActor 的类**，和前两个 USTRUCT 不同） |
| **继承** | `AActor` + `IGameplayTagAssetInterface`（**双继承**：类 + 接口） |
| **字段** | 只有 1 个：`FGameplayTagContainer StaticGameplayTags` |
| **方法** | 构造函数、`GetOwnedGameplayTags`（接口实现）、`CanEditChange`（仅编辑器） |

**三个方法各自的角色**：

| 方法 | 作用 | 特点 |
|------|------|------|
| 构造函数 | 空实现，只转发 `ObjectInitializer` | 最简形式 |
| `GetOwnedGameplayTags` | **接口实现**：把本 Actor 的标签追加到传入的容器 | 类的核心功能 |
| `CanEditChange` | 编辑器专用：禁止编辑 `AActor::Tags` 那个 FName 数组 | **`#if WITH_EDITOR` 包裹**，打包时不编译 |

## 五、几个要记住的点

1. **它是 P05.5 里唯一的 `UCLASS`**：前两个（EffectContext / SingleTargetHit）都是 `USTRUCT` 结构体，本类是真正能摆进场景的 Actor。
2. **双继承是这里的关键**：`AActor`（拿到 Actor 的一切）+ `IGameplayTagAssetInterface`（拿到"可被标签查询"的能力）。**接口是 UE 的 UINTERFACE 机制**，用 `public` 继承。
3. **只加一个字段**：`StaticGameplayTags`。名字里的 `Static` 表示"在编辑器里静态配置的、运行时不变"——区别于运行时动态添加的标签。
4. **为什么能"静态"**：因为它不复制、不动态改，就是在关卡里摆好、在细节面板配好，运行时只读。所以 `GetOwnedGameplayTags` 只有一行 `AppendTags`。
5. **`CanEditChange` 是编辑器专属**：`#if WITH_EDITOR` 包裹，打包版本整个不存在。它的作用是**禁止美术/策划去改 `AActor::Tags` 那个 FName 数组**（强制他们用 GameplayTag，避免两套标签系统混用）。
6. **零挂起**：纯引擎依赖，直接可编译。

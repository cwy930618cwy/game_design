## 四、逐段讲解

### 1. 头文件与前置声明

```cpp
#pragma once
#include "AbilitySystemGlobals.h"
#include "TenkaichiAbilitySystemGlobals.generated.h"

class UObject;
struct FGameplayEffectContext;
```

- `#include "AbilitySystemGlobals.h"`：引入引擎基类 `UAbilitySystemGlobals`（引擎 GAS 自带）。
- `#include "...generated.h"`：UHT 生成的头文件，**必须放在所有 include 之后**（固定规则）。
- `class UObject;` 前置声明：源码里有但此处实际未直接使用，是 Lyra 原文自带的，按铁律 23 一字不砍保留。
- `struct FGameplayEffectContext;` 前置声明：函数返回它的**指针**（`FGameplayEffectContext*`），
  不需要完整定义，前置声明即可——不阻塞 `.h` 编译。

### 2. 类声明

```cpp
UCLASS(Config=Game)
class UTenkaichiAbilitySystemGlobals : public UAbilitySystemGlobals
{
	GENERATED_UCLASS_BODY()
	...
};
```

- `UCLASS(Config=Game)`：这个类的属性可以从 `DefaultGame.ini` 等 Game 级配置文件读取/覆盖。
  引擎的 `UAbilitySystemGlobals` 本身就是 Config 类，Lyra 沿用。
- `GENERATED_UCLASS_BODY()`：UHT 生成宏，为带构造函数的 U 类生成必要的构造辅助（配合 `.cpp` 里
  `ULyraAbilitySystemGlobals::ULyraAbilitySystemGlobals(const FObjectInitializer&)` 构造函数）。
  **注意是 `UCLASS_BODY`，不是 `UCLASS_BODY` 之外的形式**——因为子类要带构造函数。

### 3. 重写的方法

```cpp
virtual FGameplayEffectContext* AllocGameplayEffectContext() const override;
```

- `override`：明确重写引擎基类的虚函数。
- 返回 `FGameplayEffectContext*`：GAS 每创建一个「游戏效果」时，都会调用这个函数分配它的上下文对象。
  我们重写它返回 `FLyraGameplayEffectContext`（在 `.cpp` 里，⚠️ 挂起）。
- `const`：分配动作不修改单例本身。

## 五、几个要记住的点

1. **GENERATED_UCLASS_BODY**：因为要写构造函数，用 `UCLASS_BODY` 而不是默认的 `UCLASS_BODY` 变体——对应 `.cpp` 里的构造函数。
2. **前置声明返回指针**：`FGameplayEffectContext*` 用前置声明即可，`.h` 不依赖 EffectContext 完整定义 → 零挂起。
3. **Config=Game**：GAS 全局行为配置可从 ini 读取，是 GAS 项目级定制的标准姿势。

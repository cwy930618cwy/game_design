# P05.5-4-2 GamePhaseSubsystem —— 教 .h

## 一、本文件要解决什么

把总 md 里"阶段系统的大脑"这个类落成真实的 `.h` 文件。`TenkaichiGamePhaseSubsystem.h` 定义一个 `UTenkaichiGamePhaseSubsystem` 类——它继承引擎 `UWorldSubsystem`，是整套阶段系统的**管理者 + 裁判**。

**这个 `.h` 是全组最长的（Lyra 106 行）**，因为它除了类本身，还要定义**配套的一整套"词汇表"**：

| 内容 | 数量 | 作用 |
|------|------|------|
| **4 个委托声明** | `DECLARE_DELEGATE` × 2 + `DECLARE_DYNAMIC_DELEGATE` × 2 | 对外回调接口（原生版 + 蓝图版） |
| **`EPhaseTagMatchType` 枚举** | 2 个值 | 标签匹配方式（精确 / 部分） |
| **2 个内部结构体** | `FLyraGamePhaseEntry`、`FPhaseObserver` | 活跃阶段条目、观察者 |
| **类本身** | 11 个方法 + 3 个成员 | 阶段管理逻辑 |

**为什么要"原生 + 动态"两套委托？**

- **原生委托**（`DECLARE_DELEGATE`）：C++ 专用，快，但不能被蓝图使用。
- **动态委托**（`DECLARE_DYNAMIC_DELEGATE`）：蓝图可用，慢一点（走反射）。
- Lyra **两套都声明**，然后提供 `K2_` 前缀的蓝图函数，在函数内部把动态委托**转成**原生委托。**这是 UE 里"同一套 API 同时服务 C++ 和蓝图"的标准做法。**

> 依赖纯引擎头（`WorldSubsystem` / `GameplayTagContainer` / `GameplayAbilitySpecHandle`）+ `GamePhaseAbility` 仅前置声明，**零挂起可独立编译**。

## 四、逐段讲解

### 1. 头文件引用

```cpp
#include "GameplayAbilitySpecHandle.h"
#include "GameplayTagContainer.h"
#include "Subsystems/WorldSubsystem.h"

#include "TenkaichiGamePhaseSubsystem.generated.h"
```

三个引擎头，全部是**本文件直接需要的类型**：
- `GameplayAbilitySpecHandle.h` —— `FGameplayAbilitySpecHandle`（`ActivePhaseMap` 的 key）
- `GameplayTagContainer.h` —— `FGameplayTag` / `FGameplayTagContainer`
- `Subsystems/WorldSubsystem.h` —— **基类 `UWorldSubsystem`**
- `TenkaichiGamePhaseSubsystem.generated.h` —— 反射生成头（必须最后）

> ⚠️ **没有 include 任何 Lyra/Tenkaichi 类的头** —— `UTenkaichiGamePhaseAbility` 只是下面的一行前置声明。**这就是零挂起的原因**。

### 2. 前置声明块

```cpp
template <typename T> class TSubclassOf;

class UTenkaichiGamePhaseAbility;
class UObject;
struct FFrame;
struct FGameplayAbilitySpecHandle;
```

- **`template <typename T> class TSubclassOf;`** —— 模板前置声明（注意要带 `template <typename T>`）。`TSubclassOf<UTenkaichiGamePhaseAbility>` 在下面 4 个方法签名里用到。
- **`class UTenkaichiGamePhaseAbility;`** —— ⚠️ **关键**：本类 `.h` 只用它的**指针**（`const UTenkaichiGamePhaseAbility*`），前置声明就够。**不需要 include**，所以避免了和 4-1 的互相依赖（死结处理铁律里说的"`.h` 里前置声明不阻塞编译"）。
- **`class UObject;` / `struct FFrame;` / `struct FGameplayAbilitySpecHandle;`** —— 都是签名里用到的类型，前置声明即可（`FGameplayAbilitySpecHandle` 明明上面 include 了，Lyra 还是再声明一次——照抄，无害）。

### 3. 4 个委托声明（本类的"对外接口"）

```cpp
DECLARE_DYNAMIC_DELEGATE_OneParam(FTenkaichiGamePhaseDynamicDelegate, const UTenkaichiGamePhaseAbility*, Phase);
DECLARE_DELEGATE_OneParam(FTenkaichiGamePhaseDelegate, const UTenkaichiGamePhaseAbility* Phase);

DECLARE_DYNAMIC_DELEGATE_OneParam(FTenkaichiGamePhaseTagDynamicDelegate, const FGameplayTag&, PhaseTag);
DECLARE_DELEGATE_OneParam(FTenkaichiGamePhaseTagDelegate, const FGameplayTag& PhaseTag);
```

**两对，每对都是「动态版 + 原生版」**：

| 委托 | 参数 | 用途 |
|------|------|------|
| `FTenkaichiGamePhaseDynamicDelegate` / `FTenkaichiGamePhaseDelegate` | `const UTenkaichiGamePhaseAbility* Phase` | **阶段结束**回调（带阶段技能指针） |
| `FTenkaichiGamePhaseTagDynamicDelegate` / `FTenkaichiGamePhaseTagDelegate` | `const FGameplayTag& PhaseTag` | **阶段开始/结束**观察（带阶段标签） |

**两种宏的区别**（这是 UE 委托的核心知识点）：

| 宏 | 特点 | 谁能用 |
|----|------|--------|
| **`DECLARE_DELEGATE_OneParam`** | 原生委托，编译期绑定，**快** | 仅 C++ |
| **`DECLARE_DYNAMIC_DELEGATE_OneParam`** | 动态委托，走反射/序列化，**慢一点** | 蓝图 + C++ |

⚠️ **语法差异**（容易写错）：
- 原生版：`DECLARE_DELEGATE_OneParam(名字, 类型 参数名)` —— **类型和参数名分开**
- 动态版：`DECLARE_DYNAMIC_DELEGATE_OneParam(名字, 类型, 参数名)` —— **类型和参数名用逗号隔开**（因为动态委托要额外生成反射元数据）

看代码里：
- 原生行：`FTenkaichiGamePhaseDelegate, const UTenkaichiGamePhaseAbility* Phase` —— 一个逗号
- 动态行：`FTenkaichiGamePhaseDynamicDelegate, const UTenkaichiGamePhaseAbility*, Phase` —— 两个逗号

**Lyra 为什么两套都要**：`K2_` 开头的蓝图函数接收**动态**委托，内部转成**原生**委托，再调 C++ 版主函数。**一份逻辑，两套入口**。

### 4. EPhaseTagMatchType 枚举

```cpp
// 消息接收者的匹配规则
UENUM(BlueprintType)
enum class EPhaseTagMatchType : uint8
{
	// 精确匹配只接收通道完全相同的消息
	// （例如：注册 "A.B" 会匹配广播 A.B，但不匹配 A.B.C）
	ExactMatch,

	// 部分匹配会接收以同一通道为根的所有消息
	// （例如：注册 "A.B" 会匹配广播 A.B 以及 A.B.C）
	PartialMatch
};
```

- **`UENUM(BlueprintType)`**：让这个枚举**在蓝图里可用**（不加的话蓝图看不见）。
- **`enum class ... : uint8`**：C++11 强类型枚举 + 指定底层类型为 `uint8`（省内存，UE 枚举惯例）。
- **两个值的含义**（这是"观察者订阅"的匹配规则）：
  - **`ExactMatch`**：完全相等才算匹配。`A.B` 只匹配 `A.B`，**不**匹配 `A.B.C`。
  - **`PartialMatch`**：前缀匹配。`A.B` 匹配 `A.B` **和** `A.B.C`（因为 `A.B.C` 是 `A.B` 的后代）。
- **对应到阶段场景**：订阅 `Game.Playing` 用 `PartialMatch`，则 `Game.Playing.WarmUp`、`Game.Playing.SuddenDeath` 开始时**都会**通知你；用 `ExactMatch` 则只有 `Game.Playing` 本身开始时才通知。
- ⚠️ Lyra 原注释里写的是"消息接收者/通道"（message/channel），因为这个匹配概念借自消息总线（P01），照抄即可。

### 7. StartPhase（C++ 主接口）

```cpp

	void StartPhase(TSubclassOf<UTenkaichiGamePhaseAbility> PhaseAbility, FTenkaichiGamePhaseDelegate PhaseEndedCallback = FTenkaichiGamePhaseDelegate());
```

### 9. IsPhaseActive（唯一一个非 K2 的蓝图函数）

```cpp
	// 查询指定阶段当前是否处于活跃状态
	UFUNCTION(BlueprintCallable, BlueprintAuthorityOnly, BlueprintPure = false, meta = (AutoCreateRefTerm = "PhaseTag"))
	bool IsPhaseActive(const FGameplayTag& PhaseTag) const;
```

- **为什么它可以做 `UFUNCTION`**：参数里**没有原生委托**（只有 `FGameplayTag`），所以能被蓝图调用。
- **4 个说明符/meta**：
  - `BlueprintCallable` —— 蓝图可调用。
  - **`BlueprintAuthorityOnly`** —— ⚠️ **只在有权威（服务器）的一方生效**，客户端调用直接无效。因为阶段是服务器权威状态。
  - `BlueprintPure = false` —— 不是"纯函数"（有副作用/每次调用可能不同结果），蓝图里会画成带执行引脚的节点。
  - **`meta = (AutoCreateRefTerm = "PhaseTag")`** —— 蓝图里给 `PhaseTag` 参数**自动创建一个默认项**（不用手动连线造一个 Tag 变量，节点上直接能输入）。`UFUNCTION` 的 `meta` 是给编辑器看的额外指令。
- **`.cpp` 里**：遍历 `ActivePhaseMap`，用 `PhaseEntry.PhaseTag.MatchesTag(PhaseTag)` 判断。

### 10. protected 段：DoesSupportWorldType

```cpp
protected:
	// 判断本子系统支持哪些世界类型
	virtual bool DoesSupportWorldType(const EWorldType::Type WorldType) const override;
```

- **`UWorldSubsystem` 的虚函数**，决定"哪些类型的 World 要有这个子系统"。
- **`.cpp` 里**：`return WorldType == EWorldType::Game || WorldType == EWorldType::PIE;` —— **只有真正的游戏世界和 PIE（编辑器内运行）才有**；编辑器视口、菜单世界等**不创建**。
- **为什么**：阶段是游戏流程概念，编辑器里瞎逛的世界不需要。

- **模式完全一样**：接收**动态**委托 → `.cpp` 里用 `CreateWeakLambda` 转成**原生**委托 → 调 C++ 主函数。
- **`meta = (DisplayName = "...")`**：在蓝图右键菜单里**显示成这个友好的名字**（带空格），否则显示为 `K2 When Phase Ends` 这种丑名字。
- **`BlueprintAuthorityOnly`**：同样服务器专属。
- **`Category = "Game Phase"`**：蓝图右键菜单里归到 `Game Phase` 分类。

### 12. OnBeginPhase / OnEndPhase（内部，被 4-1 回调）

```cpp
	// 由阶段技能在激活时回调：处理新阶段开始与兄弟阶段的结束
	void OnBeginPhase(const UTenkaichiGamePhaseAbility* PhaseAbility, const FGameplayAbilitySpecHandle PhaseAbilityHandle);
	// 由阶段技能在结束时回调：处理阶段结束与观察者通知
	void OnEndPhase(const UTenkaichiGamePhaseAbility* PhaseAbility, const FGameplayAbilitySpecHandle PhaseAbilityHandle);
```

- **这两个是整套系统的核心动作**（`.cpp` 里最长、逻辑最重）。
- **谁调用**：P05.5-4-1 `UTenkaichiGamePhaseAbility` 的 `ActivateAbility` / `EndAbility` 里。
- **⚠️ 它们在 `protected` 段里，加上末尾的 `friend class UTenkaichiGamePhaseAbility;`** —— 实际上 4-1 通过**友元**访问。这是 Lyra 的设计意图：普通代码不该乱调这两个。
- **`OnBeginPhase` 做的**：读 `PhaseAbility->GetGamePhaseTag()` → 遍历 `ActivePhaseMap` → 对每个活跃阶段，如果 `!IncomingPhaseTag.MatchesTag(ActivePhaseTag)`（**不是祖先**）→ 用 `CancelAbilitiesByFunc` 结束它 → 把新阶段加入 `ActivePhaseMap` → 通知 `PhaseStartObservers`。
- **`OnEndPhase` 做的**：调结束回调 → 从 `ActivePhaseMap` 移除 → 通知 `PhaseEndObservers`。

### 13. private 段：两个内部结构体 + 三个成员 + 友元

```cpp
private:
	struct FTenkaichiGamePhaseEntry
	{
	public:
		FGameplayTag PhaseTag;
		FTenkaichiGamePhaseDelegate PhaseEndedCallback;
	};

	TMap<FGameplayAbilitySpecHandle, FTenkaichiGamePhaseEntry> ActivePhaseMap;

	struct FPhaseObserver
	{
	public:
		// 判断给定的阶段标签是否符合本观察者的匹配规则
		bool IsMatch(const FGameplayTag& ComparePhaseTag) const;
	
		FGameplayTag PhaseTag;
		EPhaseTagMatchType MatchType = EPhaseTagMatchType::ExactMatch;
		FTenkaichiGamePhaseTagDelegate PhaseCallback;

	TArray<FPhaseObserver> PhaseEndObservers;

```

- **`FTenkaichiGamePhaseEntry`** —— `ActivePhaseMap` 的值：一个阶段条目 = **阶段标签** + **结束回调**。
- **`ActivePhaseMap`** —— `TMap<FGameplayAbilitySpecHandle, FTenkaichiGamePhaseEntry>`：**当前所有活跃阶段**。⚠️ **用 `FGameplayAbilitySpecHandle` 当 key**——因为它唯一标识一次 GA 激活（同一个阶段技能可以被激活多次，句柄各不相同）。
- **`FPhaseObserver`** —— 一个观察者 = **观察的标签** + **匹配方式**（默认 `ExactMatch`）+ **回调**。方法 `IsMatch()` 在 `.cpp` 里用 `switch` 实现两种匹配。
- **`PhaseStartObservers` / `PhaseEndObservers`** —— 两个观察者数组（对应"开始"和"结束"两类订阅）。
- **`friend class UTenkaichiGamePhaseAbility;`** —— ⚠️ **关键设计**：把 private 成员开放给 4-1，让它能调 `OnBeginPhase`/`OnEndPhase`。没有这行，4-1 的 `.cpp` 编译不过。

## 五、几个要记住的点

1. **两套委托是标配**：`DECLARE_DELEGATE`（C++ 快）+ `DECLARE_DYNAMIC_DELEGATE`（蓝图可用），语法上**动态版多一个逗号**（类型, 参数名）。
2. **`EPhaseTagMatchType`**：`ExactMatch` 完全相等 / `PartialMatch` 前缀匹配——决定了订阅者能收到多少通知。
3. **`ActivePhaseMap` 用句柄当 key**：唯一标识一次 GA 激活。
4. **`friend class UTenkaichiGamePhaseAbility`**：private 的 `OnBeginPhase`/`OnEndPhase` 靠友元开放给 4-1。
5. **`K2_` 前缀 + `DisplayName` meta**：蓝图友好入口的标准做法。
6. **`BlueprintAuthorityOnly`**：三个蓝图函数全有——阶段是服务器权威。

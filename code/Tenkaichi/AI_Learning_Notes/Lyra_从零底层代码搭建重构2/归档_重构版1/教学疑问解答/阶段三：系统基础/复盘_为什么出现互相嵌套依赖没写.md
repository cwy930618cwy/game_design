# 复盘：为什么阶段三出现"互相嵌套、依赖没写"

> **性质**：教学规划复盘——记录阶段三（L3 系统基础）在推进中暴露的依赖规划问题，从根因到教训。
> **触发**：推进到线 A 第 3 项 `TenkaichiGameData` 时，发现它依赖线 B 的 `TenkaichiAssetManager`，而 `AssetManager` 又依赖阶段五的 GAS 类——"线 A 独立、线 B 等依赖"的划分失效，且依赖越挖越深。

---

## 一、直接现象（发生了什么）

按总 md 规划，阶段三分两条线：

```
线 A（声称"独立优先，现在就能做"）：
  1. GameplayTagStack     ✅ 已教完（真独立）
  2. TenkaichiGameEngine  ✅ 已教完（真独立）
  3. TenkaichiGameData    ← 卡住！实际依赖线 B 的 AssetManager
  4. GameSession ...
  5. ActorUtilities ...

线 B（声称"带依赖，等前置就位再补"）：
  8. TenkaichiAssetManager  ← GameData 依赖它
  9. TenkaichiGameInstance
```

**卡住的原因**：线 A 第 3 项 `GameData` 的 `.cpp` 里，`Get()` 是这样写的（Lyra 真实源码）：

```cpp
const ULyraGameData& ULyraGameData::Get()
{
	return ULyraAssetManager::Get().GetGameData();   // ← 依赖 AssetManager！
}
```

`GameData` **强依赖 `AssetManager`**，而 `AssetManager` 被归到了线 B。**线 A 项依赖线 B 项**——这就是"互相嵌套"。

---

## 二、根因（为什么会这样）

### 根因 1：规划时只看 `.h`，没看 `.cpp` 的完整依赖

总 md 第 85 行给 `TenkaichiGameData` 的判据是：

> "虽引用 GAS 但只是 `TSoftClassPtr` 声明，不影响编译"

**这条判据只看对了 `.h`**（`GameData.h` 里的字段确实是 `TSoftClassPtr<UGameplayEffect>`，不依赖未来类）。**但漏看了 `.cpp`**——`.cpp` 的 `Get()` 调用了 `AssetManager`。

> 教训：**判断一个类能不能独立编译，必须同时看 `.h` 和 `.cpp` 的完整依赖，不能只看 `.h`。**

### 根因 2：把"依赖的类没实现"误判成"不影响编译"

`TSoftClassPtr<UGameplayEffect>` 是"软引用"，只存路径不强制链接，所以 `.h` 不阻塞编译。但 `Get()` 是**运行时真的去调用 `AssetManager`**，这要求 `AssetManager` 类**存在且能链接**。软引用 ≠ 无依赖。

> 教训：**"软引用字段"和"硬调用依赖"是两回事。前者不阻塞编译，后者直接决定能不能编译/链接。**

### 根因 3：依赖只记录了一层，没往下追

总 md 记录了 `AssetManager → PawnData（阶段五）`，但**没继续追 PawnData 又依赖什么**。实际查证：

```
GameData → AssetManager → GameplayCueManager（阶段五 GAS）
                        → PawnData（阶段五）→ AbilitySet → AbilitySystemComponent
                                           → TagRelationshipMapping
                                           → InputConfig
                                           → CameraMode → CameraComponent
```

`AbilitySet` 又依赖 `GameplayAbility`、`AttributeSet`、`GameplayEffect`…… 网是**无底的**，一路挖到整个 GAS + 角色体系。

> 教训：**依赖要追到底，不能只记第一层。** 只记一层会严重低估牵连面。

---

## 三、连锁影响（不解决会怎样）

1. **线 A/B 划分失效**：线 A 第 3 项就断了，整条"独立优先"的线跑不通。
2. **范围失控**：要还原 `GameData`，被迫连带还原 `AssetManager` → GAS 核心（`AbilitySystemComponent`、`GameplayAbility`、`GameplayCueManager`、`CameraMode`、`InputConfig`、`AbilitySet`……），**基本等于把阶段五整个提前**。
3. **阶段节奏打乱**：原"阶段三系统 → 阶段五 GAS"的顺序被破坏，变成"先 GAS 后系统"。

---

## 四、可选解法（当时摆给用户的）

| 方案 | 做法 | 代价 |
|------|------|------|
| **A（骨架隔离）** | `AssetManager` 先只实现不依赖 GAS 的部分（`Get()`/`GetGameData()` 等），GAS 类先建占位 `.h`，阶段五补实 | 阶段五要回头补，稍绕 |
| **B（整体提前）** | 按真实依赖链，把 GAS 相关类全部提前教 | 教学顺序大改，基本进入"先 GAS 后系统" |

**用户已选定方案 B**：按真实依赖链自下而上，先教最底层的类。

---

## 五、今后怎么避免（通用教训，不只阶段三）

1. **教任何类前，先读它的 `.h` + `.cpp` 完整内容**，把所有 `#include` 和运行时调用的外部类都列出来。
2. **依赖要追到底**：A 依赖 B，就继续查 B 依赖什么，直到全是"引擎类/插件/已教内容"。
3. **软引用字段 ≠ 无依赖**：`.h` 里 `TSoftClassPtr` 不阻塞编译，但 `.cpp` 里**硬调用**的外部类必须存在。
4. **别急着定"线 A/B 划分"**：先靠查证把每个类的真实依赖树画出来，再按依赖分层，而不是按"我以为它独立"分组。
5. **发现一个依赖断点，就回溯检查总 md 里同批所有类**——很可能不止一个判据是错的。

---

## 六、一句话总结

> **阶段三出问题的根子是：规划时只看 `.h` 的软引用、没看 `.cpp` 的硬调用，且依赖只记一层不追到底，导致把"真依赖"当成了"能独立编译"，线 A/B 划分失真，最后范围失控到要整体提前 GAS。**

---

> 备注：复盘后，阶段三剩余的教学顺序以**方案 B 的真实依赖链**为准（自下而上教 GAS 相关类），不再沿用原"线 A/B"划分。具体顺序见后续教学步骤。

## 一、为什么要有 TeamCreationComponent

P07.1~P07.10 把队伍系统的**零件**全做齐了：

| 类 | 角色 |
|----|------|
| P07.1 接口 | 让 Actor 能回答"你几队" |
| P07.2 外观 | 队伍长什么样（颜色/名字/贴图） |
| P07.3/4/5 信息实体 | `TeamPublicInfo` / `TeamPrivateInfo` 两个 Actor |
| P07.6 子系统 | 查询 + 广播的枢纽 |
| P07.7 工具库 | 给蓝图的电话簿 |
| P07.8 作弊 | 控制台遥控器 |
| P07.9/10 异步节点 | 给蓝图的订阅推送 |

**但没人负责"开局时把这些零件组装起来"。**

> 具体缺三件事：
> 1. **没有创建队伍实体** —— `TeamPublicInfo` / `TeamPrivateInfo` 这两个 Actor **谁去 Spawn**？
> 2. **没有给玩家分队** —— 玩家进游戏，谁来决定"你去 1 队还是 2 队"？
> 3. **没有配置入口** —— "这局要几个队、每个队长什么样" 在哪配？

### 问题场景

你开一局 5v5：

- 地图加载完 → 需要**凭空造出 2 个队伍实体**（0 队蓝、1 队红），每个队都 Spawn 一对 `PublicInfo`/`PrivateInfo` Actor
- 玩家 A 进来了 → 要分到人少的那队
- 玩家 B 中途加入 → 也要分，且**不能把某队撑爆**
- 观众（Spectator）进来了 → **不该分到任何队**（`NoTeam`）

### Lyra 的解法：挂在 GameState 上的"开局装配工"

`UTenkaichiTeamCreationComponent` 是一个 **`UGameStateComponent`**（引擎 ModularGameplay 插件），
**挂在 GameState 上**，靠**蓝图子类配置队伍表**，在 **Experience 加载完**时统一开工。

```
配置层（蓝图子类）：TeamsToCreate = { 0 → 蓝队外观, 1 → 红队外观 }
                          │
                          ▼
执行层（本组件）：BeginPlay 等 Experience 加载完
                     ├─ ServerCreateTeams()          ← 按配置 Spawn 队伍实体
                     └─ ServerAssignPlayersToTeams() ← 给已在线的玩家分队 + 监听新玩家
```

> 类比：前面 10 个类是**零件**（发动机、轮胎、方向盘），
> 本组件是**总装车间**——把零件装成整车，还要**给每个乘客安排座位**（分队）。

### 它为什么是 P07 最重的类

它**横跨了 P07 全部 + P12 Player + P13 GameModes** 三层，是 P07 的**收口类**。

## 四、关键理解点

### 概念 1：`UGameStateComponent` —— 为什么挂在 GameState 上（引擎 ① 只讲不拆）

| 问题 | 答案 |
|------|------|
| **它是什么？** | 引擎 **ModularGameplay 插件**提供的组件基类（`GameStateComponent.h:16`），继承 `UGameFrameworkComponent` |
| **挂在哪？** | 作为 `AGameStateBase` 的一个组件，随 GameState 生命周期 |
| **为什么选它？** | 队伍是**全局状态**（不属于任何单个玩家/Actor）→ 天然该放 GameState；且**服务器权威** |
| **提供什么？** | `GetGameStateChecked<T>()` 模板（`:33`），安全拿到宿主 GameState |

> 教学分级 **① 只讲不拆**：引擎自带，我们不用新建，懂它干嘛 + 何时被调用即可。
> ⚠️ 别和 Lyra 的 **`ModularGameplayActors`** 插件搞混——那是 Lyra 自己的插件（② 要还原）。

### 概念 2：`TeamsToCreate` —— 蓝图配置的队伍表（本类的"输入"）

```cpp
UPROPERTY(EditDefaultsOnly, Category=Teams)
TMap<uint8, TObjectPtr<UTenkaichiTeamDisplayAsset>> TeamsToCreate;
```

| 元素 | 说明 |
|------|------|
| `TMap<uint8, ...>` | **队号 → 外观资产** 的映射。键是 `uint8`（对应引擎 `FGenericTeamId` 的内部类型） |
| `EditDefaultsOnly` | 只能在**蓝图默认值**里配（不能运行时改） |
| `TObjectPtr<...>` | UE5 的软性对象指针包装（等价于裸指针，但支持 UHT 与 GC 追踪） |
| **外观可为空** | Lyra 注释明确写了 "the display asset can be left unset if desired" |

**这就是"这局要几个队"的配置入口**：

```
蓝图子类 B_TeamCreation_5v5：
  TeamsToCreate = { 0 → DA_BlueTeam, 1 → DA_RedTeam }

蓝图子类 B_TeamCreation_FFA：
  TeamsToCreate = { 0 → DA_P0, 1 → DA_P1, ..., 7 → DA_P7 }
```

> 💡 **这就是 `UCLASS(Blueprintable)` 的原因** —— 只有允许蓝图继承，才能做这些配置子类。

### 概念 3：分队算法 `GetLeastPopulatedTeamID`（本类最"有内容"的函数）

```
① 没配置任何队伍（NumTeams == 0）→ 直接返回 INDEX_NONE
② 建一张计数表 TeamMemberCounts：所有配置队伍 → 0
③ 遍历 GameState->PlayerArray：
     不是 TenkaichiPlayerState  → 跳过
     队号 == INDEX_NONE（未分配）→ 跳过
     IsInactive()（已断线）      → 跳过
     否则 TeamMemberCounts[队号] += 1
④ 遍历计数表选最优：
     人数更少        → 换成它
     人数相同        → 队号更小的胜出（平局规则）
⑤ 返回最优队号
```

| 细节 | 为什么 |
|------|--------|
| 跳过 `INDEX_NONE` | 未分配/观众的玩家**不该计入任何队** |
| 跳过 `IsInactive()` | 断线玩家还留在 `PlayerArray` 里，但**不该占位**（Lyra 注释："do not count unassigned or disconnected players"） |
| 平局取小队号 | 保证**确定性**——相同局面永远得到相同结果，避免抖动 |
| `BestPlayerCount` 初值 `TNumericLimits<uint32>::Max()` | 保证第一个队伍一定会被选中 |

> 💡 **类比**：餐厅领位员看哪桌人少就安排哪桌；
> 两桌一样少就**固定安排桌号小的那桌**（避免来回犹豫）。断线客人的座位不算数。

### 概念 4：观众剥队（`ServerChooseTeamForPlayer`）

```cpp
if (PS->IsOnlyASpectator())
{
    PS->SetGenericTeamId(FGenericTeamId::NoTeam);   // 观众：不给队
}
else
{
    const FGenericTeamId TeamID = IntegerToGenericTeamId(GetLeastPopulatedTeamID());
    PS->SetGenericTeamId(TeamID);                    // 正常玩家：去人最少的队
}
```

> 📌 `IsOnlyASpectator()` 是**引擎 `APlayerState` 自带**（`PlayerState.h:362`），工程无需补。
> `IntegerToGenericTeamId()` 来自 **P07.1** `TenkaichiTeamAgentInterface.h`（`GenericTeamIdToInteger` 的反向）。

### 概念 5：`ServerCreateTeam` —— 一次 Spawn 两个 Actor

```cpp
ALyraTeamPublicInfo*  NewTeamPublicInfo  = World->SpawnActor<ALyraTeamPublicInfo>(PublicTeamInfoClass, SpawnInfo);
NewTeamPublicInfo->SetTeamId(TeamId);
NewTeamPublicInfo->SetTeamDisplayAsset(DisplayAsset);       // ← 只有 Public 有这个

ALyraTeamPrivateInfo* NewTeamPrivateInfo = World->SpawnActor<ALyraTeamPrivateInfo>(PrivateTeamInfoClass, SpawnInfo);
NewTeamPrivateInfo->SetTeamId(TeamId);
```

**每个队伍号都 Spawn 一对 Actor**（Public 全客户端可见 / Private 只服务器可见），然后：

- 两者都 `SetTeamId(TeamId)` → 它们会自己去 `TeamSubsystem` 注册（P07.3 `RegisterWithTeamSubsystem`）
- 只有 Public `SetTeamDisplayAsset(DisplayAsset)` → **外观是公开信息**

> ⚠️ **`SetTeamDisplayAsset` 是 private 的**，靠 P07.4 `.h:21` 的 `friend UTenkaichiTeamCreationComponent;` 才能调。
> 这就是**友元**在 Lyra 里的实际用途——**对外只读、对装配工可写**。

> 📌 `SpawnInfo.SpawnCollisionHandlingOverride = AlwaysSpawn` ——
> 队伍信息 Actor 没有碰撞体，但**必须强制生成**，否则重叠检查可能让它 Spawn 失败。

### 概念 6：`#if WITH_SERVER_CODE` —— 为什么要条件编译

```cpp
#if WITH_SERVER_CODE
protected:
	virtual void ServerCreateTeams();
	...
#endif
```

| 宏 | 含义 |
|----|------|
| `WITH_SERVER_CODE` | 引擎宏：**当前构建是否包含服务器逻辑**（打包的纯客户端为 `0`） |
| 为什么用它 | 建队/分队是**服务器专属**逻辑，纯客户端不需要 → **减小客户端包体 + 防止作弊** |

> 💡 对比 `WITH_EDITOR`（`IsDataValid` 用）：那个是"只在编辑器里编译"。
> 两个宏是 Lyra 条件编译的**标准两件套**。

### 概念 7：三段时间线（本类的运行时流程）

```
[服务器启动] GameState 创建 → 本组件 BeginPlay
      │
      ├─ 找 ExperienceManagerComponent（P13）
      └─ 注册 CallOrRegister_OnExperienceLoaded_HighPriority
             │  （如果 Experience 已加载 → 立即回调；否则等加载完）
             ▼
[Experience 加载完] OnExperienceLoaded
      │
      ├─ HasAuthority() ? 
      ├─ ServerCreateTeams()          → 遍历 TeamsToCreate → ServerCreateTeam(T, Asset)
      │                                  → Spawn PublicInfo + PrivateInfo 各一个
      └─ ServerAssignPlayersToTeams() → 遍历 PlayerArray 给已有玩家分队
                                       → 绑 GameMode->OnGameModePlayerInitialized
```

## 〇、先给一个类比：把 Teams 想成「一场球赛的后勤系统」

| 球赛 | Teams 系统 | 对应类 |
|------|-----------|--------|
| 🪪 **球员证的"所属队"栏** | 队伍归属标记（你几队的） | `ITenkaichiTeamAgentInterface` |
| 🎨 **队服配色方案**（红队红衣、蓝队蓝衣） | 队伍外观资产（颜色/图标/名字） | `UTenkaichiTeamDisplayAsset` |
| 📋 **球队登记表**（队号 + 统计） | 队伍信息基类（队号 + 标签栈） | `ATenkaichiTeamInfoBase` |
| 📢 **对外公示牌**（谁都能看） | 公开队伍信息（含队服配色） | `ATenkaichiTeamPublicInfo` |
| 🔒 **更衣室内部白板**（只有队内看） | 私有队伍信息（只服务器可见） | `ATenkaichiTeamPrivateInfo` |
| 🗄️ **赛事组委会**（查谁哪队、能不能互打） | 队伍子系统（唯一权威数据源） | `UTenkaichiTeamSubsystem` |
| 📞 **组委会热线**（蓝图/客户端也能查） | 队伍工具库（静态函数） | `UTenkaichiTeamStatics` |
| 🎮 **场边教练席**（调试时换队） | 队伍作弊指令 | `UTenkaichiTeamCheats` |
| 👀 **记分牌观察员**（换队了告诉我） | 异步监听：队伍变化 | `UAsyncAction_ObserveTeam` |
| 🌈 **队服观察员**（配色变了告诉我） | 异步监听：队伍颜色变化 | `UAsyncAction_ObserveTeamColors` |
| 🎪 **开场总装工**（建队 + 分队） | 队伍创建组件 | `UTenkaichiTeamCreationComponent` |

> **一句话**：Lyra 用「**接口标记身份 + 双信息 Actor 存数据 + 子系统做唯一权威 + 委托广播变更**」
> 搭了一套**可复制、可扩展、UI 自动刷新**的阵营系统，回答"谁跟谁一伙"。

## 一、核心概念图：队伍变更的广播链（⭐ 理解了它就理解了 P07）

```
      某人换了队（SetGenericTeamId）
                  │
                  ▼
   ITenkaichiTeamAgentInterface::ConditionalBroadcastTeamChanged
                  │  （旧队 ≠ 新队 才广播）
                  ▼
     FOnTenkaichiTeamIndexChangedDelegate.Broadcast
         （谁、从旧队、到新队）
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
  P07.9 收到            P07.10 收到
   （只关心队号）        （关心队号 + 配色）
        │                   │
        │                   ▼
        │         BroadcastChange（三段式搬家）
        │           ① 解绑旧队的外观监听
        │           ② 广播新队号 + 新配色
        │           ③ 绑定新队的外观监听
        │                   │
        │                   ▼
        │         OnTeamChanged（蓝图引脚）→ UI 刷新颜色
        ▼
  OnTeamChanged（蓝图引脚）→ UI 刷新队伍标识
```

**为什么要"接口 + 委托"而不是"直接存个 int"？**
因为游戏里**很多东西**都可能有队伍，而且**换队后所有相关 UI 都要自动刷新**：

- 角色 Pawn 有队伍
- PlayerState 有队伍
- 队伍信息 Actor 本身也有队伍

如果是"各存各的 int"，换队时就得**手动去通知每一个 UI**；
用**接口标记 + 委托广播**就是：谁关心谁来听，**发布者完全不认识订阅者**。

## 五、常见混淆点（你晕大概晕在这）

| 容易混 | 区别 |
|--------|------|
| **`TeamAgentInterface` vs `TeamSubsystem`** | 接口是**"我可能有队伍"的标记**（挂在对象上）；子系统是**"谁哪队"的唯一权威**（全球一个） |
| **`TeamInfoBase` vs `TeamSubsystem`** | `TeamInfo` 是**一个 Actor**（代表一支队伍，会复制）；`Subsystem` 是**一本索引**（管理所有队伍，不复制） |
| **`PublicInfo` vs `PrivateInfo`** | 同一个队号**挂两个 Actor**：Public 全客户端可见（含配色），Private 只服务器可见。**这是"信息分区"的标准做法** |
| **`TeamSubsystem` vs `TeamStatics`** | `Subsystem` 是**实例**（要 `GetWorld()->GetSubsystem<>()`）；`Statics` 是**静态函数**（蓝图里直接调，内部再去取 Subsystem） |
| **`ObserveTeam` vs `ObserveTeamColors`** | 前者只报**队号**（2 参委托）；后者多报**配色**（3 参委托），而且**配色来源有两个**：换队 + 配色被改 → 所以要"解绑旧队→广播→绑定新队"三段搬家 |
| **`ObserveTeam` 为什么监听两路** | 一路是**对象换队**（`OnWatchedAgentChangedTeam`），一路是**队伍配色被改**（`OnDisplayAssetChanged`）。只听一路会漏 |
| **`TeamCreationComponent` 为什么是 P07 最后一个** | 它是**总装工**——前面的接口/资产/信息/子系统/工具全是它的"零件" |
| **两个 `AsyncAction` 为什么文件名没 `Tenkaichi` 前缀** | Lyra 原文就没有 `Lyra` 前缀 → 按铁律 24 机械替换，**保持原样**（对比其余 9 个类都有前缀） |
| **`PrivateInfo` 为什么是空壳** | Lyra 留的 TODO：将来用 **Replication Graph** 真正做成"只有队内可见"，现在先占位 |
| **观众（`IsOnlyASpectator`）为什么要显式设 `NoTeam`** | 玩家可能**先当队员再切观众**，必须显式清掉旧队伍关联，否则 UI 还显示他在旧队 |

## 六、记忆口诀（5 句）

1. **接口标记身份，子系统掌权威** —— 前者挂在对象上，后者全球一个。
2. **一队两个 Actor：Public 给外人看，Private 给自己看** —— 信息分区标准做法。
3. **换队靠委托广播，谁关心谁来听** —— 发布者不认识订阅者。
4. **Statics 是蓝图热线，Cheats 是小类钥匙** —— 前者方便查，后者能卡住整条链。
5. **P07 只有 P07.11 挂 5 处** —— 全指向 P13，`Teams\` 目录其余 20 文件零挂起。

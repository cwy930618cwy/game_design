把类总 md 里"监听队伍**颜色**（并直接给出外观资产）"落成真实的 `.h` 文件。

本文件 **55 行 / 1 个委托 + 1 个类（8 个成员）**。和 P07.9 的 `.h` 很像，但有 **6 处实质差异**：

| # | 差异点 | P07.9 | **P07.10** |
|---|--------|-------|-----------|

## 三、完整代码（注释已中文化）

你新建文件：`Source/TenkaichiGame/Teams/AsyncAction_ObserveTeamColors.h`

```cpp
// Copyright Epic Games, Inc. All Rights Reserved.

#pragma once

#include "Engine/CancellableAsyncAction.h"
#include "UObject/WeakInterfacePtr.h"

#include "AsyncAction_ObserveTeamColors.generated.h"

class ITenkaichiTeamAgentInterface;
class UTenkaichiTeamDisplayAsset;
struct FFrame;

DECLARE_DYNAMIC_MULTICAST_DELEGATE_ThreeParams(FTeamColorObservedAsyncDelegate, bool, bTeamSet, int32, TeamId, const UTenkaichiTeamDisplayAsset*, DisplayAsset);

/**
 * 监听指定对象上的队伍颜色（外观资产）变化
 */
UCLASS()
class UAsyncAction_ObserveTeamColors : public UCancellableAsyncAction
{
	GENERATED_UCLASS_BODY()

public:
	// 监听指定队伍代理（TeamAgent）上的队伍变化
	//  - 它会立刻触发一次，给出当前的队伍归属
	//  - 对于任何可能属于某个队伍的对象（实现了 ITenkaichiTeamAgentInterface 的），
	//    它之后还会持续监听队伍归属的变化
	UFUNCTION(BlueprintCallable, meta=(BlueprintInternalUseOnly="true", Keywords="Watch"))
	static UAsyncAction_ObserveTeamColors* ObserveTeamColors(UObject* TeamAgent);

	//~UBlueprintAsyncActionBase 接口开始
	// 节点被激活时调用：取当前队伍与外观资产、订阅变更委托，并立刻广播一次
	virtual void Activate() override;
	// 节点即将销毁或被取消时调用：解除"换队"委托订阅，避免对象销毁后仍被回调
	virtual void SetReadyToDestroy() override;
	//~UBlueprintAsyncActionBase 接口结束

public:
	// 当队伍被设置或改变时调用
	UPROPERTY(BlueprintAssignable)
	FTeamColorObservedAsyncDelegate OnTeamChanged;

private:
	// 统一广播出口：先解绑旧队伍的外观监听，再广播当前队伍与外观，最后绑定新队伍的外观监听
	void BroadcastChange(int32 NewTeam, const UTenkaichiTeamDisplayAsset* DisplayAsset);

	// 被监听对象换队时的回调：查出新队伍的外观资产后统一广播
	UFUNCTION()
	void OnWatchedAgentChangedTeam(UObject* TeamAgent, int32 OldTeam, int32 NewTeam);

	// 当前队伍的外观资产被修改时的回调：用上次广播的队伍号再播一次
	UFUNCTION()
	void OnDisplayAssetChanged(const UTenkaichiTeamDisplayAsset* DisplayAsset);

	// 被监听对象的接口视图，用于调用接口方法和绑定换队委托
	TWeakInterfacePtr<ITenkaichiTeamAgentInterface> TeamInterfacePtr;
	// 同一个对象的裸 UObject 弱引用，用于需要 WorldContextObject 的场合
	TWeakObjectPtr<UObject> TeamInterfaceObj;

	// 上次广播的队伍号，用于判断是否需要把外观监听从旧队搬到新队
	int32 LastBroadcastTeamId = INDEX_NONE;
};
```

## 四、逐段讲解

### 4.1 文件头 + 两个 include（第 1~8 行）

```cpp
#pragma once

#include "Engine/CancellableAsyncAction.h"
#include "UObject/WeakInterfacePtr.h"

#include "AsyncAction_ObserveTeamColors.generated.h"
```

| 行 | 干什么 |
|----|--------|
| `#pragma once` | 防重复包含（所有 `.h` 标配） |
| `Engine/CancellableAsyncAction.h` | ★ **基类来源**，提供 `UCancellableAsyncAction`。引擎文件，教学分级 ① 只讲不拆 |
| `UObject/WeakInterfacePtr.h` | 提供 `TWeakInterfacePtr<T>`（第 51 行成员）。**顺带**间接提供了 `TWeakObjectPtr`（第 52 行成员） |
| `AsyncAction_ObserveTeamColors.generated.h` | UHT 生成头，**文件名必须与本文件同名** |

> 📌 **`generated.h` 必须放最后**：UHT 要求它是最后一个 include，否则报 `expected an include at the end`。

> 💡 **`TWeakObjectPtr` 是从哪来的？**
> `WeakInterfacePtr.h` 内部 include 了 `UObject/WeakObjectPtr.h`（引擎源码 `WeakInterfacePtr.h:7`），
> 所以本文件**没有显式 include `WeakObjectPtr.h`** 也能用 `TWeakObjectPtr<UObject>`。
> **照抄 Lyra，别"顺手补一个 include"**（铁律 16）。

**和 P07.9 的对比**（为什么这里少一个 include）：

|---------|-------|--------|
| `Engine/CancellableAsyncAction.h` | ✅ | ✅ |
| `UObject/ScriptInterface.h` | ✅（形参是 `TScriptInterface`） | ❌ **没有**（无 `TScriptInterface` 形参） |
| `UObject/WeakInterfacePtr.h` | ✅ | ✅ |

### 4.2 三个前置声明（第 10~12 行）

```cpp
class ITenkaichiTeamAgentInterface;
class UTenkaichiTeamDisplayAsset;
struct FFrame;
```

| 声明 | 为什么需要 | 什么时候才真正 include |
|------|-----------|---------------------|
| `class ITenkaichiTeamAgentInterface;` | ⚠️ **`I` 开头**（接口实现类）。只在 `TWeakInterfacePtr<T>` 模板参数里用 → 前置声明够 | `.cpp` 里（要调 `GetTeamChangedDelegateChecked()`） |
| `class UTenkaichiTeamDisplayAsset;` | 只出现在**指针**位置（委托参数、函数形参）→ 前置声明够 | `.cpp` 里（要 include `TenkaichiTeamStatics.h` 间接带入） |
| `struct FFrame;` | UHT 生成的蓝图 thunk（`execXxx`）参数里用到，固定套路 | 不需要 |

> 💡 **这是 C++ 的标准做法**：头文件尽量前置声明，实现文件才 include。
> 好处是本 `.h` **零项目内依赖** → 编译快、不易被别的改动波及。

### 4.3 委托声明（第 14 行）—— 本文件第一处关键差异

```cpp
DECLARE_DYNAMIC_MULTICAST_DELEGATE_ThreeParams(FTeamColorObservedAsyncDelegate, bool, bTeamSet, int32, TeamId, const UTenkaichiTeamDisplayAsset*, DisplayAsset);
```

| 元素 | 说明 |
|------|------|
| `DECLARE_DYNAMIC_MULTICAST_DELEGATE_ThreeParams` | UHT 宏：声明**蓝图可绑定的多播委托**，带 3 个参数（P07.9 是 `TwoParams`） |
| `FTeamColorObservedAsyncDelegate` | 委托类型名（**无 `Lyra` 前缀，保留原样**） |
| `bool, bTeamSet` | "有没有队伍"：有队 `true`，无队 `false` |
| `int32, TeamId` | 队伍号，无队时 `INDEX_NONE`（`-1`） |
| `const UTenkaichiTeamDisplayAsset*, DisplayAsset` | ★ **本类新增**：直接把队伍外观资产送出去 |

> 📌 **为什么第 3 个参数要带 `const`？**
> 这是 Lyra 原样。`DYNAMIC` 委托支持 UObject 派生类的**指针**（不能是引用/值），
> `const` 表示"广播方承诺不修改它"，蓝图侧拿到是只读的。

> 📌 **为什么三个参数要一起给？**
> 蓝图拿到 `DisplayAsset` 就能直接 `GetTeamColorWithFallback` 取颜色，
> **不用再调一次 `TeamStatics::GetTeamDisplayAsset`**。
> 而 `bTeamSet` 单独存在，是因为"没队伍"是合法状态——
> 只靠 `TeamId = -1` 蓝图还得额外判断，Lyra 直接把"有没有"做成 `bool`，一眼看懂。

**和 P07.9 的委托签名对照**：

```
P07.9：  FTeamObservedAsyncDelegate       (bool bTeamSet, int32 TeamId)
P07.10： FTeamColorObservedAsyncDelegate  (bool bTeamSet, int32 TeamId, const UTenkaichiTeamDisplayAsset* DisplayAsset)
```

### 4.8 私有区：`BroadcastChange` —— 本文件核心新增（第 42~43 行）

```cpp
private:
	// 统一广播出口：先解绑旧队伍的外观监听，再广播当前队伍与外观，最后绑定新队伍的外观监听
	void BroadcastChange(int32 NewTeam, const UTenkaichiTeamDisplayAsset* DisplayAsset);
```

| 点 | 说明 |
|----|------|
| **不是 `UFUNCTION`** | 纯 C++ 内部方法，蓝图看不见 |
| 为什么需要它？ | 本类有 **3 个地方**要广播（首播 / 换队 / 外观变），**两路监听要搬家** → 抽一个统一出口 |
| 参数 `NewTeam` | 要广播的队伍号 |
| 参数 `DisplayAsset` | 要广播的外观资产（**调用方负责查好**） |

> 📌 **这是 P07.9 完全没有的方法**。P07.9 只有一次 `Broadcast` 写在 `Activate()` 里、一次写在回调里，
> 两处各自一行、**没有"搬家"逻辑** → 不需要抽函数。
> 本类因为**要解绑旧队、绑定新队**，逻辑有 3 段，抽出来才不会重复 —— 这是真实的工程判断。

**它会被谁调用（3 个入口）**：

```
Activate()                  → BroadcastChange(当前队, 当前外观)      ← 首播
OnWatchedAgentChangedTeam() → BroadcastChange(新队, 新队的外观)      ← 换队
OnDisplayAssetChanged()     → BroadcastChange(LastBroadcastTeamId, 新外观) ← 外观变
```

### 4.9 两个回调（第 45~49 行）

```cpp
	// 被监听对象换队时的回调：查出新队伍的外观资产后统一广播
	UFUNCTION()
	void OnWatchedAgentChangedTeam(UObject* TeamAgent, int32 OldTeam, int32 NewTeam);

	// 当前队伍的外观资产被修改时的回调：用上次广播的队伍号再播一次
	UFUNCTION()
	void OnDisplayAssetChanged(const UTenkaichiTeamDisplayAsset* DisplayAsset);
```

| 回调 | 绑在谁的委托上 | 签名要匹配谁 |
|------|--------------|-------------|
| `OnWatchedAgentChangedTeam` | **被监听对象**的 `GetTeamChangedDelegateChecked()`（P07.1） | `FOnTenkaichiTeamIndexChangedDelegate` = `(UObject*, int32, int32)` |
| `OnDisplayAssetChanged` | **TeamSubsystem** 的 `GetTeamDisplayAssetChangedDelegate(TeamId)`（P07.6 `.h:148`） | `FOnTenkaichiTeamDisplayAssetChangedDelegate` = `(const UTenkaichiTeamDisplayAsset*)` |

> ⚠️ **`UFUNCTION()` 空标记但必须有**——`AddDynamic` 绑定的函数必须是 `UFUNCTION`，
> 否则 UHT 不生成反射信息 → **运行时绑定失败、回调永不触发**（编译不报错，最难查）。

> ⚠️ **签名必须严格匹配**：`AddDynamic` 是运行时按名字绑定的，
> 参数个数/类型对不上会在运行时报 "Unable to bind delegate"，回调永远不触发。

> 💡 **为什么两个回调都只做一件事然后转交 `BroadcastChange`？**
> 因为它们**只是不同来源的事件入口**，真正的"广播 + 搬监听"逻辑是同一套。
> 这是标准的 **"入口分流 + 统一处理"** 结构。

### 4.10 三个私有字段（第 51~54 行）—— 本文件第二处关键差异

```cpp
	// 被监听对象的接口视图，用于调用接口方法和绑定换队委托
	TWeakInterfacePtr<ITenkaichiTeamAgentInterface> TeamInterfacePtr;
	// 同一个对象的裸 UObject 弱引用，用于需要 WorldContextObject 的场合
	TWeakObjectPtr<UObject> TeamInterfaceObj;

	// 上次广播的队伍号，用于判断是否需要把外观监听从旧队搬到新队
	int32 LastBroadcastTeamId = INDEX_NONE;
```

#### 为什么存**两个**弱引用（最反直觉的地方 ★）

**同一个对象，存了两份。** 因为用途不同：

| 成员 | 拿来干什么 | 为什么必须单独存 |
|------|-----------|----------------|
| `TeamInterfacePtr` | 调 `GetGenericTeamId()`、绑"换队"委托 | 需要**接口类型**才能调接口方法 |
| `TeamInterfaceObj` | 传给 `GEngine->GetWorldFromContextObject(...)`、`UTenkaichiTeamStatics::GetTeamDisplayAsset(WorldContextObject, ...)` | 那些函数收的是 **`const UObject*`**，不是接口 |

> 💡 你可能想问：**`TeamInterfacePtr.Get()` 拿到的不就是对象吗？**
> 不完全——`TWeakInterfacePtr::Get()` 返回的是**接口指针 `ITenkaichiTeamAgentInterface*`**，
> 它虽然能 `Cast` 回 `UObject`，但 Lyra 选择**再存一份裸的**，省掉每次转换。
> **照抄 Lyra，别"顺手优化掉一个"**。

#### 为什么都是**弱**引用

这个 AsyncAction 通过 `RegisterWithGameInstance` 挂在 GameInstance 上，
**可能比被监听的 Actor 活得久**。强引用会把 Actor 钉在内存里 → 泄漏。
弱引用则 Actor 销毁后 `Get()` 自动返 `nullptr`，**访问安全**。

#### `LastBroadcastTeamId`（P07.9 没有的状态）

```cpp
int32 LastBroadcastTeamId = INDEX_NONE;
```

**初值 `INDEX_NONE`（`-1`）= "还没广播过任何队伍"**。它有两个作用：

| 作用 | 说明 |
|------|------|
| ① 判断"队伍变没变" | `bTeamChanged = (LastBroadcastTeamId != NewTeam)` → 决定要不要搬监听 |
| ② 记住"当前绑在哪个队上" | 换队时要用**旧值**去 `RemoveAll`，新值去 `AddDynamic` |

> 💡 **为什么必须记住？** 因为 `TeamSubsystem` 的委托是**按队伍 ID 分桶**的
> （`TeamMap.FindOrAdd(TeamId).OnTeamDisplayAssetChanged`，见 `TenkaichiTeamSubsystem.cpp:445`）。
> 你监听的是"1 队的外观"，对象换到 2 队了 → **必须退订 1 队、改订 2 队**，
> 否则还在收 1 队的通知（**错的**），2 队改版反而收不到（**漏的**）。

# P07.8 UTenkaichiTeamCheats —— `.h` 声明层

## 一、本文件要解决什么

把类总 md 里"队伍系统的遥控器"落成真实的 `.h` 文件。`TenkaichiTeamCheats.h` 定义 `UTenkaichiTeamCheats` 类，继承**引擎**的 `UCheatManagerExtension`。

**这个 `.h` 只声明 3 个函数**，全部是 `virtual` + `UFUNCTION(Exec)`：

| 函数 | 控制台怎么敲 | 作用 |
|------|-------------|------|
| `CycleTeam()` | `CycleTeam` | 换到下一队（末尾绕回第一队） |
| `SetTeam(int32 TeamID)` | `SetTeam 3` | 换到指定队 |
| `ListTeams()` | `ListTeams` | 打印所有队伍 ID |

**它和 P07 其他类的三点不同（重点）**：

| 对比项 | P07.6 TeamSubsystem | P07.1 TeamAgentInterface | **P07.8 TeamCheats** |
|--------|--------------------|-------------------------|---------------------|
| 基类 | `UWorldSubsystem` | `UGenericTeamAgentInterface`（接口） | **`UCheatManagerExtension`（引擎）** |
| UCLASS 标记 | `UCLASS(MinimalAPI)` | `UINTERFACE(MinimalAPI)` | **`UCLASS()`（无 MinimalAPI）** |
| 导出宏 | 每个方法带 `UE_API` | 带 `UE_API` | **无 `UE_API`，无 `#define UE_API`** |
| 函数数量 | 21 个 | 3 个 | **3 个（全 `virtual`）** |

> **为什么没有 `UE_API` / `#define UE_API`？**
> 因为 `UCLASS()` 没标 `MinimalAPI` → 整个类的符号**默认全导出**，不需要逐个方法加导出宏。
> 对比 P07.6 `TeamSubsystem` 标了 `MinimalAPI`（只导出被 `UE_API` 标记的方法），所以那边每个方法都要带 `UE_API`。
> **这是 Lyra 的两种导出风格，照抄即可，不要"顺手统一"。**

> **为什么 3 个函数全是 `virtual`？**
> Lyra 原样如此——方便下游项目继承 `TeamCheats` 后覆盖某个命令的行为。照抄。

> 依赖只有引擎 `GameFramework/CheatManager.h` + 2 个前置声明（`UObject` / `FFrame`），**零挂起可独立编译**。

## 四、逐段讲解

### 4.1 文件头 + include（第 1~9 行）

```cpp
#pragma once

#include "GameFramework/CheatManager.h"

#include "TenkaichiTeamCheats.generated.h"
```

| 行 | 干什么 |
|----|--------|
| `#pragma once` | 防重复包含（所有 `.h` 标配） |
| `GameFramework/CheatManager.h` | ★ **唯一的项目外依赖**，提供 `UCheatManagerExtension` 基类。引擎文件，不需要挂起 |
| `TenkaichiTeamCheats.generated.h` | UHT 生成头，**文件名必须与本文件同名**（Lyra 是 `LyraTeamCheats.generated.h`，按铁律 24 换成 `Tenkaichi`） |

> 📌 **`generated.h` 必须放最后**：UHT 要求它是最后一个 include，否则编译报 `expected an include at the end`。

### 4.2 两个前置声明（第 11~12 行）

```cpp
class UObject;
struct FFrame;
```

| 声明 | 为什么需要 |
|------|-----------|
| `class UObject;` | `GENERATED_BODY()` 展开后的代码会引用 `UObject`（`Super` 类型） |
| `struct FFrame;` | UHT 生成的蓝图 thunk 函数（`execXxx`）参数里用到，是 UHT 的固定套路 |

> 这两个是 **UHT 的"固定三件套"之二**（另一个是 `generated.h`）。
> 你在 P07.6 `TeamSubsystem.h` 里也见过 `struct FFrame;`——**凡是带 `UFUNCTION` 的类基本都要它**。

### 4.3 类声明（第 14~17 行）

```cpp
/** 与队伍相关的作弊指令 */
UCLASS()
class UTenkaichiTeamCheats : public UCheatManagerExtension
{
	GENERATED_BODY()
```

| 元素 | 说明 |
|------|------|
| `UCLASS()` | **空标记**——没有 `MinimalAPI`、没有 `Blueprintable`、没有 `Config`。Lyra 原样 |
| `UCheatManagerExtension` | 引擎基类（`CheatManager.h:71`），教学分级 **① 只讲不拆** |
| `GENERATED_BODY()` | UHT 宏。注意：**接口类用 `GENERATED_UINTERFACE_BODY()` / `GENERATED_IINTERFACE_BODY()`，普通类用 `GENERATED_BODY()`** |

> **为什么是 `GENERATED_BODY()` 而不是 `GENERATED_UCLASS_BODY()`？**
> Lyra 本文件用的是 `GENERATED_BODY()`（见源码第 16 行），配 `public:` 显式声明。
> （对比 P07.9 `AsyncAction_ObserveTeam` 用的是 `GENERATED_UCLASS_BODY()`——那个要自定义构造函数。）
> **不要改成本文件没有的形式，照抄 Lyra。**

### 4.4 三个函数（第 19~30 行）

```cpp
	// 把这个玩家移动到下一个可用的队伍，如果已经在队伍列表末尾则绕回第一个队伍
	UFUNCTION(Exec, BlueprintAuthorityOnly)
	virtual void CycleTeam();

	// 把这个玩家移动到指定的队伍
	UFUNCTION(Exec, BlueprintAuthorityOnly)
	virtual void SetTeam(int32 TeamID);

	// 打印所有队伍的列表
	UFUNCTION(Exec)
	virtual void ListTeams();
```

#### `UFUNCTION(Exec)` —— 让函数变成控制台命令

| 标记 | 含义 |
|------|------|
| `Exec` | 这个函数可以**在控制台里当命令敲**。命令名就是函数名（`CycleTeam`），参数跟在后面（`SetTeam 3`） |
| `BlueprintAuthorityOnly` | 蓝图调用时**只在权威端（服务器）生效**。防止客户端乱换队 |

> ⚠️ **三档标记差异（重点）**：
> `CycleTeam` 和 `SetTeam` **会改游戏状态** → 加 `BlueprintAuthorityOnly`。
> `ListTeams` **只打印不改状态** → **不加**，客户端也能敲。
> Lyra 就是这么区分的，别图省事三个都加。

#### `virtual` —— 三个都虚

Lyra 原样。好处：下游项目可以继承 `UTenkaichiTeamCheats` 覆盖某个命令（比如换队时发个自定义消息）。

#### 参数

| 函数 | 参数 | 来源 |
|------|------|------|
| `CycleTeam` | 无 | 操作对象 = `GetPlayerController()`（基类提供，见 `.cpp`） |
| `SetTeam` | `int32 TeamID` | 控制台敲 `SetTeam 3` 传进来 |
| `ListTeams` | 无 | — |

> 📌 **注意参数名是 `TeamID`（大写 ID）**，不是 `TeamId`。
> Lyra 里 `TeamSubsystem` 用 `TeamId`，这里用 `TeamID`——**两处不一致是 Lyra 原样，照抄不要统一**。

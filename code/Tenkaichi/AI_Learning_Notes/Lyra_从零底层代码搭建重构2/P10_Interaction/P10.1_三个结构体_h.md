## 二、文件 1：`InteractionQuery.h`（查询信封）

**这个文件回答"谁在发起交互"**。交互系统要把"请求"发给附近的东西时，就把这个结构体打包递过去。

### 完整代码

```cpp
// Copyright Epic Games, Inc. All Rights Reserved.

#pragma once

#include "CoreMinimal.h"
#include "Abilities/GameplayAbility.h"
#include "InteractionQuery.generated.h"


/**  */
USTRUCT(BlueprintType)
struct FInteractionQuery
{
	GENERATED_BODY()

public:
	/** 发起交互的 Pawn（请求交互的那具身体） */
	UPROPERTY(BlueprintReadWrite)
	TWeakObjectPtr<AActor> RequestingAvatar;

	/** 允许我们指定一个控制器，不需要与发起交互的 Pawn 的拥有者匹配 */
	UPROPERTY(BlueprintReadWrite)
	TWeakObjectPtr<AController> RequestingController;

	/** 一个用来塞入交互所需额外数据的通用 UObject 槽 */
	UPROPERTY(BlueprintReadWrite)
	TWeakObjectPtr<UObject> OptionalObjectData;
};
```

### 逐段讲解

| 成员 | 作用 |
|------|------|
| `RequestingAvatar` | **谁在发起交互**。`TWeakObjectPtr<AActor>` 弱引用，不持有所有权（不阻止对方被销毁）。 |
| `RequestingController` | **谁在操控**。通常就是玩家的 PlayerController，但允许和 Avatar 的拥有者不匹配（比如 AI 控制的角色）。 |
| `OptionalObjectData` | **万能口袋**。装任意额外数据（`UObject*`），交互系统自己解释里面的内容。 |

> 💡 **为什么用 `TWeakObjectPtr` 而不是裸指针？** 弱引用不参与生命周期管理，且能安全判空——发起者可能中途被销毁，弱引用会自动失效为 `nullptr`，避免悬空指针。

## 三、文件 2：`InteractionOption.h`（选项信封）

**这个文件回答"能怎么交互"**。系统把附近所有可交互的东西问一遍后，收集到的"可选方案"就是一堆 `FInteractionOption`。

### 完整代码

```cpp
// Copyright Epic Games, Inc. All Rights Reserved.

#pragma once

#include "CoreMinimal.h"
#include "Abilities/GameplayAbility.h"
#include "InteractionOption.generated.h"

class IInteractableTarget;
class UUserWidget;

/**  */
USTRUCT(BlueprintType)
struct FInteractionOption
{
	GENERATED_BODY()

public:
	/** 可交互的目标（那个能被你交互的东西） */
	UPROPERTY(BlueprintReadWrite)
	TScriptInterface<IInteractableTarget> InteractableTarget;

	/** 交互显示的主文本（比如"拾取"） */
	UPROPERTY(EditAnywhere, BlueprintReadWrite)
	FText Text;

	/** 交互显示的副文本（比如"铁剑"） */
	UPROPERTY(EditAnywhere, BlueprintReadWrite)
	FText SubText;

	// 交互方式
	//--------------------------------------------------------------

	// 方式 1：把技能放在发起者身上，交互时触发

	/** 靠近可交互物时，授予发起者的技能（交互时触发它） */
	UPROPERTY(EditAnywhere, BlueprintReadOnly)
	TSubclassOf<UGameplayAbility> InteractionAbilityToGrant;

	// - 或 -

	// 方式 2：被交互的目标自己有技能系统，直接触发它身上的技能

	/** 目标身上的技能系统，可用于 TargetInteractionHandle 和发送事件 */
	UPROPERTY(BlueprintReadOnly)
	TObjectPtr<UAbilitySystemComponent> TargetAbilitySystem = nullptr;

	/** 要在目标身上触发的技能 Spec 句柄 */
	UPROPERTY(BlueprintReadOnly)
	FGameplayAbilitySpecHandle TargetInteractionAbilityHandle;

	// UI
	//--------------------------------------------------------------

	/** 显示这种交互要用的 UI 控件 */
	UPROPERTY(EditAnywhere, BlueprintReadWrite)
	TSoftClassPtr<UUserWidget> InteractionWidgetClass;

	//--------------------------------------------------------------

public:
	// 重载运算符，让这个结构体能放进数组比较、排序
	FORCEINLINE bool operator==(const FInteractionOption& Other) const
	{
		return InteractableTarget == Other.InteractableTarget &&
			InteractionAbilityToGrant == Other.InteractionAbilityToGrant &&
			TargetAbilitySystem == Other.TargetAbilitySystem &&
			TargetInteractionAbilityHandle == Other.TargetInteractionAbilityHandle &&
			InteractionWidgetClass == Other.InteractionWidgetClass &&
			Text.IdenticalTo(Other.Text) &&
			SubText.IdenticalTo(Other.SubText);
	}

	FORCEINLINE bool operator!=(const FInteractionOption& Other) const
	{
		return !operator==(Other);
	}

	FORCEINLINE bool operator<(const FInteractionOption& Other) const
	{
		return InteractableTarget.GetInterface() < Other.InteractableTarget.GetInterface();
	}
};
```

### 逐段讲解

**1. 前置声明（第 8~9 行）**

```cpp
class IInteractableTarget;
class UUserWidget;
```

只用前置声明，不 `#include`。因为这里只声明了指针/引用，不需要完整定义——编译时不阻塞（铁律 30），也避免头文件互相包含。

**2. 核心成员**

| 成员 | 作用 |
|------|------|
| `InteractableTarget` | **那个可交互的东西**。`TScriptInterface` 是"接口类型的智能指针"，既能指向对象，又能调用其接口方法。 |
| `Text` / `SubText` | **给玩家看的文字**（如主文本"拾取"、副文本"铁剑"）。 |
| `InteractionAbilityToGrant` | **方式 1 的钥匙**：交互时给发起者上的技能。 |
| `TargetAbilitySystem` + `TargetInteractionAbilityHandle` | **方式 2 的钥匙**：目标自己有技能系统时，直接触发它身上的技能。 |
| `InteractionWidgetClass` | **UI**：显示这种交互用哪个控件（软引用，`TSoftClassPtr` 不阻塞加载）。 |

**3. 三个运算符（第 62~81 行）**

```cpp
FORCEINLINE bool operator==(const FInteractionOption& Other) const
```

- `==`：两个选项是否**同一个方案**（目标、技能、UI、文本全相同）。
- `!=`：取反。
- `<`：按 `InteractableTarget` 的**接口指针地址**排序，让选项能放进 `TSet`/`TMap` 或排序。

> 💡 **为什么需要这些运算符？** 交互系统经常要"合并/去重/排序"选项列表（比如帧内多次采样），有了它们才能放进 `TArray` 做 `Contains`、`Sort` 等操作。

## 四、文件 3：`TenkaichiInteractionDurationMessage.h`（时长消息信封）

这个文件回答"交互按了多久"。做"按住 3 秒才生效"这类进度交互时，UI 靠它知道该显示多长进度条。

### 完整代码

```cpp
// Copyright Epic Games, Inc. All Rights Reserved.

#pragma once

#include "CoreMinimal.h"
#include "GameplayTagContainer.h"
#include "NativeGameplayTags.h"

#include "TenkaichiInteractionDurationMessage.generated.h"

UE_DECLARE_GAMEPLAY_TAG_EXTERN(TAG_INTERACTION_DURATION_MESSAGE);

/**
 * 交互时长消息：广播"谁正在交互 + 需要持续多久"
 */
USTRUCT(BlueprintType)
struct FTenkaichiInteractionDurationMessage
{
	GENERATED_BODY()

public:
	/** 发起交互的人 */
	UPROPERTY(BlueprintReadWrite)
	TObjectPtr<AActor> Instigator = nullptr;

	/** 需要持续的秒数 */
	UPROPERTY(BlueprintReadWrite)
	float Duration = 0;
};
```

### 逐段讲解

**1. GameplayTag 声明（第 11 行）**

```cpp
UE_DECLARE_GAMEPLAY_TAG_EXTERN(TAG_INTERACTION_DURATION_MESSAGE);
```

声明一个**外部 GameplayTag**：这个名字只在头文件里"预告"一下，真正的定义在别处。这样别的文件 `#include` 后就能用 `TAG_INTERACTION_DURATION_MESSAGE` 这个标签订阅/广播。

> ⚠️ 这里和 P10.1 其他两个结构体不同：它虽无 `.cpp`，但这个 tag 的**定义**需要在工程某处 `UE_DEFINE_GAMEPLAY_TAG` 声明一次（否则链接报错）。这一步在**后面真正用它广播的模块**（如交互技能 `.cpp`）里落实，现在只要知道它是"外部标签声明"即可。

**2. 两个成员**

| 成员 | 作用 |
|------|------|
| `Instigator` | **谁在交互**（发起交互的那个 Actor）。 |
| `Duration` | **要持续几秒**。UI 拿它算进度条时长。 |

> 💡 **为什么这算"信封"？** 它自己不做任何事，只是"把『谁 + 多久』打包好，交给广播系统"。收到它的人（进度条 UI）才知道该显示什么。

## 五、三个文件一起看：它们怎么配合

| 结构体 | 什么时候被用 | 一句话 |
|--------|------------|--------|
| `FInteractionQuery` | 发起交互时 | "**我问**：谁要交互？" |
| `FInteractionOption` | 收集结果时 | "**我答**：可以这样交互（目标+文本+技能+UI）" |
| `FTenkaichiInteractionDurationMessage` | 交互进行中 | "**我播报**：这个交互要按住 X 秒" |

三者都**不做事**，只**装数据**——真正的逻辑在 P10.4~P10.9 的类和技能里。

## 一、这个类解决什么问题（先讲为什么）

`UIndicatorDescriptor`（P16.7.2）只是"一条指示器的数据"，它自己不知道"谁在管我"。系统需要一个**容器**：
- 记住所有活跃的指示器。
- 支持增删，并在增删时**广播事件**（让 `SActorCanvas` 知道要重画）。

`ULyraIndicatorManagerComponent` 就是这个容器——挂在 `PlayerController` 上（每个玩家一份），管他自己的所有指示器。

> **类比**：`Descriptor` 是"任务卡"，`ManagerComponent` 是"卡片盒"——装卡、取卡、加卡/删卡时喊一声（广播）。

**为什么挂 PlayerController？** 因为指示器是"给某个玩家看的"（队友标记只对他自己显示）。每个玩家有独立的指示器集合。

### `TenkaichiIndicatorManagerComponent.cpp`（42 行）

```cpp
// 版权声明（可保留或省略，不影响编译）
#include "TenkaichiIndicatorManagerComponent.h"

#include "IndicatorDescriptor.h"

#include UE_INLINE_GENERATED_CPP_BY_NAME(TenkaichiIndicatorManagerComponent)

// 构造函数：自动注册 + 自动激活。
UTenkaichiIndicatorManagerComponent::UTenkaichiIndicatorManagerComponent(const FObjectInitializer& ObjectInitializer)
	: Super(ObjectInitializer)
{
	bAutoRegister = true;
	bAutoActivate = true;
}

// 从控制器上找本组件（便捷静态方法）。
/*static*/ UTenkaichiIndicatorManagerComponent* UTenkaichiIndicatorManagerComponent::GetComponent(AController* Controller)
{
	if (Controller)
	{
		return Controller->FindComponentByClass<UTenkaichiIndicatorManagerComponent>();
	}

	return nullptr;
}

// 添加一条指示器。
void UTenkaichiIndicatorManagerComponent::AddIndicator(UIndicatorDescriptor* IndicatorDescriptor)
{
	IndicatorDescriptor->SetIndicatorManagerComponent(this);
	OnIndicatorAdded.Broadcast(IndicatorDescriptor);
	Indicators.Add(IndicatorDescriptor);
}

// 移除一条指示器。
void UTenkaichiIndicatorManagerComponent::RemoveIndicator(UIndicatorDescriptor* IndicatorDescriptor)
{
	if (IndicatorDescriptor)
	{
		ensure(IndicatorDescriptor->GetIndicatorManagerComponent() == this);
	
		OnIndicatorRemoved.Broadcast(IndicatorDescriptor);
		Indicators.Remove(IndicatorDescriptor);
	}
}
```

## 三、关键点讲解

### 1. 基类 `UControllerComponent`——"只能挂 Controller"的组件

```cpp
class UTenkaichiIndicatorManagerComponent : public UControllerComponent
```

`UControllerComponent` 是 **ModularGameplay 插件**（S1）提供的组件基类——**只能挂在 `AController` 上**（类比 `UGameStateComponent` 只能挂 GameState，P13.5）。

好处：类型上保证"不会误挂到 Actor 上"，且自动参与 Controller 的组件体系。

### 2. `bAutoRegister` / `bAutoActivate`

```cpp
bAutoRegister = true;
bAutoActivate = true;
```

- `bAutoRegister`：组件创建时**自动注册**（参与 Tick/复制等）。
- `bAutoActivate`：组件创建时**自动激活**（`Activate()` 被调用）。

> 对比普通 `UActorComponent` 默认 `bAutoActivate = true` 但 `bAutoRegister` 需要手动。这里两个都显式开。

### 3. `GetComponent(AController*)`——静态便捷方法

```cpp
/*static*/ UTenkaichiIndicatorManagerComponent* UTenkaichiIndicatorManagerComponent::GetComponent(AController* Controller)
{
	if (Controller)
	{
		return Controller->FindComponentByClass<UTenkaichiIndicatorManagerComponent>();
	}
	return nullptr;
}
```

`/*static*/` 是**注释**（不是语法）——UE 代码风格里用于**标记**"这是静态函数"（因为 `.cpp` 定义处不写 `static` 关键字，靠注释提示）。

> 按铁律 23 照抄 `/****/` 注释。

### 4. `AddIndicator`——三步（注意顺序）

```cpp
void UTenkaichiIndicatorManagerComponent::AddIndicator(UIndicatorDescriptor* IndicatorDescriptor)
{
	IndicatorDescriptor->SetIndicatorManagerComponent(this);   // ① 反向绑定
	OnIndicatorAdded.Broadcast(IndicatorDescriptor);            // ② 广播
	Indicators.Add(IndicatorDescriptor);                        // ③ 加进列表
}
```

**注意顺序**：**广播在 `Add` 之前**！

**为什么？** 因为监听者（`SActorCanvas`）收到 `OnIndicatorAdded` 时需要立刻处理这个指示器——它可能会调 `GetIndicators()` 或者直接操作 Descriptor。此时 Descriptor 已经"知道自己归属"（①），可以安全处理。

> 如果先 `Add` 再广播，监听者在广播里遍历 `Indicators` 时会看到"刚加的那个"——两种顺序都行，但 Lyra 选了"广播在前"（监听者不依赖列表状态）。

### 5. `RemoveIndicator`——`ensure` 校验归属

```cpp
if (IndicatorDescriptor)
{
	ensure(IndicatorDescriptor->GetIndicatorManagerComponent() == this);
	
	OnIndicatorRemoved.Broadcast(IndicatorDescriptor);
	Indicators.Remove(IndicatorDescriptor);
}
```

`ensure(... == this)`：确认"这个指示器确实归我管"。如果别的管理器在删，说明有 bug（打警告）。

> 注意：**这里没有** `IndicatorDescriptor->SetIndicatorManagerComponent(nullptr)`——因为 `SetIndicatorManagerComponent` 只能设一次（P16.7.2 的 `ensure(IsExplicitlyNull())`）。删掉后 Descriptor 的 `ManagerPtr` 仍指向本组件（但它已经从列表移除，不会再被使用）。

### 6. `DECLARE_EVENT_OneParam`——C++ 专用事件

```cpp
DECLARE_EVENT_OneParam(UTenkaichiIndicatorManagerComponent, FIndicatorEvent, UIndicatorDescriptor* Descriptor)
FIndicatorEvent OnIndicatorAdded;
FIndicatorEvent OnIndicatorRemoved;
```

`DECLARE_EVENT_OneParam(拥有者类, 事件类型名, 参数类型)`：声明一个 **C++ 专用事件**（`TMulticastDelegate<void(参数)>` 的轻量版）。

对比 P16.4.5 的 `DECLARE_DYNAMIC_MULTICAST_DELEGATE`（蓝图可绑）。这里是 C++ 专用：
- 更轻量（不生成 UFunction）。
- 蓝图**不可见**（`SActorCanvas` 是 C++，够用）。

**注意**：声明在类**内部**（不像前面在类外/文件作用域）。这是 `DECLARE_EVENT_*` 的常见用法（宏展开后就是类内 typedef）。

### 7. `GetIndicators()` 返回 `const TArray<T*>&`（裸指针）

```cpp
const TArray<UIndicatorDescriptor*>& GetIndicators() const { return Indicators; }
```

注意返回的是 **`UIndicatorDescriptor*`（裸指针）**，而成员是 `TObjectPtr<UIndicatorDescriptor>`。

> `TObjectPtr<T>` 可以隐式转成 `T*`——所以 `TArray<TObjectPtr<T>>` 能转 `const TArray<T*>&`？**不能**（不同类型）。
>
> 实际上这里能编译是因为：`TArray<TObjectPtr<T>>` 和 `TArray<T*>` 布局兼容，UE 提供了隐式转换的 hack（`TArray` 有 `operator const TArray<T*>&` 之类）。这是 UE 容器的特殊处理。
>
> 按铁律 23 照抄，不要在工程里改成别的写法。

## 一、这一小步要解决什么问题

模块地基（Build.cs / 模块入口）已经搭好了，但还差一件事：**给日志分类**。

先回顾一个场景：你在调试时想打印日志，会用 `UE_LOG(...)`。但一个游戏项目里日志会非常多——技能系统的、经验流程的、队伍系统的、角色生成的……全混在一起，`Output Log` 里刷屏，你根本分不清哪条是谁打的、该去哪找。

**日志通道（Log Category）就是解决这个的**：它给日志**分类**，每类起个名字。打印时指定用哪一类，UE 就能：
1. 按类别过滤日志（只看技能系统，别的屏蔽掉）；
2. 按类别控制详细程度（某些类别只在出问题时才输出）；
3. 在日志输出里带上类别名，一眼看出这条日志属于哪个模块。

Lyra 在这一步就先把「自己项目要用哪些日志分类」**提前声明好**，放在模块地基里，这样后面所有层（L2~L7）的代码都能直接拿这些分类来打日志，不用各自再定义一遍。

**验收**：读完本文，能说清「日志通道是什么、为什么要放模块地基、Lyra 声明了哪几个通道」。本步不写代码。

## 二、Lyra 的日志通道长什么样（先查真实源码）

打开 `E:\ue5\LyraStarterGame5.6\LyraStarterGame\Source\LyraGame\LyraLogChannels.h`，全文 14 行：

```cpp
// Copyright Epic Games, Inc. All Rights Reserved.

#pragma once

#include "Logging/LogMacros.h"

class UObject;

LYRAGAME_API DECLARE_LOG_CATEGORY_EXTERN(LogLyra, Log, All);
LYRAGAME_API DECLARE_LOG_CATEGORY_EXTERN(LogLyraExperience, Log, All);
LYRAGAME_API DECLARE_LOG_CATEGORY_EXTERN(LogLyraAbilitySystem, Log, All);

LYRAGAME_API FString GetClientServerContextString(UObject* ContextObject = nullptr);
```

Lyra 声明了 **4 个日志通道** + **1 个工具函数**：

| 日志通道 | 中文含义 | 用来打哪类日志 |
|---------|---------|---------------|
| `LogLyra` | 通用日志 | 项目里杂七杂八的通用信息 |
| `LogLyraExperience` | 经验系统日志 | 阶段 L4 的 Experience（玩法流程）相关 |
| `LogLyraAbilitySystem` | 技能系统日志 | 阶段 L5 的 GAS（Gameplay Ability System）相关 |
| `LogLyraTeams` | 队伍系统日志 | 阶段 L5 的 Teams（队伍）相关 |

外加一个工具函数 `GetClientServerContextString()`——它判断「当前是 Server 端还是 Client 端」，拼出一段字符串（`Server` / `Client` / `[]`），方便联机调试时把这段塞进日志，一眼看出日志来自哪端。

## 三、两个关键概念（先讲清为什么，再讲怎么写）

### 概念 ①：日志分类的「两件套」—— `DECLARE` 在 `.h`、`DEFINE` 在 `.cpp`

UE 的日志分类，一个分类要写**两次**（引擎源码 `LogMacros.h` 核实）：

- **`DECLARE_LOG_CATEGORY_EXTERN(名字, 默认级别, 编译级别)`** —— 写在 `.h` 里，是「**声明**」。它说「这个分类存在，别的文件 include 这个头文件就能用」。
- **`DEFINE_LOG_CATEGORY(名字)`** —— 写在 `.cpp` 里，是「**定义**」。它说「这个分类真正在这里落地，分配实际的存储」。

> 为什么分两处？这是 C++ 的经典「声明 vs 定义」分离：`.h` 负责「让所有文件都知道有这个分类」，`.cpp` 负责「只在这一个地方真正创建它」。如果只在 `.h` 声明、忘了在 `.cpp` 定义，链接阶段会报「找不到这个分类」。

引擎里 `DECLARE_LOG_CATEGORY_EXTERN` 的真实定义（`LogMacros.h` 第 332 行）：

```cpp
#define DECLARE_LOG_CATEGORY_EXTERN(CategoryName, DefaultVerbosity, CompileTimeVerbosity) \
	extern struct FLogCategory##CategoryName : public FLogCategory<ELogVerbosity::DefaultVerbosity, ELogVerbosity::CompileTimeVerbosity> \
	{ \
		FORCEINLINE FLogCategory##CategoryName() : FLogCategory(TEXT(#CategoryName)) {} \
	} CategoryName;
```

不用深究这个宏内部，先记住两点：**① 它在 `.h` 里声明一个「全局日志分类对象」；② 三个参数是「名字、默认级别、编译级别」。**

### 概念 ②：三个参数 `Log, All` 是什么意思

Lyra 每个通道写的是 `DECLARE_LOG_CATEGORY_EXTERN(LogLyra, Log, All)`，中间那两个 `Log` 和 `All` 是**详细程度（Verbosity）**：

- **第二个参数 `Log`** = **默认运行时级别**。正常运行时，这个分类默认输出 `Log` 级别（及更严重）的日志。
- **第三个参数 `All`** = **编译时允许的最高级别**。`All` 表示这个分类的所有级别日志都会被编译进代码（不会被编译器砍掉）。

> 日志级别从轻到重大致是：`Verbose` → `VeryVerbose` → `Log` → `Display` → `Warning` → `Error` → `Fatal`。`Log, All` 的意思 =「默认显示 Log 及以上，且所有级别都编译保留」。这是 Lyra 的通用选择，照抄即可（具体每个级别的语义，等后面真正打日志时再展开）。

## 四、为什么这些「日志通道」要放在模块地基（第 1 步）

这是关键，回到依赖层次：

```
L1 模块地基：模块入口 / Build.cs / 日志通道 / GameplayTags
```

日志通道放在 L1（最底层），是因为**后面所有层都要用它**：

- L2 的 ModularGameplayActors、L3 的 System、L4 的 Character、L5 的 AbilitySystem/Teams……这些代码里都会写 `UE_LOG(LogLyraAbilitySystem, ...)` 之类的日志。
- 如果日志通道不先建好，后面每写一层代码，就得回头补日志分类，或者各自乱定义，乱成一团。
- 所以 Lyra 在「地基」这一步就把 4 个日志通道一次性声明好，后面直接用。

> 这就是「自下而上」的体现：**被依赖的东西先建**。日志通道被 L2~L7 依赖，所以它在 L1 先落地。

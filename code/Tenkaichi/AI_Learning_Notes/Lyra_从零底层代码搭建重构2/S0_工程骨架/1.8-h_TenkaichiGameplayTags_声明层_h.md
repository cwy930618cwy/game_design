## 一、先讲为什么（这文件解决什么）

回顾总 md：GameplayTag 要「用变量不用字符串」，那么**变量得先声明出来**，别人才知道「有 `Ability_ActivateFail_IsDead` 这么个 Tag 变量可以用」。

`.h` 的职责就是干这件事：**把 38 个 Tag 变量名、2 个映射表、1 个工具函数，一股脑 `extern` 声明出去**。别的文件只要 `#include "TenkaichiGameplayTags.h"`，就能用 `TenkaichiGameplayTags::Ability_ActivateFail_IsDead` 拿到这个 Tag，而且编译器会帮你查变量名拼写。

> 和 1.7 日志通道一个套路：`.h` 声明、`.cpp` 定义，成对出现（铁律 11）。

## 二、先讲几个没教过的东西（铁律 18）

### 1. `#include "NativeGameplayTags.h"`

这是 `UE_DECLARE_GAMEPLAY_TAG_EXTERN` / `UE_DEFINE_GAMEPLAY_TAG_COMMENT` 这两个宏的「家」。不 include 它，下面 38 个 `UE_DECLARE_GAMEPLAY_TAG_EXTERN` 会报「宏未定义」。

引擎真实路径（已核实）：`Engine/Source/Runtime/GameplayTags/Public/NativeGameplayTags.h`。里面核心宏：

```cpp
#define UE_DECLARE_GAMEPLAY_TAG_EXTERN(TagName) extern FNativeGameplayTag TagName;
```

所以 38 行 `UE_DECLARE_GAMEPLAY_TAG_EXTERN(...)` 展开后就是 38 个 `extern FNativeGameplayTag 变量名;`——**声明**一个 `FNativeGameplayTag` 类型的全局变量，别的文件 include 后就能引用。

### 2. `namespace TenkaichiGameplayTags { ... }`

Lyra 不用 `class`，而是用**命名空间**包住这些 Tag 变量。原因：Tag 是「全局唯一的一堆常量」，不需要实例化对象，直接 `TenkaichiGameplayTags::Ability_ActivateFail_IsDead` 用即可。命名空间里全是「全局变量 + 函数」，没有成员函数/构造。

### 3. `LYRAGAME_API` → `TENKAICHIGAME_API`（导出宏）

和日志通道 1.7 一样，这是模块导出宏（`TenkaichiGame` 模块 → `TENKAICHIGAME_API`）。放在 `extern` 变量/函数前面，表示「这个符号要导出，让别的模块能用」。**变量声明必须带这个宏**，否则链接时报「无法解析的外部符号」。

### 4. `UE_DECLARE_GAMEPLAY_TAG_EXTERN(TagName)` 的参数只有变量名

注意它**只有一个参数**（变量名，下划线版），不像 `.cpp` 里的 `UE_DEFINE_GAMEPLAY_TAG_COMMENT` 有三个参数。因为「变量名 ↔ 真实字符串 ↔ 注释」的绑定在 `.cpp` 做，`.h` 只需要知道「有这么个变量」。

### 5. `extern const TMap<uint8, FGameplayTag> MovementModeTagMap;`

这不是 Tag，是**映射表**（把引擎的移动模式枚举 `uint8` 映射到对应 Tag）。`extern` 表示「定义在 `.cpp`，这里只声明」。后面 L5 的移动逻辑会用它。

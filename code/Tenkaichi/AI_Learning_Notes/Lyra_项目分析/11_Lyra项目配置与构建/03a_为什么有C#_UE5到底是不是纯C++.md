# 03a — 为什么有 C#？UE5 到底是不是"纯 C++"？

> **定位**：上一篇 `03` 拆 `LyraClient.Target.cs` 时，`using System.Collections.Generic` 这种 C# 语法冒出来了。你可能一直以为"UE5 是纯 C++"，怎么会有 C#？这一篇把这个疑问一次讲清。
>
> **结论先行**：UE5 的**游戏运行时是 C++**；但它的**构建/打包工具链是用 C# 写的**，`Target.cs`、`Build.cs` 属于工具链，不在游戏里跑。所以"UE5 底层有 C#"和"UE5 是 C++"都对——说的是**两层不同的东西**。

---

## 一、一张图先建立全局观：UE5 = 三层

```
 ┌───────────────────────────────────────────────────────────┐
 │ ③ 蓝图层（可视化脚本，存成 .uasset）                        │
 │     事件图表 / 变量 / 节点连线                              │
 └───────────────────────────────────────────────────────────┘
 ┌───────────────────────────────────────────────────────────┐
 │ ② 运行时层 = C++（进游戏包，玩家设备上执行）                 │
 │     Engine 引擎核心 + 你的项目模块（LyraGame、code）        │
 │     文件后缀：.h / .cpp                                     │
 │     ↓ 会被编译器编进游戏 exe                                │
 └───────────────────────────────────────────────────────────┘
 ┌───────────────────────────────────────────────────────────┐
 │ ① 构建工具层 = C#（只在你电脑上跑，绝不打进游戏）             │
 │     UBT  UnrealBuildTool  读 Target.cs / Build.cs 规则     │
 │     UAT  UnrealAutomationTool  打包/自动化                  │
 │     文件后缀：.cs                                          │
 └───────────────────────────────────────────────────────────┘
```

| 层 | 语言 | 什么时候运行 | 文件后缀 |
|---|---|---|---|
| 构建工具层 | **C#** | 编译 / 打包 / 生成工程时 | `.cs`（Target.cs、Build.cs、UBT 本体） |
| 运行时层 | **C++** | 玩家打开游戏后 | `.h` / `.cpp` |
| 蓝图层 | 蓝图（可视化） | 游戏内由虚拟机解释 | `.uasset` |

> 💡 **场景记忆**：你做一盘炒饭（游戏本体 = C++）——
> - 炒饭里的大米、鸡蛋是 C++（玩家吃到嘴里）
> - 而**菜谱、采购单是 C#**（厨师=UBT 照着下单，菜谱不会出现在盘子里）
> - 蓝图是"给不会炒菜的人看的图解步骤卡"，也能指挥下锅，但最后还是要 C++ 的锅铲来炒

## 二、为什么"有人说 UE5 底层有 C#"——他没说错，但要加个范围

确实存在大量 C#，但它们都在**第一层（构建工具层）**，不在"引擎运行时底层"：

| 东西 | 是什么语言 | 干嘛的 |
|---|---|---|
| `Engine/Source/Programs/UnrealBuildTool/` | **C#** | UBT 本体：负责解析 Target.cs/Build.cs、组织编译 |
| `Engine/Source/Programs/AutomationTool/` | **C#** | UAT：打包、烘焙内容、自动化流程 |
| 项目里的 `*.Target.cs` / `*.Build.cs` | **C#** | 你写的"构建规则"，被 UBT 加载执行 |
| 引擎运行时 `Engine/Source/Runtime/...` | C++ | 渲染、物理、GAS 等，真正的"引擎底层" |

**传闻的原版出处**大概是：有人翻引擎目录，发现 `UnrealBuildTool`、`AutomationTool` 等一大片是 C#，于是说"UE5 底层有 C#"。

> ✅ 准确说法应该是：**UE5 的引擎/游戏运行逻辑是 C++；UE5 的构建与自动化工具链是 C#。**

---

## 三、那 `LyraClient.Target.cs` 里的 C# 具体在干嘛

回到上一篇那个 17 行文件：

```csharp
using UnrealBuildTool;                  // ← C#：引入 UBT 类型库
using System.Collections.Generic;       // ← C#：引入 .NET 集合库

public class LyraClientTarget : TargetRules   // ← C#：定义一个"目标类"
{
	public LyraClientTarget(TargetInfo Target) : base(Target)
	{
		Type = TargetType.Client;                       // 属性赋值
		ExtraModuleNames.AddRange(new string[] { "LyraGame" });
	}
}
```

这里每一行都是 **C# 规则代码**，作用是：UBT（一个 C# 程序）在编译前先执行这些代码，得知"要编一个 Client 类型的程序、带上 LyraGame 模块"。

> 💡 **为什么必须用 C# 而不用 C++？**
> 1. UBT 每天要跨 Windows/Mac/Linux 解析 JSON（`.uproject`、`.uplugin`）、读命令行、配编译参数——C# 做这些"开发机上的管理活"很顺手；
> 2. 构建工具**不追求运行性能**（多跑几毫秒无所谓），但求**易读、易扩展、跨平台**——正好是 C# 的强项；
> 3. 这类工具代码要是也用 C++，会显著拖慢引擎全量编译，还没必要。

## 四、确认一下：这些 C# 真的不会进玩家电脑吗

**不会。** 玩家运行的是打包后的游戏 exe，里面是 C++ 编译出的机器码 + 资源。`.cs` 只是"开发期说明书"：

```
你写 .cs → UBT(运行 .NET) 读取 → 决定编什么 → C++ 编译器产 exe → 玩家只拿到 exe
           ↑ 这步发生在你的开发机上，与玩家无关
```

> 证据：打开一个打包好的游戏目录，你找不到任何 `.cs` 或 `.dll`（除非你主动集成了 .NET 功能）。你之前给 `code.Build.cs` 加 GAS 三件套那件事，改完也只是**影响编译结果**，游戏运行时不执行它。

## 五、补充：还有哪几种语言会在 UE 里出现？

| 技术 | 语言 | 你在哪遇到 |
|---|---|---|
| 游戏逻辑（推荐） | C++ | 写能力、角色、组件 |
| 可视化脚本 | 蓝图 | 编辑器的蓝图图表 |
| 构建规则 | C# | `Target.cs` / `Build.cs` / UBT |
| 着色器 | HLSL | `.usf` 材质/Shader 文件 |
| 老的脚本语言 | UnrealScript | **UE3 及以前**才有，UE4 起删了（蓝图接班） |

> 💡 如果有人再说"UE 以前不是用 UnrealScript 吗"——那是 UE3 时代的事，UE4/UE5 已经不用它写玩法了。

## 六、本系列里 C# 会出现在哪几个场景（对你最有用的点）

| 你会遇到的动作 | 接触的文件（C#） | 语言 |
|---|---|---|
| 给模块加依赖（如加 GAS） | `code.Build.cs` | C# |
| 新增一个可打包的程序 | `xxx.Target.cs` | C# |
| 右键 Generate VS 工程文件 | UBT（自动） | C# |
| 命令行打包 / 跑自动化测试 | UAT（自动） | C# |
| 写游戏功能本身 | `.h` / `.cpp` | **C++** |

**本篇一句话**：看到 `.cs` 别慌——那是 UE 的"**构建工具用的 C#**"，只在编译/打包时替你下命令；真正跑在玩家机器上的游戏代码，依然是 C++。两种你都可能碰，但记住**写玩法 = C++，配置构建 = C#**，就不会混了。

## 七、常见追问：为什么不全都用 C++？又不是不会写

> 上面道理懂了，但你可能还卡在一个点上："**UE 自己不就是 C++ 写的吗？顺手把工具也用 C++ 写了不完了？**"——这一节专门回答这个。

### 1. 因为"游戏运行时"和"帮你编译游戏的工具"是两种完全不同的任务

用一个餐厅的比喻（换一个，跟上文炒饭互补）：

```
 游戏本体 = 餐厅后厨（C++）         构建工具 = 收银/点单系统（C#）
 ─────────────────────────       ─────────────────────────
 · 出菜快、火候准                  · 不用快，但要：
 · 一帧 16ms 内干完所有事           ·  好改（加个菜很快）
 · 内存要精打细算                  ·  好维护（谁都能看懂）
 · 这是玩家吃进嘴的东西             ·  不容易写错
```

收银台不需要用后厨的铁锅去炒菜。**任务不一样，选的语言就不一样**——而不是"哪个语言高级用哪个"。

### 2. 用 C# 写构建工具的 5 条实在理由

| # | 理由 | 展开说 |
|---|---|---|
| 1 | **工具不在乎性能** | UBT 多跑 0.1 秒无所谓；游戏 C++ 慢 1ms 就掉帧。没性能压力 → 选"好写"的语言 |
| 2 | **现成库一大把** | 构建要解析 JSON（`.uproject`）、正则、遍历文件、调用 MSBuild/clang、生成 `.sln`——C#/.NET 全是现成的；C++ 得自己造 |
| 3 | **跨平台省事** | C# 装个 .NET 环境，Win/Mac/Linux 直接跑；C++ 工具要三个平台各编各维护 |
| 4 | **防止"先有鸡还是先有蛋"** | UBT 是**负责编译 UE 的**。UBT 要是 C++，谁来先编译 UBT？C# 不用——装好 .NET 就能跑 |
| 5 | **你的 `.cs` 要频繁改** | 给 `Build.cs` 加个依赖是常事，C# 规则能即时编译、秒级生效；C++ 每次改完先等编译 |

### 3. 推演："全用 C++"会发生什么

技术上**能**做（UE 早期有些工具就是 C++），代价是：

```
全用 C++ 的成本                         换来什么收益
─────────────────────────────        ──────────
· 写起来慢、内存容易出错                 · 工具快几毫秒？（没人在乎）
· Windows/Mac/Linux 各维护一份           · 玩家体验变好？（工具不上玩家机器）
· 加个小功能要重新编译整个工具
· 还要自己造 JSON/正则/编译调用库
```

**成本一堆，收益为零**——因为 C++ 的强项（性能、底层控制）在工具上根本没处发挥。

### 4. 记住一句"选语言"的准则

```
 任务要跑在玩家设备上、追求性能  ──►  C++（游戏代码）
 任务只在你开发机上跑、求好维护  ──►  C#（构建工具）
```

回到你手上的活：**写角色、技能、伤害永远是 C++**；只有"加模块依赖""新增打包目标"这种**配构建**的活才碰 `.cs`，而且那不需要你会写 C#，照抄格式即可——就像你之前给 `code.Build.cs` 加 GAS 三件套一样。

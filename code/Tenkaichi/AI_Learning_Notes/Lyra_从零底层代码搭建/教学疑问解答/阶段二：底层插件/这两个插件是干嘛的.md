# 这两个插件是干嘛的？—— 阶段二底层插件讲解

> 说明：本文回答「`ModularGameplayActors` 和 `GameplayMessageRouter` 到底是干嘛的」。
> 源码依据：`Tenkaichi\Plugins\` 下这两个插件（刚从 Lyra 一比一复制过来）。

---

## 一、一句话概括

| 插件 | 一句话 | 类比 |
|------|--------|------|
| `ModularGameplayActors` | 给 Actor 留"扩展插槽"，让别的插件能往它身上动态挂组件 | 出厂机器 + 一排可插拔扩展卡槽 |
| `GameplayMessageRouter` | 让互不认识的对象，靠"暗号（Tag）"互相广播/监听消息 | 对讲机广播，喊暗号就能对上号 |

---

## 二、ModularGameplayActors —— 模块化 Actor 基类

### 它解决什么问题？

引擎原生的 `ACharacter`/`AGameMode`/`APlayerState` 这些类，**能力在编译时就写死了**。Lyra 想要的是：**同一个角色类，在不同玩法（射击/大逃杀）下拥有不同的能力组合**，而这些能力由"游戏功能插件（Game Feature Plugin）"在**运行时动态提供**。

`AModularCharacter` 之类的基类，就是继承原生类，但**额外留一个"挂钩子"的口子**，让别的插件能往这个 Actor 上动态添加组件。

### 它到底做了什么？（看真实源码）

以 `ModularCharacter.cpp` 为例，整个类就三个函数，每个都只干一件事——**调用 `UGameFrameworkComponentManager`（框架组件管理器）**：

```cpp
void AModularCharacter::PreInitializeComponents()
{
    Super::PreInitializeComponents();
    // ① 把自己登记为"可接收扩展组件"的目标
    UGameFrameworkComponentManager::AddGameFrameworkComponentReceiver(this);
}

void AModularCharacter::BeginPlay()
{
    // ② 广播一个事件："我这个 Actor 已经 Ready 了，谁要给我挂组件的赶紧来"
    UGameFrameworkComponentManager::SendGameFrameworkComponentExtensionEvent(
        this, UGameFrameworkComponentManager::NAME_GameActorReady);
    Super::BeginPlay();
}

void AModularCharacter::EndPlay(const EEndPlayReason::Type EndPlayReason)
{
    // ③ 销毁时注销登记
    UGameFrameworkComponentManager::RemoveGameFrameworkComponentReceiver(this);
    Super::EndPlay(EndPlayReason);
}
```

**关键点**：这个基类本身**没有任何游戏逻辑**，它只做三件事——「登记 → 广播 Ready 事件 → 注销」。真正往它身上挂组件的是别的插件（Game Feature），它们监听那个 `NAME_GameActorReady` 事件，趁 Actor 准备好的时候把自己要加的组件挂上去。

### 它提供了哪些基类？（全景清单）

| 基类 | 继承自 | 用途 |
|------|--------|------|
| `AModularCharacter` | `ACharacter` | 模块化角色 |
| `AModularPawn` | `APawn` | 模块化 Pawn |
| `AModularPlayerController` | `APlayerController` | 模块化玩家控制器 |
| `AModularPlayerState` | `APlayerState` | 模块化玩家状态 |
| `AModularGameModeBase` | `AGameModeBase` | 模块化基础游戏模式 |
| `AModularGameMode` | `AGameMode` | 模块化游戏模式 |
| `AModularGameStateBase` | `AGameStateBase` | 模块化基础游戏状态 |
| `AModularGameState` | `AGameState` | 模块化游戏状态 |
| `AModularAIController` | `AAIController` | 模块化 AI 控制器 |

> 后面 L4 阶段，Lyra 自己的 `ALyraCharacter`、`ALyraGameMode` 等，**继承的就是这些 `AModular*` 基类**，而不是直接继承引擎原生类。这就是它作为"地基"的意义。

## 三、GameplayMessageRouter —— 消息路由

### 它解决什么问题？

传统做法：A 对象想通知 B，得**拿到 B 的引用**再调 B 的方法 → 强耦合（A 必须认识 B）。

消息路由做法：A 和 B 都只认识一个"中间人"（`UGameplayMessageSubsystem`）和一个"暗号"（`FGameplayTag`）。A 广播"我发了 `GameplayEvent.Death` 消息"；B 监听"`GameplayEvent.Death` 来了叫我"。中间人负责牵线，A 和 B **永远不需要互相认识**。

> 这正是 L1 阶段我们建的 `TenkaichiGameplayTags.h` 里那些 `GameplayEvent_Death`、`GameplayEvent_Reset` 等标签的用途——它们就是消息路由用的"暗号/频道"。

### 核心类：`UGameplayMessageSubsystem`

它是个**游戏实例子系统（`UGameInstanceSubsystem`）**，整个游戏生命周期就一个实例，充当"消息总线"。

**两个核心操作**（看头文件源码）：

1. **广播消息**（发）：
```cpp
template <typename FMessageStructType>
void BroadcastMessage(FGameplayTag Channel, const FMessageStructType& Message);
```
- `Channel`：频道（用 Tag 标识，如 `GameplayEvent.Death`）
- `Message`：消息体（一个 `USTRUCT` 结构体，发的人和收的人必须约定好同一个类型）

2. **注册监听**（收）：
```cpp
template <typename FMessageStructType>
FGameplayMessageListenerHandle RegisterListener(
    FGameplayTag Channel,
    TFunction<void(FGameplayTag, const FMessageStructType&)>&& Callback,
    EGameplayMessageMatch MatchType = EGameplayMessageMatch::ExactMatch);
```
- 返回一个 `FGameplayMessageListenerHandle`（句柄），拿着它以后可以 `Unregister()` 取消监听。

**怎么拿到这个子系统**（头文件注释里写得很清楚）：
```cpp
// 从游戏实例拿
UGameInstance::GetSubsystem<UGameplayMessageSubsystem>(GameInstance);
// 或从任何有 world 上下文的对象拿
UGameplayMessageSubsystem::Get(WorldContextObject);
```

### 关键设计点（值得记住）

1. **靠 Tag 对上号，不靠对象引用** —— 松耦合的本质。
2. **消息体是 `USTRUCT` 类型** —— 发的人和收的人必须约定同一个结构体类型，否则会报错。
3. **类型安全** —— 模板函数 `BroadcastMessage<FMessageStructType>` 会把结构体类型也一起传过去，监听端用 `reinterpret_cast` 转回，类型不对会打错误日志。
4. **多个监听者顺序不保证** —— 同一个频道多个监听者，调用顺序可能变化（头文件注释明确说了）。

## 四、为什么它们放在 L2（底层），而不是更高层？

回到总纲依赖层次：

- `ModularGameplayActors` 是**后面所有角色/GameMode 的基类**（L4 的 `ALyraCharacter` 继承 `AModularCharacter`），所以是"被依赖"的地基。
- `GameplayMessageRouter` 是**跨系统通信的总线**（L3/L4/L5 大量用到 `GameplayEvent_*` 广播），也是"被依赖"的地基。

它们自己不依赖 `TenkaichiGame` 模块（甚至不依赖 Lyra 自己的代码），所以位于最底层，先搭好，上面的层才能用。

## 五、这两个插件和 L1 的区别（重要认知）

| 维度 | L1（日志通道 / GameplayTags） | L2（这两个插件） |
|------|------------------------------|------------------|
| 谁写的 | 我们自己在 `TenkaichiGame` 模块里写的 | Epic 写的现成插件 |
| 类名有没有 `Lyra` 前缀 | 有（`LogTenkaichi` 等） | **没有**（就叫 `AModularCharacter`） |
| 教学动作 | 用户自己写代码 | 直接复制插件目录，**不自己重写** |
| 前缀替换规则适用吗 | 适用（`Lyra`→`Tenkaichi`） | **不适用**（类名里没有 `Lyra`） |

> 这就是为什么阶段二不是"教用户重写这两个插件"，而是"理解原理 + 结构对齐（复制现成插件）"。

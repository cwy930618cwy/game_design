# 3.4.3 InputConfig —— 总 md

## 一、为什么要有这一节

前面 3.4.1 摘了 `AbilitySourceInterface`（技能来源接口）、3.4.2 摘了 `AbilityTagRelationshipMapping`（技能标签关系映射）。
这一节是 GAS 叶子的第三片：**`InputConfig`（输入配置）**。

它解决一个问题：**把"玩家按下的按键（输入动作）"和"游戏里的技能标签"绑定起来。**

举个栗子：玩家按下 `鼠标左键` → 输入动作 `IA_Fire` → 标签 `InputTag.MouseButton.Left` → 触发"开火"这个技能。
`InputConfig` 就是存这张"按键 → 标签"对照表的地方。

## 二、真实依赖核实（铁律 30/31）

> 逐个读 Lyra 源码 `.h`（`#include` + 前置声明）+ `.cpp`（运行时硬调用），依赖追到底。

| 文件 | 依赖 | 能否现在教 |
|------|------|-----------|
| `LyraInputConfig.h` | 引擎 `UDataAsset` + `GameplayTagContainer` + 前置声明 `UInputAction`（不阻塞编译） | ✅ 真独立 |
| `LyraInputConfig.cpp` | 引擎 + `LogLyra`（L1 已教） | ✅ 真独立 |

> `UInputAction` 来自引擎的 **EnhancedInput** 插件（UE5 自带，非第三方），`.h` 里只是**前置声明 + 指针字段**，不阻塞编译；`.cpp` 里只调用了 `UInputAction` 的指针成员，也无需额外依赖。**结论：可独立编译。**

## 三、本文件里有什么（全景）

一个 `UDataAsset`（数据资产，编辑器里配置）+ 一个配套结构体 + 2 个查询函数：

### 1. 结构体 `FTenkaichiInputAction`（一条"输入动作 ↔ 标签"的映射）

```cpp
USTRUCT(BlueprintType)
struct FTenkaichiInputAction
{
	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly)
	TObjectPtr<const UInputAction> InputAction;   // 输入动作（比如 IA_Fire）

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly, Meta = (Categories = "InputTag"))
	FGameplayTag InputTag;                        // 技能标签（比如 InputTag.MouseButton.Left）
};
```

### 2. 数据资产类 `UTenkaichiInputConfig`（装着两堆这样的映射）

```cpp
UCLASS(BlueprintType, Const)
class UTenkaichiInputConfig : public UDataAsset
{
	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly, Meta = (TitleProperty = "InputAction"))
	TArray<FTenkaichiInputAction> NativeInputActions;   // 原生输入（手动绑定）

	UPROPERTY(EditDefaultsOnly, BlueprintReadOnly, Meta = (TitleProperty = "InputAction"))
	TArray<FTenkaichiInputAction> AbilityInputActions;  // 技能输入（自动绑定到技能）
};
```

### 3. 两个查询函数（根据标签找输入动作）

```cpp
const UInputAction* FindNativeInputActionForTag(const FGameplayTag& InputTag, bool bLogNotFound = true) const;
const UInputAction* FindAbilityInputActionForTag(const FGameplayTag& InputTag, bool bLogNotFound = true) const;
```

## 四、为什么分成"原生"和"技能"两组？

这是 Lyra 输入设计的核心思想：

| 组 | 用途 | 绑定方式 |
|----|------|---------|
| **NativeInputActions**（原生） | 游戏 UI 操作、非技能的输入（如打开菜单、暂停） | **手动**绑定，代码里自己写绑定逻辑 |
| **AbilityInputActions**（技能） | 触发 GAS 技能的输入（开火、跳跃、翻滚） | **自动**绑定，按标签自动接到对应技能上 |

> 这样分，是因为技能输入将来要自动跟 `GameplayAbility` 挂钩（阶段五 `LyraHeroComponent` / `AbilitySystemComponent` 会用到），而原生输入不用，所以分成两个数组，逻辑更干净。

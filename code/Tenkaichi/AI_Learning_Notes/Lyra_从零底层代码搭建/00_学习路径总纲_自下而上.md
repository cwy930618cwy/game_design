## 三、自下而上的真实依赖层次（全景地图）

> 依据：逐个查证 `Source/LyraGame/**/*.h` 和 `.cpp` 的 `#include` + 硬调用（铁律 30/31），不是凭目录语义猜。
> 原则：**被依赖的在下，依赖别人的在上**。搭建时从下往上逐层推进。
> ⚠️ 本节反映**真实依赖**，与"按目录语义分的层"不同——下面【重要】说明了为什么。

```
┌─────────────────────────────────────────────────────────┐
│  L7  业务层（玩法）：Weapons / Interaction / Equipment   │  ← 最上
│       GameFeatures 内容插件（ShooterCore 等）            │
├─────────────────────────────────────────────────────────┤
│  L6  表现层：UI / Animation / Audio / Feedback / Cosmetics│
├─────────────────────────────────────────────────────────┤
│  L5  Gameplay 系统：AbilitySystem / Inventory / Teams     │
│       Camera / Input（EnhancedInput 绑定）               │
├─────────────────────────────────────────────────────────┤
│  L4  角色与玩家：Character / Player / GameModes /        │
│       Experience（GameFeature 挂载机制）                 │
├─────────────────────────────────────────────────────────┤
│  L3  系统基础：System（GameInstance/AssetManager/Engine） │
│       Messages（GameplayMessageRouter 消息总线）         │
├─────────────────────────────────────────────────────────┤
│  L2  轻量插件：ModularGameplayActors（模块化 Actor 基类）│
│       GameplayMessageRouter（消息路由）                  │
├─────────────────────────────────────────────────────────┤
│  L1  模块地基：Game 模块（.uproject/Build.cs/模块入口）  │
│       LyraLogChannels（日志）/ LyraGameplayTags（Tag）   │
└─────────────────────────────────────────────────────────┘
                        引擎原生类（AGameMode/ACharacter 等）
```

> ### 【重要】为什么"按目录语义的 L1~L7"不能直接当教学顺序（2026-10-08 教训）
>
> 上面这张 L1~L7 的图是**按目录语义**分的层，看起来清晰，但**它和真实依赖是错位的**。真实依赖（查证后）是这样的：
>
> ```
> 【System 目录】（L3）里藏了两类截然不同的东西：
>   ✅ 真独立的：LyraGameEngine（UGameEngine）、LyraGameplayCueManager（UGameplayCueManager）
>   ❌ 假独立的：LyraAssetManager（依赖 GameData+PawnData+GAS）、LyraGameData（依赖 AssetManager）
>                 LyraGameInstance（依赖 CommonGame 插件 + Player）
>
> 【角色体系】（L4）被 GAS 反向依赖：
>   LyraGameplayAbility → Character / PlayerController / HeroComponent / GameplayEffectContext ...
>
> 【GAS 核心】（L5）又依赖角色体系：
>   LyraAbilitySystemComponent → GameplayAbility / GlobalAbilitySystem / AssetManager / GameData / AnimInstance
> ```
>
> 一句话：**L3 的 AssetManager / GameData / GameInstance 和 L4 的角色、L5 的 GAS 是互相缠绕的**。按"阶段三系统 → 四角色 → 五GAS"的顺序教，到 AssetManager 就会撞墙（这正是 2026-10-08 卡住的原因）。
>
> **因此：L1~L7 只用于"理解 Lyra 整体"，教学顺序必须看下面第四节【真实依赖链驱动的阶段划分】，它把缠绕区作为一个整体按依赖自下而上铺开。**

## 四、分层阶段划分（学习里程碑）

> ⚠️ **本节阶段划分严格按真实依赖链（铁律 30/31），不是按目录语义**。阶段三及以后之所以要这样重排，正是因为 L3 的 `AssetManager`/`GameData`/`GameInstance` 是"收口类"，要等它们依赖的角色+GAS 就位才能教——见第三节的说明。

### 阶段一（L1 模块地基）✅ 已完成
建 `TenkaichiGame` 模块、Build.cs 依赖、模块入口、日志通道、GameplayTags。
对应：`LyraGame.Build.cs`、`LyraGameModule.cpp`、`LyraLogChannels.*`、`LyraGameplayTags.*`

### 阶段二（L2 底层插件）✅ 已完成
引入 ModularGameplayActors、GameplayMessageRouter（理解"模块化 Actor"和"消息总线"）。
对应：`Plugins/ModularGameplayActors`、`Plugins/GameplayMessageRouter`

### 阶段三（L3 系统基础地基 + GAS 叶子）— 现在从这里继续

> **为什么这么设计**：L3 的 System 类里，只有 `GameEngine` 和 `GameplayCueManager` 真独立；`AssetManager`/`GameData`/`GameInstance` 都依赖后面的角色+GAS。而角色+GAS 又依赖一批 GAS 叶子类。所以阶段三先铺"地基 + 叶子"，把依赖的底打好。

| 步骤 | 内容 | 真实依赖 | 状态 |
|------|------|---------|------|
| 3.1 | **CommonGame + CommonUser 插件**（从 Lyra `Plugins/` 复制，含 CommonUI/CommonInput 依赖） | GameInstance/PlayerController 的父类，**必须先装** | ⬜ 待做 |
| 3.2 | `TenkaichiGameEngine`（`UGameEngine`） | 引擎 | ✅ 已教完 |
| 3.3 | `TenkaichiGameplayCueManager`（`UGameplayCueManager`） | 引擎 GAS + LogChannels | ⬜ 待做 |
| 3.4 | GAS 叶子：`AbilitySourceInterface` → `AbilityCost` → `AbilityTagRelationshipMapping` → `InputConfig` | 引擎 GAS / EnhancedInput | ⬜ 待做 |

> 3.1~3.4 完成后，"地基 + 叶子层"就位。这些是后续 `AssetManager`/`PawnData`/角色体系都会用到的底层，**必须先有**。

### 阶段四（角色体系，自下而上）— 依赖 GAS 叶子 + CommonGame

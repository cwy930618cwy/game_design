# 阶段二：底层插件（L2）—— 总 md

> **定位**：本文件是阶段二（L2 底层插件）的**总入口 + 全景地图**。
> 目标：理解并一比一还原 Lyra 依赖的**两个轻量插件**——`ModularGameplayActors`（模块化 Actor 基类）和 `GameplayMessageRouter`（消息路由）。这两个插件在依赖层次里，位于 `TenkaichiGame` 模块**之下**（被 L3/L4/L5 依赖），所以要先搭好。

---

## 一、为什么有这一层（解决什么问题）

回到总纲的依赖层次图：

```
L1 模块地基：Game 模块（.uproject/Build.cs/模块入口/日志/Tag）  ← 已完成
L2 底层插件：ModularGameplayActors / GameplayMessageRouter      ← 本阶段
L3 系统基础：GameInstance / AssetManager / GameEngine / 消息
L4 角色与玩家：Character / Player / GameMode / Experience
...
```

L1 我们已经把 `TenkaichiGame` 模块本身建好了。但一个游戏不能只有模块——它需要**能跑起来的 Actor、GameMode、PlayerState** 这些"演员"。Lyra 不是直接继承引擎原生的 `ACharacter`/`AGameMode`，而是先套了一层**模块化基类**，再往上盖自己的逻辑。

这一层要解决的核心问题有两个：

1. **模块化扩展（ModularGameplayActors）**：让一个 Actor（角色/玩家状态/GameMode…）能被"游戏功能插件（Game Feature Plugin）"在**运行时动态扩展**，而不是写死在类里。这是 Lyra 整个"体验系统（Experience）"能玩起来的地基。
2. **松耦合消息通信（GameplayMessageRouter）**：让"毫无关联"的两个对象之间能互相发消息/监听消息，不需要互相引用。这是 Lyra 里"死亡事件""重置事件"等跨系统通知的通道。

> 一句话：**L2 给了两个"万能底座"——一个让 Actor 能被扩展，一个让对象能互相传话。**

## 三、关键概念（先建立认知，再拆小步）

### 概念 1：什么是"模块化 Actor"？为什么不能直接继承 `ACharacter`？

引擎原生 `ACharacter` 是一个"写死"的类——它的能力在编译时就固定了。但 Lyra 想让**同一个角色类**在不同玩法（射击模式 / 大逃杀模式）下拥有**不同的能力组合**，这些能力由"Game Feature 插件"动态提供。

`AModularCharacter` 的作用就是：继承 `ACharacter`，但**额外留一个"挂钩子"的接口**（通过 `ModularGameplay` 插件的扩展机制），让别的插件能在运行时往这个 Actor 上**动态添加组件**。这样角色就"可插拔"了。

> 类比：原生 `ACharacter` 是一台"出厂焊死"的机器；`AModularCharacter` 是同一台机器，但**留了一排扩展插槽**，可以随时插拔功能卡。

### 概念 2：什么是"消息路由"？为什么用 Tag 而不是直接调用？

传统做法：A 对象想通知 B 对象，得**拿到 B 的引用**，然后调 B 的方法。这会带来强耦合（A 必须认识 B）。

消息路由做法：A 和 B 都只认识一个"中间人"（`UGameplayMessageSubsystem`）和一个"暗号"（GameplayTag）。A 说"我广播 `GameplayEvent.Death` 消息"；B 说"我监听 `GameplayEvent.Death`"。中间人负责牵线，A 和 B 永远不需要互相认识。

> 类比：对讲机广播。A 不需要知道 B 是谁、在哪，只要喊一句暗号，所有守着这个暗号的人都能收到。

### 概念 3：这两个插件是"外部依赖"，不是 `TenkaichiGame` 里的代码

注意区分：L1 的日志通道、GameplayTags 是**我们自己在 `TenkaichiGame` 模块里写的**；而 L2 这两个插件是 **Lyra 自带的独立插件**，我们（Tenkaichi 项目）是"引用/依赖"它们，不是"自己重写"它们。

所以本阶段的学习重点是**理解它们怎么工作**，而不是把代码抄进 `TenkaichiGame`。实际上，`TenkaichiGame.Build.cs` 里早就已经写了依赖 `ModularGameplayActors` 和 `GameplayMessageRuntime`（见 L1 的 1.3）。

## 四、教学顺序（本阶段怎么走）

按"先搭地基、再教上层依赖"的原则，以及两个插件的依赖关系：

1. **先教 ModularGameplayActors**（它是"角色能被扩展"的地基，后面 L4 的 Character/GameMode 都继承自它）
   - 总概念 → 逐个类拆 `.h`/`.cpp`
2. **再教 GameplayMessageRouter**（它是"对象间通信"的地基，后面 L3/L4 大量用到消息广播）
   - 总概念 → 逐个类拆 `.h`/`.cpp`

> 注：这两个插件**本身互相独立**，没有谁依赖谁，所以顺序上先教哪个都行。我建议先 `ModularGameplayActors`（更贴近后面 L4 要继承的基类），你可以提出异议。

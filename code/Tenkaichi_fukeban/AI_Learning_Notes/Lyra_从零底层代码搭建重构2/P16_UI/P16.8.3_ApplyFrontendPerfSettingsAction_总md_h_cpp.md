## 一、这个类解决什么问题（先讲为什么）

主菜单（前端）不需要高画质——它只是静态 UI + 背景场景。如果沿用游戏内的高画质设置，会浪费性能（笔记本风扇狂转、耗电）。

`UApplyFrontendPerfSettingsAction` 是一个 **GameFeatureAction**：前端经验激活时，告诉 `ULyraSettingsLocal`"现在用前端性能设置"（低画质）；前端经验停用时恢复。

**难点**：多个前端经验可能同时激活（PIE 多 world）。所以用**引用计数**（`ApplicationCounter`）：
- 计数从 0 → 1：真正应用前端设置。
- 计数从 1 → 0：真正恢复。

> **类比**：和 P15.3 的 `SplitscreenConfig` 投票计数**完全同一个模式**——多个来源要求同一件事，全部撤销才恢复。

## 三、关键点讲解

### 1. `static int32 ApplicationCounter`——静态引用计数

```cpp
static int32 ApplicationCounter;
...
int32 UApplyFrontendPerfSettingsAction::ApplicationCounter = 0;   // .cpp 里定义
```

和 P15.3 的 `GlobalDisableVotes` 一样：**静态成员**（所有实例共享），`.h` 声明 + `.cpp` 定义一次。

**为什么必须静态？** 因为多个前端经验（多个 Action 实例）要共同决定"要不要应用前端设置"。

### 2. 引用计数模式（0→1 应用，1→0 恢复）

```cpp
// 激活
ApplicationCounter++;
if (ApplicationCounter == 1)   // 从 0 变 1：真正应用
{
	// SetShouldUseFrontendPerformanceSettings(true);
}

// 停用
ApplicationCounter--;
check(ApplicationCounter >= 0);   // 不能变负（激活/停用不配对就是 bug）
if (ApplicationCounter == 0)      // 归零：真正恢复
{
	// SetShouldUseFrontendPerformanceSettings(false);
}
```

**和 P15.3 SplitscreenConfig 的对比**：

| 方面 | P15.3 SplitscreenConfig | P16.8.3 ApplyFrontendPerfSettings |
|------|------------------------|-----------------------------------|
| 计数粒度 | **每个 viewport 一份**（`TMap<FObjectKey, int32>`） | **全局一份**（单个 `int32`） |
| 为什么 | 分屏时每个 viewport 独立 | 性能设置是**全局**的（不分 world） |
| 校验 | 无 | `check(ApplicationCounter >= 0)` |

> 注释里解释了为什么全局：**"游戏用户设置（以及它们驱动的引擎性能/可伸缩性设置）是全局的，所以对多人 PIE 来说没必要按 world 追踪"**。

### 3. `check(ApplicationCounter >= 0)`——不能变负

```cpp
ApplicationCounter--;
check(ApplicationCounter >= 0);
```

`check`（不是 `ensure`）：计数变负是**严重逻辑错误**（激活/停用不配对），直接崩溃暴露问题。

> 对比 P15.3 没有这个检查——因为那里用 `TMap` 按 key 存，不会"变负"。

### 4. `final` + `meta=(DisplayName=...)`

```cpp
UCLASS(MinimalAPI, meta = (DisplayName = "Use Frontend Perf Settings"))
class UApplyFrontendPerfSettingsAction final : public UGameFeatureAction
```

- `final`：终点类（不再继承）。
- `meta=(DisplayName="Use Frontend Perf Settings")`：编辑器里显示为 "Use Frontend Perf Settings"。

### 5. 直接继承 `UGameFeatureAction`（不是 `WorldActionBase`）

```cpp
class UApplyFrontendPerfSettingsAction final : public UGameFeatureAction
```

对比 P15.3/P15.4/P15.5/P15.6/P15.7 都继承 `UGameFeatureAction_WorldActionBase`（需要 world）。

**为什么这个不需要？** 因为性能设置是**全局**的（不分 world），所以不需要 `AddToWorld`。

> 这是"选哪个基类"的判断依据：**需要按 world 处理 → `WorldActionBase`；全局处理 → 直接 `UGameFeatureAction`**。

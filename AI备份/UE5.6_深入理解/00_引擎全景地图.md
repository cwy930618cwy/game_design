# UE5.6 引擎全景地图

> 目标：一眼看懂 UE5 引擎的完整结构，知道每个文件夹是干嘛的、该往哪找代码。
> 
> 和 `UE5.6_源码分析` 的区别：那个是"鸟瞰 + 类继承"，这个是"按模块深入，逐个击破"。

## 二、Engine 目录（核心）

```
Engine/
├── Binaries/            ← 编译产物（.dll / .exe），你不需要看
├── Build/               ← 构建脚本（.bat / .sh），打包时用
├── Config/              ← 引擎默认配置（.ini），了解即可
├── Content/             ← 引擎内置资源（默认材质、音效、蓝图模板）
├── Documentation/       ← 离线文档（.udn = Unreal Document Network）
├── Extras/              ← 附加工具（Python 脚本、性能分析器）
├── Intermediate/        ← 编译中间文件，自动生成，不用管
├── Platforms/           ← 各平台特定代码（Android/iOS/Linux...）
├── Plugins/             ← ★ 插件（GAS、EnhancedInput、MetaHuman...）
├── Programs/            ← 独立程序（UnrealBuildTool、ShaderCompiler...）
├── Shaders/             ← 着色器源码（.usf / .ush），渲染相关
├── Source/              ← ★★★ 所有 C++ 源码（重点中的重点）
└── Saved/               ← 运行时生成的临时文件
```

## 三、Source 目录（源码核心）

```
Engine/Source/
├── Runtime/             ← ★ 运行时（游戏跑起来需要的代码）
├── Editor/              ← 编辑器（只在编辑器里跑的代码）
├── Developer/           ← 开发工具（打包、调试、分析工具）
├── Programs/            ← 独立程序的源码（UBT、UHT 等）
└── ThirdParty/          ← 第三方库（PhysX、FMOD、Vulkan SDK...）
```

## 七、命名前缀速查（看到前缀就知道是啥）

UE 所有东西都有**前缀字母**，一看开头就知道它是什么类别。**这是 UE 最基础、最常见的命名规范，忘了随时回来看。**

### 常见前缀总表

| 前缀 | 含义 | 例子 | 生命周期管理 |
|------|------|------|:---:|
| **T** | **模板类**：能指向/装载任意类型（`<类型>` 可换） | `TArray`、`TMap`、`TSet`、`TSharedPtr`、`TObjectPtr` | 取决于模板 |
| **F** | **固定类型**：就是某一种具体类型，不能换 | `FVector`、`FString`、`FMath` | 栈/智能指针 |
| **U** | UObject 类（受 GC 管） | `UActorComponent`、`UGameInstance` | **GC** |
| **A** | Actor 类（派生自 AActor） | `AActor`、`APawn`、`ACharacter` | **GC** |
| **E** | 枚举（Enum） | `EEnemyState`、`EDamageType` | - |
| **I** | 接口（Interface，以 I 开头） | `IAbility`、`IMovement` | - |
| **G** | 全局函数/类（Global，较少见） | `GEngine`、`GWorld` | 全局单例 |
| **b** | 布尔变量（小写 b 开头） | `bIsDead`、`bCanJump` | - |
| **S** | Slate 类（UI，较少见） | `SButton`、`SBox` | - |
| **C** | 旧版组件命名（少见，现在多用 U） | `CUIWidget` | - |

### 核心记忆（新手先记这 5 个）

```
T  → 模板类（TArray/TMap）
F  → 普通类（FVector/FString）
U  → UObject（UGameInstance）→ 受 GC 管
A  → Actor（ACharacter）→ 受 GC 管
E  → 枚举（EEnemyState）
b  → 布尔（bIsDead，小写 b）
```

### 一看到类型怎么判断"谁管它内存"

```
看到 U 或 A 开头 → 受 GC 管（用 TObjectPtr / TWeakObjectPtr）
看到 F 开头       → 普通类（用 TSharedPtr / TUniquePtr / TWeakPtr）
```

### 为什么 TSharedPtr 不用 GC 管？

因为它管的是 **F 开头的普通 C++ 类**（非 UObject），不是 U/A 开头的 UObject。UObject 才归 GC，普通类归你（用智能指针）管。

> **经验**：看到 `TSharedPtr` / `TUniquePtr` 装的都是 **F 前缀**对象；看到 `TObjectPtr` / `TWeakObjectPtr` 装的都是 **U/A 前缀**对象。**前缀直接告诉你能不能塞给智能指针。**

### 补充：函数/变量命名

- **函数**：通常也带类前缀或直接描述性命名，如 `AActor::TakeDamage()`（类前缀 + 动词）
- **变量**：布尔 `b` 开头，其他按类型
- **参数**：`In` 前缀表示入参（`InHealth`），`Out` 前缀表示出参（`OutResult`）

> **经验**：`InXxx` = 传进来的参数，`OutXxx` = 带出去的参数。看源码时非常有用。

## 八、教学规范（本笔记系列的铁律）

> **这条是整个学习笔记系列的指导思想，每次教学都必须遵守。**

### 核心原则：概念必须配具体场景，不许空讲理论

讲解 UE5 / C++ 等**任何**技术概念时，绝不能只堆理论定义。每讲一个概念 / 类型 / 函数，**必须同时配上一个具体的、能写进代码的游戏或项目使用场景**，让理论落到实际应用上。

### 场景的三个要求

1. **具体**：能写进代码，不是抽象描述。例如"角色掉血时血条要更新"、"技能冷却查询"、"死亡事件通知"。
2. **游戏相关**：尽量贴近 UE 实际开发（战斗、技能、UI、AI 等）。
3. **可运行**：配的代码片段应当是完整、能跑的，而不是残缺的伪代码。

### 举例（符合规范 vs 违反规范）

| 类型 | ❌ 空讲理论 | ✅ 配了场景 |
|------|-----------|-----------|
| TSharedPtr | "它是共享所有权的智能指针，引用计数归零时自动销毁" | "技能系统的 Buff 数据被角色面板/HUD/日志三处共享，谁都不用手动释放" |
| TWeakObjectPtr | "它是 UObject 世界的弱引用，不阻止 GC" | "角色被杀死时记录凶手，但不想为了记录就保住已死的小怪（否则越打越卡）" |
| TObjectPtr | "它是 UE5 推荐的 UObject 指针，替代裸指针" | "角色长期锁定攻击目标，防止目标被 GC 中途回收" |

### 落地提醒

- 每次教学、写笔记、改文档时，先问自己：**这个概念配具体场景了吗？**
- 如果只是定义 + 语法，没有场景 → 不合格，要补上真实使用案例。

> 这条规范要像"命名前缀"一样，忘了一查就能想起来。它决定了本系列笔记是否真正可学会。

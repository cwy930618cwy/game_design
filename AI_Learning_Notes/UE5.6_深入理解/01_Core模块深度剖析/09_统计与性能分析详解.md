# 09 — 统计与性能分析详解（Stats/ + ProfilingDebugging/）

> **定位**：Core 里"性能优化"相关的两块——`Stats/`（性能统计）和 `ProfilingDebugging/`（性能分析工具）。它们是**找"哪里卡"的工具**。
>
> **一句话**：`Stats/` = **量化每段代码耗时**（SCOPE_CYCLE_COUNTER 标记）；`ProfilingDebugging/` = **把耗时数据导出来看**（Unreal Insights 分析器）。配套用：Stats 统计，ProfilingDebugging 分析。
>
> **文件**：`Core/Public/Stats/`、`Core/Public/ProfilingDebugging/`

---

## 一、先搞懂：为什么要性能分析？（"卡"不知道在哪）

游戏掉帧卡顿，你得知道**卡在哪段代码**。凭感觉猜没用，要**量化数据**——知道每段代码花了多少毫秒，才能精准优化。

```
❌ 瞎猜："好像是物理卡？好像是 AI 卡？"
✅ 量化：Unreal Insights 显示 "AI 更新占了 8ms，物理占了 2ms" → 去优化 AI
```

**性能分析的价值**：把"感觉卡"变成"数据证明哪卡"。

---

## 二、Stats/ 和 ProfilingDebugging/ 分工

| | Stats/ | ProfilingDebugging/ |
|---|---|---|
| 干嘛的 | **标记**代码段，统计耗时/次数 | 把数据**导出/分析**（Unreal Insights） |
| 常用宏 | `SCOPE_CYCLE_COUNTER`、`DECLARE_STATS_GROUP` | `PROFILE` 标记、分析器接入 |
| 关系 | 先**统计** | 再**分析** |

**流程**：你用 `Stats/` 的宏给代码打"计时标记" → 用 `ProfilingDebugging/` 的 Unreal Insights 查看分析结果。

---

## 三、Stats/ —— 性能统计（重点）

### 3.1 SCOPE_CYCLE_COUNTER —— 统计一段代码耗时

在函数里加一行宏，这段代码的耗时就会被统计：

```cpp
#include "Stats/Stats.h"

void AMyCharacter::Tick(float DeltaTime) {
    SCOPE_CYCLE_COUNTER(STAT_CharacterTick);   // ← 标记：统计这段耗时
    // ...角色更新逻辑
}
```

**具体场景**：想知道"角色每帧 Tick 花了多少时间"：

```cpp
void UpdateAllEnemies() {
    SCOPE_CYCLE_COUNTER(STAT_EnemyUpdate);   // 统计敌人更新耗时
    for (auto& Enemy : Enemies) {
        Enemy->UpdateAI();
    }
}
```

**运行后**：在编辑器按 `~` 打开控制台，输入 `stat` 相关命令，就能看到这段代码的耗时统计。

### 3.2 自定义统计组（DECLARE_STATS_GROUP）

可以自己定义"统计分组"，把相关统计归到一起：

```cpp
// 声明统计组
DECLARE_STATS_GROUP(TEXT("MyGame"), STATGROUP_MyGame, STATCAT_Advanced);

// 声明一个统计项
DECLARE_CYCLE_STAT(TEXT("伤害计算"), STAT_DamageCalc, STATGROUP_MyGame);

// 在代码里用
SCOPE_CYCLE_COUNTER(STAT_DamageCalc);   // 统计"伤害计算"耗时
```

## 四、ProfilingDebugging/ —— 性能分析（重点）

### 4.1 Unreal Insights —— 最常用的性能分析器

UE5 的 **Unreal Insights** 是官方的性能分析工具，能看到整个游戏的帧耗时、线程、内存。

**使用流程**：
1. 运行游戏时打开 Unreal Insights（或命令行加 `-statnamedevents` 等）
2. 记录一段时间
3. 在分析器里看每个函数耗时

### 4.2 PROFILE 标记 / TRACE 宏

```cpp
#include "ProfilingDebugging/ProfilingHelpers.h"

// 给一段代码加分析标记
TRACE_CPUPROFILER_EVENT_SCOPE(MyGame_ProcessFrame);
ProcessFrame();   // 这段会在 Insights 里被标记
```

**具体场景**：标记"AI 更新"这段，方便在分析器里单独看它耗时：

```cpp
void Tick(float dt) {
    TRACE_CPUPROFILER_EVENT_SCOPE(Update_AI);   // 标记
    UpdateAI();
}
```

### 4.3 其他调试工具

| 工具 | 作用 |
|------|------|
| `ProfilingHelpers.h` | 截图、dump 辅助 |
| `UnrealMemory.h` 相关 | 内存分析辅助 |
| 崩溃处理 | 崩溃日志、mini-dump |

## 五、性能分析的完整工作流（配具体场景）

**场景：游戏"打怪时掉帧"，怎么找原因？**

```
第 1 步：用 Stats 标记可疑代码段
    void SpawnEnemies() {
        SCOPE_CYCLE_COUNTER(STAT_SpawnEnemies);   // 标记生成怪物的耗时
    }

第 2 步：用 Unreal Insights 跑一段，看数据
    打开 Insights → 记录打怪过程 → 看 SpawnEnemies 耗时多少

第 3 步：发现是"生成怪物时反复 new"耗时高
    优化：改用对象池（见 04 内存分配），避免频繁 new

第 4 步：再跑一次，确认耗时降下来了
```

**核心思路**：标记 → 分析 → 定位 → 优化 → 验证。

## 六、日常开发要学吗？—— 分轻重

| 工具 | 日常用得勤吗 | 建议 |
|------|:---:|------|
| `SCOPE_CYCLE_COUNTER` | 排查卡顿时用 | **了解**，卡顿再学 |
| Unreal Insights | 性能分析 | **会用**（官方主要工具） |
| `DECLARE_STATS_GROUP` | 自定义统计 | 进阶学 |
| 各种 TRACE 宏 | 分析标记 | 用到再看 |

**结论**：
1. **性能分析是"进阶"内容**，日常开发先不用学
2. 等真遇到卡顿/掉帧，再学 `SCOPE_CYCLE_COUNTER`（统计）+ Unreal Insights（分析）
3. 现在知道"这俩是找卡顿用的"就够

## 七、常见误区

**① 一上来就优化（不该优化的地方）**
```cpp
// ❌ 没量化就乱优化
// ✅ 先用性能分析确定"哪段最耗时"，再针对性优化
```

**② 以为"不卡"就不用管性能**
```cpp
// ❌ 现在不卡，等卡了再找，很难定位
// ✅ 平时了解怎么分析，卡了能快速定位
```

**③ 只看一帧，不看整体**
性能分析要看多次、整体趋势，不能只看一帧。

## 八、总结速查

```
Stats/ = 性能统计（标记耗时）
├── SCOPE_CYCLE_COUNTER(STAT_xxx)   ← 统计一段代码耗时
├── DECLARE_STATS_GROUP              ← 自定义统计组
└── DECLARE_CYCLE_STAT               ← 声明统计项

ProfilingDebugging/ = 性能分析（导出/分析）
├── Unreal Insights                  ← 官方性能分析器
└── TRACE_CPUPROFILER_EVENT_SCOPE    ← 分析标记

工作流：标记 → 分析 → 定位 → 优化 → 验证
日常：先不学，卡顿/掉帧时再深入
```

**一句话**：`Stats/` 统计"每段代码耗时多少"，`ProfilingDebugging/` 把数据导到 Unreal Insights 分析。这俩是**性能优化的工具**，日常开发先不用学，等真遇到卡顿再用。核心流程：**标记 → 分析 → 定位 → 优化**。

---

## 九、什么时候深入？

- **现在**：知道这俩是"找卡顿的工具"即可，不用学
- **遇到掉帧/卡顿**时：学 `SCOPE_CYCLE_COUNTER` + Unreal Insights
- **做正式性能优化**时：再深入 Stats 分组、TRACE 标记

> 和其他笔记不同：这块**属于真正的进阶**，前期先知道"有这东西、用在哪"，遇到性能问题再回头深入，效率更高。

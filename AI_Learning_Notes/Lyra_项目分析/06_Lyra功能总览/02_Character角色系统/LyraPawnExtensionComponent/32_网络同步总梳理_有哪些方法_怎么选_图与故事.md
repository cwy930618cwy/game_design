# 32 — 网络同步总梳理：有哪些方法？各自什么时候用？（配图 + 故事）

> **定位**：前面好几篇（LyraPawn/35/36/38、LyraPawnExtension 的 29/31）都在"零敲碎打"地讲网络复制。这篇把它们**收拢成一张总表**：UE 到底有哪几种"把东西同步到客户端"的方法、每种解决什么问题、Lyra 里在哪用。看完你就有全局了。
>
> **衔接**：这是网络同步的"地图篇"；细节可回看对应篇目。

---

## 〇、先搞清楚：网络同步到底在解决什么问题？

**一句话**：一台服务器 + 多台客户端，大家要看到**同一个游戏世界**——但世界上只有服务器是"权威"，客户端是"猜"。网络同步 = **把服务器上的变化，用最省带宽的方式告诉所有客户端**。

UE 的方法不是一种，而是**一整套**，按"**数据 vs 事件**"分两大派：

```
网络同步 = 两大类
├─ ① 状态同步（复制属性）：把"持续的状态"同步过去
│    例：血量 100→50、队伍从蓝变红、道具是否还在
│    特点：客户端"随时能读到最新值"，错过几帧下次还能补上
└─ ② 事件同步（RPC）：把"一次性的事"喊过去
      例：开枪、放技能、请求开门
      特点：只发生一次，错过了就没了（所以要可靠/不可靠选择）
```

**先记住这个分法**，后面所有方法都归这两类。

---

## 一、方法总表：UE 网络同步有哪几招？

| # | 方法 | 分类 | 一句话 | 在哪声明 |
|---|---|---|---|---|
| 1 | **Actor 复制** | 前置开关 | 整个 Actor 愿不愿意同步 | `AActor::SetReplicates(true)` |
| 2 | **组件复制** | 前置开关 | 组件愿不愿意跟着同步 | 组件构造 `SetIsReplicatedByDefault(true)` |
| 3 | **属性复制** | 状态同步 | 某属性值变了就同步 | `.h` `Replicated` + `.cpp` `DOREPLIFETIME` |
| 4 | **RepNotify** | 状态+事件 | 属性到了，顺便调个回调 | `ReplicatedUsing = OnRep_X` |
| 5 | **条件复制** | 优化 | 只同步给特定人/特定时刻 | `DOREPLIFETIME_CONDITION` |
| 6 | **Server RPC** | 事件 | 客户端喊服务器"我要做X"（带校验） | `UFUNCTION(Server, Reliable, WithValidation)` |
| 7 | **Client RPC** | 事件 | 服务器单独告诉某个客户端 | `UFUNCTION(Client, Reliable/Unreliable)` |
| 8 | **Multicast RPC** | 事件 | 服务器广播给所有人 | `UFUNCTION(NetMulticast)` |
| 9 | **可靠 vs 不可靠** | 传输质量 | 必达 vs 允许丢 | RPC/属性都可配 |
| 10 | **PlayerState/属性集复制** | 谁持有 | 跨死亡保留的数据放 PlayerState | 继承 ALyraPlayerState + DOREPLIFETIME |

> 别被 10 个吓到——**真正的核心就 4 个**：①Actor/组件复制（开关）、②属性复制（状态）、③RepNotify（到了调回调）、④RPC 三兄弟（事件）。其余是它们的变体和优化。

## 二、逐个展开（每种给 Lyra 真实例子）

### 方法 1+2：Actor 复制 / 组件复制 —— "大门开关"

```cpp
// Actor 级：这个角色愿意同步（通常在 Pawn/Character 构造或类默认）
SetReplicates(true);

// 组件级：这个组件愿意跟着同步（LyraPawnExtensionComponent 构造 L28）
SetIsReplicatedByDefault(true);
```
> 层层授权：**Actor 开 → 组件开 → 属性登记**，三层都过才同步（第 31 篇）。

### 方法 3：属性复制 —— "状态变了就同步"（最常用）

```cpp
// .h：标 Replicated
UPROPERTY(Replicated)
bool bIsWeaponAvailable;

// .cpp：登记进复制名单
void ALyraWeaponSpawner::GetLifetimeReplicatedProps(...)
{
	DOREPLIFETIME(ALyraWeaponSpawner, bIsWeaponAvailable);
}
```
> Lyra 真实例子：`LyraWeaponSpawner`（武器是否可捡）、`LyraInventoryManagerComponent` 的 `InventoryList`、`LyraTeamPublicInfo` 的 `TeamDisplayAsset`。

### 方法 4：RepNotify —— "同步到了顺便干活"

```cpp
// .h
UPROPERTY(ReplicatedUsing = OnRep_Health)
FGameplayAttributeData Health;

// .cpp（收到后调这个回调去刷新血条/广播）
void ULyraHealthSet::OnRep_Health(...) { ... }
```
> Lyra 真实例子：`LyraHealthSet` 的 Health/MaxHealth（第 15 篇）、`LyraPawnExtensionComponent` 的 PawnData（客户端靠它触发初始化）。

### 方法 5：条件复制 —— "不是所有人都要，只给该给的人"

```cpp
// CombatSet：只有属性所有者（自己）需要看到 BaseDamage
DOREPLIFETIME_CONDITION_NOTIFY(ULyraCombatSet, BaseDamage, COND_OwnerOnly, REPNOTIFY_Always);

// TeamPublicInfo：队伍显示资产只需初始同步一次
DOREPLIFETIME_CONDITION(ThisClass, TeamDisplayAsset, COND_InitialOnly);
```
> 省带宽的关键优化：**谁需要看才发给谁、什么时候需要才发**。

### 方法 6~8：RPC 三兄弟 —— "一次性事件"

```cpp
// 6. Server RPC：客户端→服务器，"我要开门/我要放技能"（服务器校验合法性）
UFUNCTION(Reliable, Server, WithValidation)
void ServerRequestOpenDoor();

// 7. Client RPC：服务器→某个客户端，"只有你知道这件事"
UFUNCTION(Client, Unreliable)
void ClientNotifyAbilityFailed(...);   // Lyra ASC 里就有（技能失败提示）

// 8. Multicast RPC：服务器→所有客户端，"大家看这个特效"
UFUNCTION(NetMulticast, Unreliable)
void MulticastPlayExplosionFX();
```
> Lyra 真实例子：`ALyraPlayerController` 里 `Server` RPC（带 `WithValidation` 校验）、`ULyraAbilitySystemComponent` 里 `Client, Unreliable` 的 `ClientNotifyAbilityFailed`（第 10 篇见过）。

### 方法 9：可靠 vs 不可靠 —— 传输质量

| | 可靠 Reliable | 不可靠 Unreliable |
|---|---|---|
| 保证 | **必达**，重发直到到达 | 可能丢，不重发 |
| 适合 | 重要事件（开门、放技能） | 高频次要（位置、特效、提示） |
| 代价 | 高（占带宽、可能阻塞队列） | 低 |

### 方法 10：PlayerState / 属性集复制 —— "数据放对地方"

- **跨死亡保留的数据**（分数、队伍、使用的 PawnData）→ 放 `APlayerState` 并 DOREPLIFETIME（LyraPlayerState 里 PawnData/MyTeamID 都这么同步）。
- **GAS 属性**（血量等）→ AttributeSet 里 `ReplicatedUsing`（LyraHealthSet）。

> 放对地方很重要：PlayerState 跨重生保留，Pawn 死了数据不丢。

## 三、核心难题：怎么选？(决策思路)

给你一张"遇到需求往哪走"的决策图：

```
我要让客户端知道一件事…
│
├─ 是"持续的状态"（血、队、开关）？
│     └─ 放哪：Actor/组件复制开 → 属性标 Replicated → DOREPLIFETIME
│         要不要顺便做反应？→ 加 ReplicatedUsing(OnRep)
│         所有人都要看吗？→ 不是 → 加 COND_ 条件
│
├─ 是"一次性的事件"（开枪、开门、请求）？
│     ├─ 客户端想对服务器干？      → Server RPC（要校验加 WithValidation）
│     ├─ 服务器想单独告诉一个人？  → Client RPC
│     └─ 服务器想广播给所有人？    → NetMulticast RPC
│         重要必达？→ Reliable     高频可丢？→ Unreliable
│
└─ 数据会跨死亡保留？→ 放 PlayerState（别放 Pawn）
```

> **一句话记忆**：**状态用"属性复制"，事件用"RPC"；先问自己是哪种，再选方法。**

## 四、结尾：看图 + 听故事

### 图：一局游戏里"网络同步全家福"（谁在同步什么）

```
       官方广播站（服务器）
       ┌────────────────────────────────────┐
       │ PlayerState（玩家档案·跨死亡保留）    │
       │   分数 MyTeamID PawnData ──DOREPLIFETIME──► 所有客户端都有一份
       │                                        │
       │ Pawn/Character（角色身体）              │
       │   MyTeamID 属性复制 ──────────────────►│ 同步队伍颜色
       │   (改了 → OnRep_MyTeamID → 广播)       │
       │                                        │
       │ 你按下"开门"请求 ──Server RPC──► 服务器 │
       │                       校验合法后        │
       │  ──────────NetMulticast RPC──────────► │ 大家看到门开了
       │                                        │
       │  ──────Client RPC(单独)──────────────► │ 只告诉你"你中奖了"
       └────────────────────────────────────┘
```

### 故事：全班一起玩"传声筒拼图"

想象一个班级（=一局游戏），老师在讲台上（=服务器），同学们各自桌上（=客户端）都摆着一份**拼图的副本**。目标：让大家手里的拼图**永远拼得一样**。

**情况 1：老师改了一块拼图（= 状态变了）**
老师的拼图从"天空是蓝的"改成"天空是红的"。老师不会把整幅拼图重发，只喊："**注意，天那块改成红色！**"（= 属性复制，只同步变了的属性）。每个同学听到就改自己桌上那块（= 客户端更新）。同学们不用问"为什么"，只需要**知道最新值**（= 状态同步的特点：随时可读最新，漏听下次还能补）。

**情况 2：某个同学想动拼图（= 客户端想做改变）**
小明想把自己那块拼图加一颗星星。他不能自己直接改（怕各改各的乱套），**先举手向老师申请**："老师我想加颗星星！"（= Server RPC）。老师检查合理（= 服务器校验），批准后广播："**小明那块加星星了！**"（= NetMulticast RPC）——大家才一起改。

**情况 3：老师只想告诉一个人**
小红拼对了，老师**只凑到她耳边**说："你做得对！"（= Client RPC），别人不知道。

**情况 4：重要的话 vs 随口的话**
老师说"明天春游"（重要）= 可靠 Reliable，哪怕有同学走神也要**再说一遍直到他听到**。老师随口说"今天食堂茄子不错"（次要）= 不可靠 Unreliable，没听到就算了，不影响上课。

**情况 5：全班都知道的"公共信息"（= PlayerState）**
每个同学的"学号、班级"贴在桌上，**永远都在、不随拼图换**（= 跨死亡保留的档案放 PlayerState）。

### 故事 ↔ 方法对照表

| 故事 | 方法 |
|---|---|
| 老师只喊"哪块变了" | 属性复制（DOREPLIFETIME） |
| 老师喊完，同学做记录/反应 | RepNotify（OnRep_X） |
| 小明举手申请改拼图 | Server RPC（可加 WithValidation） |
| 老师广播"都改了" | NetMulticast RPC |
| 老师凑耳边告诉一个人 | Client RPC |
| 重要的话反复说 / 随口的话丢了算了 | Reliable / Unreliable |
| 桌上永远贴着的学号班级 | PlayerState 复制 |
| 只让该听的人听到 | 条件复制（COND_OwnerOnly 等） |

## 五、总结一句话

> **UE 网络同步 = 状态同步（属性复制：变了就发，客户端随时能读到最新值）+ 事件同步（RPC：发生一次，喊一嗓子）。** 方法就四招核心：**Actor/组件复制（大门开关）→ 属性复制（状态）+ RepNotify（到了做反应）+ RPC 三兄弟（Server/Client/Multicast 处理事件）**，再配"可靠/不可靠"和"条件复制/PlayerState"做优化和归位。**选型口诀：状态用属性复制，事件用 RPC；重要必达用可靠，只有该知道的人用条件。**

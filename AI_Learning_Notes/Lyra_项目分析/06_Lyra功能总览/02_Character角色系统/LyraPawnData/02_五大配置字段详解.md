# 02 — `LyraPawnData` 五大配置字段详解

> **定位**：逐个讲透 `LyraPawnData.h` 第 35~53 行这五个字段——它们就是一份 Pawn 配置的"全部参数"。每个字段都回答一个问题："这个角色**是什么 / 会什么 / 怎么操作 / 镜头怎么跟**"。
>
> **不讲代码**，只讲每个字段"干嘛的、为什么需要它、填了之后发生什么"。

---

## 先看全貌

```cpp
TSubclassOf<APawn> PawnClass;                              // ① 造哪个类
TArray<TObjectPtr<ULyraAbilitySet>> AbilitySets;           // ② 给哪些能力
TObjectPtr<ULyraAbilityTagRelationshipMapping> TagRelationshipMapping;  // ③ 能力间的规则
TObjectPtr<ULyraInputConfig> InputConfig;                  // ④ 按键怎么绑
TSubclassOf<ULyraCameraMode> DefaultCameraMode;            // ⑤ 默认什么镜头
```

记住一个分组：**① 管"身体"，②③ 管"技能"，④ 管"操作"，⑤ 管"视角"**。

---

## ① `PawnClass` —— 造哪个 Pawn 类

```cpp
// Class to instantiate for this pawn (should usually derive from ALyraPawn or ALyraCharacter).
TSubclassOf<APawn> PawnClass;
```

**它是干嘛的**：指定"**用哪个 Pawn 类来造这个角色的身体**"。

- 类型是 `TSubclassOf<APawn>`——一个"能装 Pawn 子类的容器"（可以理解为"指向某个 Pawn 类的指针"）。
- 注释说得很清楚：通常应该填 `ALyraPawn` 或 `ALyraCharacter` 的子类。

**为什么需要它**：这是整份资产的**起点**。没有它，系统不知道要 new 出什么样的对象。

**填了之后发生什么**：运行时，生成系统读这个字段 → `new` 出对应的 Pawn 实例 → 后面的能力/输入/镜头都往这个实例上挂。

> **类比**：造车时，`PawnClass` = "用哪个底盘/车型"。它是第一步，决定了后面所有东西往哪装。

---

## ② `AbilitySets` —— 给哪些能力（GAS）

```cpp
// Ability sets to grant to this pawn's ability system.
TArray<TObjectPtr<ULyraAbilitySet>> AbilitySets;
```

**它是干嘛的**：列出"**要给这个角色的一堆能力集合**"。

- 类型是**数组**（`TArray`），说明一个角色可以有**多组**能力。
- `ULyraAbilitySet` 是 Lyra 对 GAS（GameplayAbilitySystem）的封装——一组能力通常包含：技能（Abilities）、属性（Attributes）、初始效果（Effects）等。

**为什么需要它**：把"这个角色会什么"数据化。战士有剑击、格挡；法师有火球、闪现——**区别就在填不同的 AbilitySets**。

**填了之后发生什么**：Pawn 造好后，系统遍历这个数组，把每组能力"授予"给角色的能力系统（ASC），角色就学会了这些技能、拥有了这些属性。

> **类比**：`AbilitySets` = "给这个角色装上哪些装备/技能书"。

---

## ③ `TagRelationshipMapping` —— 能力之间的规则

```cpp
// What mapping of ability tags to use for actions taking by this pawn
TObjectPtr<ULyraAbilityTagRelationshipMapping> TagRelationshipMapping;
```

**它是干嘛的**：定义"**能力标签之间的关系/互斥规则**"。

- 这是 GAS 里非常关键的概念。每个能力/状态都带"标签"（Tag），比如 `State.Debuff.Stun`（眩晕）、`Action.Attack`（攻击）。
- 这个映射表决定：**当某个标签存在时，哪些动作能做、哪些不能做**。

**为什么需要它**：游戏里大量逻辑依赖状态互斥——

- 眩晕时不能攻击
- 施法时不能移动
- 跳跃中不能二段跳

  这些规则如果写死在代码里会很乱，抽成一张"标签关系表"就能**数据化配置**。

**填了之后发生什么**：能力系统在判断"现在能不能放这个技能"时，会查这张表来决定允许/拒绝。

> **类比**：`TagRelationshipMapping` = "交通规则表"——红灯停、绿灯行，定义哪些状态能共存、哪些冲突。

---

## ④ `InputConfig` —— 按键怎么绑

```cpp
// Input configuration used by player controlled pawns to create input mappings and bind input actions.
TObjectPtr<ULyraInputConfig> InputConfig;
```

**它是干嘛的**：提供"**输入配置**"——把玩家的按键绑定到具体动作。

- 注释说得很明确：玩家控制的 Pawn 用它来"创建输入映射、绑定输入动作"。
- 里面通常包含：每个动作（跳跃、攻击、移动……）对应哪个键、用哪种触发方式。

**为什么需要它**：不同角色可能需要不同的操作方案。把它做成配置，就能让策划独立调整手感，不用碰代码。

**填了之后发生什么**：Pawn 造好并被控制器附身后，系统用这份配置建立 Enhanced Input 的映射上下文（Mapping Context），把按键和动作连起来。

> **类比**：`InputConfig` = "手柄/键盘的键位表"——按 A 做什么、按 B 做什么。

---

## ⑤ `DefaultCameraMode` —— 默认什么镜头

```cpp
// Default camera mode used by player controlled pawns.
TSubclassOf<ULyraCameraMode> DefaultCameraMode;
```

**它是干嘛的**：指定"**这个角色默认用哪种摄像机模式**"。

- 类型是 `TSubclassOf<ULyraCameraMode>`——又一个"类选择器"，选的是镜头模式类。
- Lyra 的相机系统是可插拔的模式（第三人称、第一人称、俯视角等），这里选默认用哪个。

**为什么需要它**：不同角色视角可能不同——第三人称的动作角色、第一人称的射击角色、俯视角的策略单位。用配置区分，不用改代码。

**填了之后发生什么**：Pawn 造好后，相机系统读取它，激活对应的 CameraMode，角色就有了正确的视角。

> **类比**：`DefaultCameraMode` = "装哪种摄像头/跟拍方式"。

---

## 五字段对照表

| 字段 | 回答的问题 | 类型特点 | 类比 |
|------|-----------|---------|------|
| `PawnClass` | 造哪个类？ | 单个类选择 | 用什么底盘/车型 |
| `AbilitySets` | 给哪些能力？ | **数组**（多组） | 装哪些装备/技能书 |
| `TagRelationshipMapping` | 能力间什么规则？ | 单张规则表 | 交通规则（红停绿行） |
| `InputConfig` | 按键怎么绑？ | 单份配置 | 手柄键位表 |
| `DefaultCameraMode` | 默认什么镜头？ | 单个类选择 | 装哪种摄像头 |

---

## 共同点：为什么都用 `EditDefaultsOnly, BlueprintReadOnly`？

注意这五个字段的 `UPROPERTY` 标注**完全一样**：

```cpp
UPROPERTY(EditDefaultsOnly, BlueprintReadOnly, Category = "...")
```

- **`EditDefaultsOnly`**：只能在**编辑器里、作为默认值**修改（运行时不能改）→ 保证配置稳定。
- **`BlueprintReadOnly`**：蓝图里能读、不能写 → 防止运行时误改。
- **`Category = "Lyra|XXX"`**：在编辑器细节面板里归到对应分类下，方便策划找。

> **一句话**：这五个字段都是"**只配一次、运行时只读**"的配置项，符合 DataAsset "不可变" 的设计初衷。

---

## 总结

```
一份 LyraPawnData = 回答五个问题：

  ① PawnClass         → 身体：造哪个 Pawn 类
  ② AbilitySets       → 技能：给哪些能力（可多组）
  ③ TagRelationshipMapping → 规则：能力间的互斥/允许关系
  ④ InputConfig       → 操作：按键绑什么动作
  ⑤ DefaultCameraMode → 视角：默认哪种镜头

前两个决定"是什么"，中间两个决定"怎么用"，最后一个决定"怎么看"。
全部只配一次、运行时只读 —— 这就是数据驱动的角色配置。
```

**一句话**：这五个字段把"一个角色**长什么样（PawnClass）、会什么（AbilitySets + TagMapping）、怎么操作（InputConfig）、镜头怎么跟（CameraMode）**"全部数据化了。它们是策划手里的配置项，运行时被系统读取并应用到造好的 Pawn 上。
